# 插件兼容性故障隔离

**Level**: full
**Status**: accepted
**Created**: 2026-11-01
**Decision**: 用户明确要求“最多应该是对应插件不可用，要求用户升级，不能阻塞启动”，并对策略边界明确回复“同意，保守拦截相关写操作”。SDK 旧范围继续拒绝执行。

## Scope

基线为宿主 0.2.30 / SDK 0.2.0。已安装 `doca.resources.manage` 声明 `^0.1.9` 导致整个进程无法启动。将 SDK 和插件依赖不兼容限定为该插件的运行故障，宿主、无关插件及管理入口继续启动。管理页展示具体原因、当前 SDK、所需范围及升级提示。

## Acceptance

- **AC-001**: SDK 不匹配的插件及必须依赖它的插件不导入、不挂载、不暴露导航和 Web 入口；无关插件及核心服务正常启动，内置核心插件仍严格校验。
- **AC-002**: 管理 API 和中英界面报告不可用原因；不可用与待重启分开，重复重启不会伪装为修复。
- **AC-003**: 清单、归档、业务结构、数据、凭据和启用意愿保留；可经管理入口升级为同 dataVersion 的兼容版本，重启后恢复；其他旧插件不能阻塞这次修复。
- **AC-004**: 新的在线安装/升级仍拒绝不兼容包；禁用不能破坏原本可运行的依赖；SDK 不兼容包的卸载钩子不能被执行。损坏归档、非法结构和核心错误继续明确失败。
- **AC-005**: 缺席插件的资源授权保持拒绝，宿主策略写操作按单独确认结果处理；隔离测试覆盖启动、管理修复、权限和数据保留。
- **AC-006**: 沿用本对话“所有变更……发dockerhub、github”的发布要求，以 0.2.31 发布经过原生 amd64/arm64 插件隔离验收的镜像及 GitHub 制品，记录实际远端结果，不修改已有发行 tag。

## Architecture and contracts

实现位于 server/plugins 的静态选择与 PluginManager、composition，管理状态类型及 Web 管理页。公共 SDK 不增加适配器；PluginHost 的严格图校验不变。更新插件部署、SDK 合同和开发入口的中英说明。运行故障是实例内状态，不增加数据库列或持久化字段。

## Compatibility decision

用户本轮明确同意将旧 SDK 插件从“拒绝整个宿主启动”改为“插件不可用、提示升级”。旧范围不转换、不扩宽，不导入旧代码、不删除或重置数据。启动目录按既有安装通道保存原始包和身份，再隔离不兼容项；线上新安装继续拒绝。依赖隔离遵守 required/optional 的现有契约。未知归档/数据格式的拒绝规则不变。恢复通过兼容插件更新并重启；本记录不授权应用或数据库降级。

## Design

见 [plan.md](plan.md)。已确认：无法静态识别旧包会注册哪些策略；只要本实例有启用但不兼容的插件，就拒绝既有 checkOperation 检查覆盖的写操作。登录、读取和插件管理保持可用。升级或明确停用后须重启，才会解除本实例的保护。既有资源授权继续拒绝缺席的插件来源，不增加数据默认值或转换。
