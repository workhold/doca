# 인증, 등록 승인, 계정 연동

리모트 전용 데스크톱 클라이언트는 만료일이 없는 별도의 브라우저 인증 호스트 자격 증명을 추가합니다. 보기 [데스크톱 클라이언트 계약](desktop-client.ko.md)기존의 브라우저/모바일 세션은 그 만료일과 저장 규칙을 그대로 유지됩니다.

[中文](authentication.zh-CN.md)

이는 공간도 없고 조직 트리도 없는 현재의 Doca에 적용됩니다. 로컬 계정, 외부 신원 제공자, 등록 승인, 로그인 방법 변경 등을 포함합니다.

<a id="boundary"></a>

## 경계

한 Doca 사용자는 여러 로그인 ID를 연결할 수 있습니다. 문서, 권한, 아바타, 설정은 항상 안정적으로 존재합니다. `users.id`계정은 이메일, 표시 이름, 또는 전화번호로 결합되지 않습니다. 사용자는 원래 계정에 로그인하여 새로운 신분을 의도적으로 연결합니다.

이 설계는 프로필 데이터와 로그인 정보를 분리하며, 암시적 이메일 매칭이 아닌 명시적인 링크 방식을 사용합니다. 계정 생성과 활성화는 별개의 과정이므로, 검토 대기 상태가 가능합니다. 기존 계정은 다른 인증 제품으로 이전되지 않으며, Doca는 외부 authentik 서비스에 의존하지도 않습니다.

관리자는 자체 전체 페이지 셸을 사용합니다: 내비게이션, 스크롤 영역, 그리고 작업 공간으로 돌아가는 방법이 있습니다. 계정 설정은 자체 내비게이션을 사용합니다. 시각적 언어는 Doca의 것을 그대로 유지합니다.

<a id="three-registration-policies"></a>

## 3가지 등록 정책

관리자, 로그인 및 등록 섹션에서 각 항목은 별도로 설정됩니다.

| 입장 | 새로운 사용자 없음 | 자동 등록 | 승인이 필요함 |
| --- | --- | --- | --- |
| 사이트 비밀번호 | 등록 신청은 종료되었습니다. | 등록 후 로그인 가능 | 대기 중인 사용자가 생성됨 |
| 엔터프라이즈 OIDC | 이미 연결된 ID만으로 로그인할 수 있습니다. | 첫 번째 로그인은 사용자를 생성합니다. | 첫 번째 로그인 시 대기 중인 사용자가 생성됩니다. |
| 구글, GitHub, 위챗, QQ | 이미 연결된 ID만으로 로그인할 수 있습니다. | 첫 번째 로그인은 사용자를 생성합니다. | 첫 번째 로그인 시 대기 중인 사용자가 생성됩니다. |

이미 연결된 활성 사용자는 “닫힌 등록”으로 차단되지 않으며 다른 신원을 연결할 수 있습니다. 관리자가 생성한 사용자는 즉시 활성화됩니다. 대기 중인 사용자는 사이트 세션이 없어 문서나 WebSocket을 열 수 없습니다. 관리자는 전용 등록-검토 페이지를 사용하여 승인하거나 거부합니다. 일반 사용자의 켜기/끄기 기능으로는 대기 중인 계정을 승인할 수 없습니다. 승인 후 해당 사용자는 다시 로그인해야 합니다. 기존의 인증 프로세스는 활성화되지 않습니다.

외부 등록 및 모든 신원 제공자는 기본적으로 비활성화되어 있습니다. 비밀번호 입력 기능은 계속 사용 가능하므로, 신원 제공자 서비스 중단으로 인해 관리자가 접근이 차단되지 않습니다. 연락 확인, 전화 코드 로그인, 비밀번호 복구 기능이 존재합니다. 코드 발송 및 시도 제한은 공유 데이터베이스를 사용합니다. 비밀번호 로그인 및 공개 봇 IP 제한은 Redis가 설정된 경우 Redis 없이 프로세스별 카운터를 사용하며, Redis가 설정된 경우 공유 카운터도 사용하지 않습니다. SMS에는 별도의 허용 규칙이 있습니다. 제3자 소스는 카테고리 정책을 우회할 수 있습니다.

로그인 방법이 변경될 때, 서버는 활성 사용자와 관리자들을 활성화된 방법, 확인된 연락처, 비밀번호 식별자, 제공자 자격 정보와 비교하여 검사합니다. 변경 후 사용할 수 있는 방법이 없는 경우, 저장은 거부됩니다. 관리자는 "사용자들이 로그인 방법을 추가해야 하는지 요구" 옵션에서 새로운 방법을 먼저 선택할 수 있습니다. 그 사용자들이 사이트를 열 때는 반드시 확인하거나 연결해야 합니다. 모든 사람이 작업을 마칠 때까지는 기존 방법은 종료됩니다. 방법을 추가하더라도 기본적으로 사용하도록 강제되지는 않습니다.

<a id="identity-providers"></a>

## 식별 정보 제공자

- **OIDC SSO.** 예를 들어 Keycloak이나 authentik과 같은 표준 디스커버리 방식입니다. `openid-client` 6.8.8, 인증 코드와 PKCE S256, 상태, nonce, ID 토큰 서명 검사, 그리고 발급자, 청취자, 유효기간 검사. 클라이언트 인증은 `client_secret_post`개인 키 JWT, mTLS, SAML은 지원되지 않습니다. 단순한 OAuth 2는 OIDC 설정이 아닙니다.
- **구글.** 수정된 발견 `https://accounts.google.com`, 범위 `openid profile`출처가 이메일을 명시할 때 이메일로 연락해 주세요.
- **GitHub.** 인증 코드와 PKCE S256 및 `read:user`안정적인 숫자 ID는 그로부터 얻어짐 `/user`이메일이 발표될 때. `user:email` 인증된 주소 이메일을 읽습니다.
- **위챗.** 웹사이트 QR `snsapi_login`바인딩은 app id 아래의 OpenID를 사용합니다. UnionID는 계정을 합치지 않습니다. 이는 공식 계정 페이지, 미니프로그램, 모바일 앱 로그인이 아닙니다.
- **QQ.** 웹사이트 OAuth. 토큰 및 `me` JSON을 사용하면 프로필이 읽힙니다. `me.client_id` 설정과 일치해야 합니다.

위챗과 QQ 어댑터는 시뮬레이션된 응답을 사용하여 구현 및 테스트되었습니다. 이는 실제 플랫폼에서는 사용할 수 없습니다. 모든 외부 제공업체는 해당 플랫폼의 애플리케이션과 자격증명이 필요합니다. 이 프로세스에서 위챗과 QQ는 PKCE를 전송하지 않으며 OIDC PKCE와 동등하지 않습니다.

Doca는 SSO 클라이언트에만 해당합니다. OIDC 제공자로서의 역할을 하지만, SAML 및 글로벌 SSO 로그아웃 또는 취소 동기화 기능은 구현되어 있지 않습니다. ID 제공자에서 계정을 비활성화해도 이미 발급된 Doca 세션은 취소되지 않습니다. 브라우저 세션은 기본적으로 24시간으로 설정되며, 이는 설정할 수 있습니다. [로그인 생명주기](configuration.ko.md#login-lifetime)기존 세션은 저장된 만료일을 그대로 유지합니다. 사이트 관리자가 사용자를 비활성화하거나, 이후 IdP 생명주기 이벤트가 필요합니다.

<a id="deployment"></a>

## 배포

1. 각 플랫폼에서 신청서를 등록하세요. 설정된 HTTP(S)를 사용하세요. `DOCA_ORIGIN`프록시는 설정된 호스트를 유지합니다.
2. 플랫폼 설정 > 서비스 자격 증명 > SSO에서 자격 증명 이름과 클라이언트 시크릿을 추가하고 허용되는 커스텀 SSO 원본을 설정합니다. 시크릿은 데이터베이스에 저장되며 저장될 때 효과가 발생하고 반복되지 않습니다.
3. 식별자 제공자를 추가하세요: 표시 이름, OIDC용 발행자, 클라이언트 또는 앱 ID, 그리고 자격 증명 ID를 포함합니다. 비활성 상태로 두고 저장한 후 콜백 URL을 복사하세요.
4. 그 URL을 플랫폼 허용 목록에 정확히 추가하세요. `https://doca.example.com/api/v1/auth/providers/<UUID>/callback`각 제공업체마다 고유한 URL이 있습니다. 임의의 반환 URL은 받아들여지지 않습니다.
5. 등록 정책을 설정하고 제공자를 활성화합니다. 프로필 페이지에서 연결하거나 로그아웃하고 로그인 테스트를 진행합니다. 작동할 때까지 원래의 관리자 방법을 유지합니다.

Google, GitHub, WeChat, QQ의 HTTPS 호스트는 기본적으로 허용됩니다. OIDC 발행자 내의 모든 호스트와, 디스커버리에서 반환되는 권한 부여, 토큰, JWKS URL에서는 각 줄에 하나의 전체 원본으로 custom SSO allowed origins에 나열되어야 합니다. 리디렉션은 금지됩니다. 명시적으로 허용 목록에 포함된 자체 호스팅 제공자는 HTTP를 사용할 수 있으며, OIDC도 이 경우 HTTP 디스커버리와 엔드포인트를 허용합니다. 운영자는 허용 목록과 egress 정책을 함께 관리합니다. 변경 가능한 신뢰할 수 없는 DNS나 임의의 개인 주소를 신뢰하지 마세요.

타입, 발행자, 클라이언트 ID는 불변의 네임스페이스입니다. 새로운 발행자나 애플리케이션은 새로운 제공자가 됩니다. 사용자들이 직접 연결합니다. 기존 ID를 다른 제공자에 사용하지 마세요. 이름, 자격 증명 ID, 활성화 상태는 버전 최적화 잠금을 사용하며 기존 권한 프로세스를 무효화합니다. 제공자를 비활성화하면 그 소스만을 사용했던 사용자들이 접근할 수 없게 됩니다. 먼저 다른 연결을 준비하세요. 관리자가 기존 방법을 대체하고 "사용자에게 로그인 방법 추가 요구"를 설정하지 않는 한 새로운 로그인 방법을 강제로 적용하지 않습니다.

<a id="security-flow"></a>

## 보안 흐름

1. 동일 원산지의 POST는 무작위 상태, 브라우저 자격 증명, 노치, PKCE 검증자가 시작됩니다. 링크를 통해 관리자가 설정한 별도의 보안 검사를 완료합니다. 이 자격 증명은 5분 이내에 한 번만 사용됩니다.
2. 서버는 상태의 해시, 브라우저 자격 증명, 그리고 10분 간의 흐름을 저장합니다. 흐름 쿠키는 HttpOnly이며 SameSite=Lax입니다. 주 쿠키는 HttpOnly이며 SameSite=Strict이고, HTTPS에서는 Secure로 설정됩니다.
3. 콜백은 제공자, 상태, 브라우저 자격 증명을 확인하고, 한 번의 흐름을 처리한 후 신원을 검증합니다. 로그에는 콜백 요청 매개변수, 코드, 토큰, 또는 제공자 오류 본문이 기록되지 않습니다.
4. 브라우저가 리디렉션됩니다. `/#/auth/complete`동일 원본의 POST가 완료되면 엄격한 세션이 복구됩니다. 링크는 여전히 그 세션을 시작한 사용자와 링크여야 하며, 보안 검사 자격증도 여전히 유효해야 합니다.
5. 거래는 흐름을 소비하고 제공자 버전, 고유 식별자 소유권, 등록 정책, 사용자 상태를 확인합니다. Pending 상태에서는 세션을 발행하지 않습니다. Active 상태에서는 Doca 세션만 발행합니다.

제3자 접근 및 갱신 토큰은 저장되지 않습니다. 대상, 당시의 표시 이름, 링크 메타데이터는 저장됩니다. 소스에서 지정된 HTTP(S) 아바타 URL이 표시될 수 있습니다. 서버는 맹목적으로 이를 가져오지 않습니다. 업로드된 아바타는 여전히 사이트 저장소를 사용합니다.

연결을 끊기려면 최근의 인증이 필요하며, 마지막 사용 가능한 방법을 제거할 수 없습니다. 비활성화된 제공자나 자격 증명이 없는 계정은 그 마지막 방법으로 간주되지 않습니다. 비밀번호가 없는 계정은 최근 인증 후 사이트 비밀번호를 설정할 수 있습니다. 이미 비밀번호가 있는 계정은 일반적인 비밀번호 변경 절차를 사용합니다. 공개 사용자 ID와 로그인 정보는 하나의 유일한 문자열입니다. 소스가 적절한 ID를 제공하지 않으면 사용자가 직접 제공해야 합니다. UUID는 이름으로 생성되지 않습니다. 내부 사용자 UUID는 안정적으로 유지됩니다.

<a id="database"></a>

## 데이터베이스

현재 기준은 이러한 신원 구조를 포함합니다. 이는 스스로 사용자를 생성하거나 비밀번호를 재설정하지 않습니다.

- `settings.registration_review` 기존 등록 스위치를 사용하여. `sso_registration` 그리고 `social_registration` 닫혀 있거나 자동으로 처리되거나 승인됩니다. 모두 수정 잠금을 공유합니다.
- `account_flows` 일회성 보안 확인 자격증을 저장합니다. 이 세션은 그 자격증이 아닙니다.
- `auth_providers` 설정, 불변된 네임스페이스, 그리고 버전을 저장합니다. 비밀번호는 저장하지 않습니다. `type` 또한 발행자와 클라이언트 ID는 고유합니다.
- `auth_identities` 지도 `user_id` to `provider_id` 더하기 `subject`그 쌍은 독특해요. `user_id` 더하기 `provider_id` 사용자당 제공업체당 하나의 식별자만 허용됩니다.
- `auth_flows` 10분짜리 단일 사용형 흐름입니다. `stage` 시작되거나 교환되거나 검증된 경우, 완료되면 삭제됩니다. 만료가 되면 새로운 흐름이 시작될 때 정리됩니다.

<a id="http"></a>

## HTTP

접두사는 `/api/v1`글은 원본과 일치해야 합니다.

| 노선 | 누가 | 행동 |
| --- | --- | --- |
| GET /auth/providers | 공공 | 자격 정보(id, name, type)가 있는 제공자만 활성화됩니다. |
| GET /admin/auth | 관리자 | 세 가지 정책, 수정, 제공자, 준비 상태, 콜백 URL. 비밀번호는 없습니다. |
| GET/PUT /admin/accounts/policy | 관리자 | 비밀번호, 전화 및 이메일 로그인, 비밀번호 계정 유형, 그리고 `forcedLoginMethod`모든 활성 사용자가 하나의 사용 가능한 방법을 보유하고 있는지 확인하는 절차를 저장합니다. |
| PUT /admin/auth/policy | 관리자 | `{revision,local,sso,social}` 닫힌, 자동, 또는 승인된 상태로 |
| POST /admin/auth/providers | 관리자 | `{type,name,issuer,client_id,credential_ref,enabled,version:0}` |
| PUT /admin/auth/providers/:id | 관리자 | 동일한 필드, 현재 버전. 불변 필드는 변경될 수 없음 |
| POST /auth/providers/:id/start | `{intent:"login"\|"link"\|"security"\|"replace"}` | 반환 `{url}` 그리고 플로우 쿠키도요. 링크는 최신 인증이 필요합니다. |
| GET /auth/providers/:id/callback | 제공자 | 식별을 확인하고, 그 후 이 출처로 다시 연결됩니다. |
| POST /auth/complete | 인증된 흐름을 소비함 | 활성, 연결된, 또는 대기 중 상태입니다. 활성 문제는 세션을 생성합니다. |
| GET /me/identities | 로그인 완료 | 로컬 로그인, 비밀번호가 있는지, 링크가 있는지, 그리고 사용 가능한지. 주제나 토큰 없음. |
| POST /auth/reauth | 로그인 완료 | `{password}` 이 세션의 최근 확인 시간을 업데이트합니다. |
| POST /auth/password/setup | 최근 확인 | `{password}` 12~128자 이내, 첫 설정에만 적용되며 다른 세션은 무효화됩니다. |
| DELETE /me/identities/:id | 최근 확인 | 탈휴식. 마지막으로 사용 가능한 방법은 보호되어 있습니다. |
| GET /admin/users?status=pending | 관리자 | 필터 및 페이지가 활성, 대기 중, 또는 비활성 상태입니다. |
| GET /admin/registration-reviews | 관리자 | 페이지화된 대기/승인/거부된 리뷰 |
| POST /admin/registration-reviews/:id | 관리자 | `{decision:"approved"\|"rejected",message?}` |
| PATCH /admin/users/:id | 관리자 | 일반 활성/장애 사용자만 해당; 409 응답 대기 중 |

`POST /auth/register` 추가 `status`대기 중인 상태는 사람에게 기다리라고 말하고, 등록을 하지 않습니다.

<a id="tests"></a>

## 테스트

`tests/identity.test.ts` 실제 환경에서 RSA로 서명된 시뮬레이션된 OIDC 응답을 사용함 `openid-client` 패스. 이는 PKCE, 서명, 노스크, 발행자, 쿠키, 반복 및 만료된 콜백, 세션 바인딩, 정책, 승인, 그리고 해제와 관련된 내용을 포함합니다. 소셜 어댑터는 시뮬레이션된 HTTP를 사용합니다. 이는 공급업체 검토나 공개 네트워크 테스트가 아닙니다.

SQLite과 격리된 PostgreSQL 데이터베이스는 모두 현재 스키마에 대한 전체 회귀 분석을 수행합니다. 실제 신원 제공자, HTTPS 프록시, 계정 복구는 각각 별도의 승인이 필요합니다.

<a id="september-2026-module-split"></a>

## 2026년 9월 모듈 분할

정체성은 살아있다. `packages/core/src/modules/identity`프로토콜 어댑터는 실제로 존재합니다. `apps/server/src/adapters/identity-providers.ts`사용자 정의 OAuth 2 인증 코드 및 PKCE 어댑터를 통해 엔드포인트와 안정적인 신원 필드를 설정할 수 있으며, 이는 여전히 HTTP(S) 원본 허용 목록에 속합니다. 이는 OIDC와는 별개의 것입니다. 일반적인 OAuth 토큰은 ID 토큰으로 간주되지 않습니다.

각 소스의 `profile_config` 등록 필드, 그 출처, 그리고 수정이 가능한지 또는 동기화가 가능한지를 명시합니다. 프로필이 불완전한 경우는요. `/auth/complete` 반환 `needs_profile` 전체 세션을 생성하지 않습니다. 필요한 프로필 및 연락처 확인 자격증을 제출한 후에도 등록 또는 승인이 계속됩니다. 사용자 이름의 고유성과 제공자-피험자 결합은 독립적입니다. 중복된 이름은 계정을 합치지 않습니다. 맞춤형 프로토콜 설정은 생성된 후 다른 신원 네임스페이스에 지정될 수 없습니다.
