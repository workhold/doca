<a id="reset-an-administrator-password"></a>

## Сброс пароля администратора

Если администратор все еще имеет проверенный телефон или электронную почту, используйте код на странице входа. В противном случае используйте локальный команду восстановления на машине для развёртывания. Она принимает только существующего администратора. Она не создает нового администратора и не доступна через HTTP:

```zsh
read "DOCA_RESET_ADMIN_LOGIN?Administrator login: "
read -s "DOCA_RESET_ADMIN_PASSWORD?New password (at least 12 characters): "
export DOCA_RESET_ADMIN_LOGIN DOCA_RESET_ADMIN_PASSWORD
pnpm admin:reset-password
unset DOCA_RESET_ADMIN_LOGIN DOCA_RESET_ADMIN_PASSWORD
```

Команда проверяет, что учетная запись является активным администратором, обновляет пароль и отменяет все сессии. PostgreSQL нуждается в `DOCA_DATABASE_URL` В том же окружении. SQLite использует `DOCA_SQLITE_PATH`Не вводите секрет восстановления. `.env`История оболочки или изображение.

## URLы статических ресурсов

Производство HTML всегда происходит через Doca, а API использует тот же источник. `DOCA_ASSET_BASE` только переписывает `/assets/...` URLы в HTML.

Когда это не установлено, контейнер предоставляет JS, CSS и другие файлы сборки. `/assets`Когда это установлено, эти HTML-адреса используют префикс, например `https://cdn.example.com/doca/0.1.10/assets/index-abc.js`Префикс – это HTTP(S) URL без информации о пользователе, запроса или хэша. Для публичного сайта используйте HTTPS, а для надежной внутренней сети – HTTP. `/assets` Остается в контейнере. Фоны и изображения, упомянутые в CSS с корневой путем, все равно приходят в Doca.

Официальная метка, например `v1.2.3` Это позволяет GitHub Actions собрать веб-приложение и создать релиз. Приложение находится в приложении. `doca-web-assets-v1.2.3.tar.gz`. Сохраняйте `assets` директория после развалки, и установите `DOCA_ASSET_BASE` к префиксу HTTP(S), который его содержит. Предрелизующий тег, например `v1.2.3-rc.1` не создает релиз. Пуш-команда `main` Также нет. Не используйте. `github.com/.../releases/download` как `DOCA_ASSET_BASE`Этот URL перенаправляет и не отправляет заголовки кросс-оригината для модулей ES. Удалите нераспакованный файл. `assets` Директория на CDN или объектном хранилище, которая позволяет чтение скриптов из разных источников.

<a id="production-process"></a>

## Процесс производства

```sh
pnpm check
NODE_ENV=production DOCA_ORIGIN=https://docs.example.com pnpm start
```

`check` Задаётся за проверку типов, тестирование и сборку веб-кода. `start` Работает с веб-приложением и API без Vite. Замените имя примера, завершите TLS в обратном прокси, сохраните Host и Origin, и перенаправьте. `DOCA_PORT`.

Сервер не доверяет произвольным. `X-Forwarded-*` Заголовки. Никакой прокси, включая loopback, не считается надежным по умолчанию. Установите `DOCA_TRUST_PROXY` Только к реальным IP-адресам/CIDR-объектам прокси. Ограничения на скорость аутентификации используют IP-адрес соединения, поэтому пользователи, находящиеся за одним прокси, могут использовать общий лимит. Прокси, используемый в продакшене, должен быть настроен как доверенный. Не включайте. `trustProxy` для публичного интернета.

## Журналы работы ИИ

Контейнер производства записывает логи доступа Fastify и ошибки работы AI-задач в stdout:

```sh
docker compose ps
docker compose logs -f --tail=200 doca
```

Чтобы избежать сбоев в ИИ:

```sh
docker compose logs --since=30m doca | grep -E "AI job failed|AI 工作流|模型|图片"
```

Только с Docker — замените `doca` с именем контейнера. В Kubernetes прочитайте stdout podа. `kubectl logs`API сессии браузера возвращает `jobs[].id`, `jobs[].status`и `jobs[].error`Сопоставьте этот ID работы. `AI job failed`Логи записывают скрытый класс ошибок. Они не выводят ключи модели или полный запрос.

Это базовая версия для разработки, которая можно использовать для разработки, но не является готовой версией для производственного использования. Реализовано восстановление учетных данных, и для этого необходимы настроенные шлюзы проверки для восстановления через контакты. Роль провайдера OIDC не доступна; мониторинг целевой инфраструктуры и настройка больших запросов требуют отдельного одобрения. Публично [служба мониторинга](plugin-monitoring.ru.md) реализовано. Существуют внешние адаптеры OIDC и социального входа. Живые учетные данные находятся в [аутентификация](authentication.ru.md)Границы находятся здесь. [архитектура](architecture.ru.md).

<a id="data-protection"></a>

## Защита данных

- Пустые базы данных создаются из текущего целевого объекта; существующие базы данных получают обновления после запуска. Предустановленный путь к SQLite — `data/v1/doca.db`.
- Статические файлы — это только `apps/web/dist`. `.archive`, `data`и `.env` не являются публичными.
- Стартап согласовывает установленную структуру с текущими требованиями. Если проверка или верификация не удается, сервер не будет слушать запросы, и операция обновления отменяется. Сделайте резервную копию и протестируйте восстановление перед внедрением в производство.
- Оффлайнный резервный копирование SQLite останавливает все записи, а затем копирует весь каталог. Онлайнное резервное копирование использует API резервного копирования. Копирование основного файла и пропуск WAL не является резервной копией.
- PostgreSQL использует собственную систему резервного копирования и восстановления. Реципирование после катастрофы — задача оператора.
- SIGINT и SIGTERM завершают работу с HTTP, Vite и базой данных. В продакшене используется управляющий процесс для перезапуска.

## Изменения в базе данных

Читайте и следите за [Контракт на обновление базы данных](database-schema-evolution.ru.md) до модификации основной структуры или сохраненных форматов. Это стандарт текущего проекта: новые создания и обновления используют последнюю версию DDL. `schemaEvolution` Объявляются согласованные добавления, а обычные добавления сохраняют совместимость генерации. Исторические значения полей и семантические/деструктивные изменения требуют конкретного плана сохранения, верификации и восстановления. [AGENTS.md](../AGENTS.md).

Изменения в базе данных требуют изолированного SQLite и регрессии старого схемы PostgreSQL 17/18, включая сохраненные строки, стандартные параметры, повторное/конкурентное запуск и проверка без частичных записей. Принятие релиза также обновляет базу данных, созданную в затронутой старой версии. Матрица CI для PostgreSQL `.github/workflows/database-upgrade.yml`Это дополняет стандартный набор функций. Обновите контракт и примечания к обновлениям с любыми согласованными изменениями в поведении или поддержке.
