# 인터페이스 언어

Doca 0.3.0은 인터페이스 언어 8종을 지원합니다. 언어마다 별도의 메시지 카탈로그가 있으며, 안정적인 영문 키를 공통으로 사용합니다. 프로젝트 및 편집기의 구현 규칙은 [영어 원문](https://github.com/workhold/doca/blob/main/docs/i18n.md)에 있습니다.

<a id="language-codes"></a>

## 언어 코드

| 코드 | 언어 | `html lang` |
| --- | --- | --- |
| `zh` | 중국어 간체 | `zh-CN` |
| `en` | 영어 | `en` |
| `zh-Hant` | 중국어 번체 | `zh-Hant` |
| `ja` | 일본어 | `ja` |
| `fr` | 프랑스어 | `fr` |
| `ko` | 한국어 | `ko` |
| `es` | 스페인어 | `es` |
| `ru` | 러시아어 | `ru` |

사이트의 초기 기본 언어는 중국어 간체이며 관리자가 변경할 수 있습니다. 방문자와 `ui.locale`을 설정하지 않은 사용자는 사이트 기본 언어로 접속합니다. 계정에 저장된 선택이 있으면 해당 언어를 우선합니다.

API에 값을 쓸 때는 표의 표준 코드를 사용합니다. 지역 또는 시스템 언어 태그를 해석할 때 `zh-TW`, `zh-HK`, `zh-MO`, `zh-Hant`는 중국어 번체에 해당합니다. 다른 지원 언어는 기본 언어 태그로 판별합니다. 저장된 값을 인식할 수 없으면 작업 공간은 사이트 기본 언어를 사용합니다.

계정의 언어는 페이지 상태 `ui.locale`에 저장합니다. 웹은 `localStorage`에 `doca.locale`도 보관하며, 모바일은 기기에 언어를 저장합니다. 도우미는 기존 `page_state` 기능으로 계정의 언어를 변경할 수 있습니다.

웹 로그인 화면을 열 때마다 관리자가 지정한 사이트 기본 언어가 먼저 표시됩니다. 로그인 화면의 선택은 현재 방문에 즉시 적용됩니다. 로그인한 뒤에는 계정 설정과 사이트 기본 언어로 작업 공간의 표시 언어를 결정합니다.

<a id="host-catalog"></a>

## 호스트 카탈로그

카탈로그가 있습니다. `packages/i18n`. 영어 카탈로그 `en` 키의 원천입니다. 다른 모든 언어는 정확히 같은 키를 포함해야 합니다.

```ts
t("account.expires", { date })
// en: Expires {date}
// zh: 到期时间：{date}
```

- 키는 점이 있는 소문자 영어로, 지역별로 그룹화되어 있습니다. 예를 들어 `nav.trash` 그리고 `settings.language`.
- 플레이스홀더는 `{name}`문장을 나누지 말고 조각들을 합치지 마세요.
- 복수형 사용 `files.count.one` 그리고 `files.count.other`통화는 아직 진행 중입니다. `t("files.count", { count })`영어는 사용된다 `one` 때에 `count === 1` 그리고 `other` 그렇지 않으면, 중국어에서는 같은 문장을 두 경우 모두에 사용할 수 있습니다.
- 누락된 번역은 영어를 사용하고, 그 다음에 키 자체를 사용합니다.
- 선택자에 각 언어의 고유 이름을 사용하세요. 원본 라벨은... `localeNames`.
- 날짜 및 정렬 사용 `Intl` 활성 언어 태그를 위해.
- 문서 제목, 본문 텍스트, 댓글, 이메일, 파일 이름, 사용자 입력은 번역되지 않습니다.

웹 앱은 사용합니다 `useI18n()` for `locale`, `t`, 그리고 `setLocale`Ant Design과 Ant Design X도 그렇습니다. `locale`데스크톱과 모바일에서는 호스트 카탈로그를 사용합니다. 브라우저 확장 프로그램은 해당 브라우저의 언어를 기억합니다. 이중 언어 플러그인을 사용하는 기여물은 6개의 새로운 언어에서 영어 필드를 사용합니다.

코드가 없는 사용자가 볼 수 있는 서버 오류는 여전히 중국어 문장입니다. 새로운 검증 오류는 안정적인 코드를 사용합니다. `invalid_locale`그리고 인터페이스가 그 내용을 번역합니다. 이 버전에서는 기존 API 오류들이 모두 변환되지 않습니다.

새로운 AI 이미지 생성, 모델 연결, 그리고 작업자 오류는 명시적인 표현 방식을 사용하며, 기존의 오류 텍스트 필드에 시리얼화되어 저장됩니다.

```ts
{ type: "system_error", version: 1, code: "image_edit_failed", data: { status: 422 } }
```

새로 생성된, 명시적으로 코딩된 시스템 오류만이 이 형식을 사용합니다. 역사적 오류 텍스트, 메시지, 도구 결과, 논리, 저장된 프롬프트 컨텍스트는 그대로 읽어야 하며, 스캔하거나 번역하거나 변환하거나 이동해서는 안 됩니다. 태그가 없는 오류는 변경되지 않습니다. 웹과 모바일은 동일합니다. `systemErrorMessage` 독자 `@doca/i18n`태그된 작업 오류가 사용됨 `useI18n().t`새로운 HTTP 오류는 동일한 제공자가 선택한 로케일을 사용합니다. 알 수 없는 코드는 카탈로그에 등재된 일반적인 오류를 표시하며, 잘못된 또는 지원되지 않는 데이터는 그대로 유지됩니다.

`AppError.message` 모델에 접근하는 오류 시리얼라이제이션은 변경되지 않습니다. 프레젠테이션 메타데이터는 오류 객체 외부의 WeakMap에 저장됩니다. 이미지 실패 체크포인트는 별도의 구조화된 이유를 포함하므로, 이후 작업 실패 시 표준 도구 피드백을 변경하지 않고도 이를 표시할 수 있습니다. 인터페이스 언어는 시스템 프롬프트, 도구 정의, 또는 재생된 역사에 결코 추가되지 않으며, 사용자가 언어를 전환할 때 캐시된 모델 접두사를 보존합니다.

이것은 기존의 텍스트 파일과 새로운 암호화된 오류에 대한 합의된 읽기 정책입니다. 역사적 데이터나 데이터베이스 스키마 마이그레이션은 없습니다. 롤백 과정에서는 새로운 엔벨로프 기록을 중단해야 하며, 엔벨로프 읽기 기능과 모든 저장된 데이터는 유지되어야 합니다.

## 저장된 시스템 상태

데이터베이스, 작업 체크포인트, 이벤트 스트림, API 응답은 안정적인 영어 코드와 구조화된 매개변수를 저장합니다. 어떤 언어로 된 표시 문장도 저장하지 않습니다. 웹 및 모바일 앱은 이 코드를 현재 카탈로그에 맞는 제목, 설명, 단계 이름으로 변환합니다.

```ts
{ code: "folder_available", data: { name: "Research" } }
t("ai.progress.event.folderAvailable", { name: event.data.name })
```

상태로 저장된 단계, 이벤트, 승인 및 오류 원인은 이 규칙을 따릅니다. 예를 들어 코드를 비교해 보세요. `phase === "completed"`결과를 비교하지 마세요. `t(...)` 중국어 또는 영어로 된 라벨이면 됩니다. 사용자 입력, 모델 답변, 문서 제목, 파일 이름, 웹 출처는 그대로 유지됩니다. 자연스러운 내용을 코드로 변환하지 마세요.

## 편집기 하위 패키지

편집기 하위 패키지는 자체 인터페이스 사본을 유지합니다. Doca의 카탈로그를 가져오지도 않고 Doca 페이지 상태를 읽지도 않습니다.

진행자가 통과합니다:

```tsx
<RichTextEditor locale={locale} />
```

`locale` 문자열입니다. 설치된 편집기들은 표에 있는 8가지 코드를 인식합니다. 인식되지 않는 패키지 로케일은 영어로 전환됩니다.

1. 선택적 추가 `locale?: string`제외될 경우 표시 `zh`현재 중국어 인터페이스와 일치합니다.
2. 키는 안정적인 영어 식별자입니다. `toolbar.bold` 그리고 `find.replaceAll`.
3. 각 지원되는 언어에 대한 동일한 키의 전체 카탈로그를 제공하세요.
4. 플레이스홀더는 `{name}`카운트는 사용됩니다. `key.one` 그리고 `key.other`선정된 사람 `count`.
5. 변경하기 `locale` 업데이트 버튼, 메뉴, 플레이스홀더, 그리고 힌트를 추가합니다. 문서, Y.Doc, 공동 작업 어댑터, 또는 플러그인 목록을 다시 생성하지 않습니다.
6. 선택적 `messages?: Record<string, string>` 개인 키를 우회할 수 있습니다. 누락된 키는 여전히 내장 번역을 사용합니다.
7. 사용자가 문서에 입력한 텍스트, 공식, 셀 값은 번역되지 않습니다.

설치된 패키지의 유형이 포함된 후 `locale`진행자는 현재 상황을 전달합니다. `locale` 산악 지역에서. 두지 마세요. `locale` 문서, Y.Doc, 공동 작업 어댑터 또는 플러그인 목록을 다시 생성하는 의존성에서.

## 언어 추가하기

1. 코드를 추가하세요. `locales`, 그리고 `html lang` 값.
2. 정확한 영어 키를 가진 호스트 카탈로그를 추가하세요.
3. 언어의 자체 이름을 추가하세요, 예를 들어 `locale.ja`.
4. 웹 앱에 맞는 Ant Design 지역화 설정을 추가하세요.
5. 모든 편집기 하위 패키지에 동일한 언어 카탈로그를 추가하세요.
6. `ui.locale` 새 코드를 받아들입니다. 왜냐하면 유효성 검사가 동일하게 읽기 때문입니다. `locales` 리스트.
