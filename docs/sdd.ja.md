# 仕様主導型開発

[中文](sdd.zh-CN.md)

このワークフローは、Doca全体の新しい作業に適用されます。GitHub Spec Kit 1.0.4には、チェックインされたCodexのスキル、スクリプト、テンプレートが含まれています。インストールやアップグレードの詳細はそこにあります。 [.specify/README.md](../.specify/README.md). [AGENTS.md](../AGENTS.md)、その [憲法](../.specify/memory/constitution.md) そして、既存の技術契約がその使用を規定している。まずは… [モジュールインデックス](sdd-module-index.ja.md) 現在のソース、契約、再利用可能なチェックを特定する。

<a id="choose-the-level"></a>

## レベルを選択してください

| レベル | 意味的影響 | 実施前の最小記録 |
| --- | --- | --- |
| `full` | データベースまたは保存されたフォーマット；認証/承認；共同編集；公開されたSDK/API契約；アーキテクチャ、認証情報、またはデプロイの境界 | `spec.md`, `plan.md`, `tasks.md`, `validation.md` 1つの機能ディレクトリ内 |
| `standard` | 既存の境界内でのその他の特徴や観察可能な行動の変化 | 一つ `spec.md` 範囲、受け入れ性、設計、タスク、および検証 |
| `light` | 制限された修正、コピー、スタイル、テスト、または文書については、上記のいずれの影響もありません | PR問題、最終的な行動、検証、影響の説明 |

行動を判断し、行数ではない。1行の承認変更は完全なものだ。指定された動作を復元する修正は、契約を変更しないか、リスクの高い境界を変更しない限り、軽微なものかもしれない。プロセス上の変更は、採用を記録するために完全なものを選ぶこともある。 [このインストール](../specs/001-sdd-adoption/spec.md) そうです。タスクを拡張する前にレベルを上げ、範囲を更新してください。PRで分類理由を明記してください。自動チェックでは正しいセマンティックレベルを確定することはできません。

<a id="work-on-a-change"></a>

## 変更作業

1. モジュールインデックス、実際のソース/パッケージのエクスポート内容、および適用可能なスキルを確認する。現在のバージョンを記録し、実装された動作と提案内容を区別する。既存のユーザー認可はレビューチェックポイントを超えて継続する。
2. 完全な/標準的な作業を行うためには、作成する `specs/<number>-<short-name>/spec.md` 実装前に。次に使用されていない3桁の数字を使用し、識別子は一意です。Gitブランチは独立しており、通常は使用されます。 `codex/`記録 `Level`, `Status`, `Created`, `Decision`, `Scope` そして安定した `AC-001` 受け入れID。 [プロジェクトテンプレート](../.specify/templates/overrides/spec-template.md) セクションを提供します。
3. 完全な作業には、計画、受け入れIDを参照するチェックボックスタスク、そして初期段階で保留中の検証記録が含まれます。 [計画](../.specify/templates/overrides/plan-template.md), [タスク](../.specify/templates/overrides/tasks-template.md) そして [検証](../.specify/templates/overrides/validation-template.md) テンプレートが利用可能です。標準的な作業が続きます。 `Design`, `Tasks` そして `Validation` 仕様書において、範囲がそれを要求する場合にのみ、別途の研究、データモデル、契約を追加する。
4. 互動性実装前に、AGENTS.mdで要求される具体的な合意事項を個別に取得する：影響を受けるバージョン/フォーマット、拒否/保持/変換/移行の動作、保存、検証、復元。仕様の承認状態はそのようなものではない。データベースの変更は以下に従う。 [アップグレード契約](database-schema-evolution.ja.md).
5. スコープ付きタスクを実装し、同じPR内で影響を受ける現在の契約を更新する。受け入れIDをチェックや観察事項にマッピングする。実際の結果、スキップされたケース、バージョン、制限事項を記録する。出力内容は既存のものに従う。 [アーティファクトルール](documentation.ja.md#assets-and-updates).
6. 実行する `pnpm sdd:check` および関連するモジュールのチェック。使用する。 [PRテンプレート](../.github/PULL_REQUEST_TEMPLATE.md)宣言されたレベルと1つの主要仕様パスを記録する。その他の作業項目は主要仕様からリンクされることができる。高リスクな境界、契約、および個別の互換性決定を明確に確認する。

<a id="codex-skills"></a>

## コーデックススキル

チェックイン済み `.agents/skills/speckit-*` スキルは、Codexセッションがプロジェクトのスキルを発見した時に利用可能になります。現在のセッションがインストールより前のものである場合は、新しいプロジェクトチャットを開きます。スキルはターミナルではなく、エージェントチャットで呼び出します。完全な作業には、この手順を使用できます。

```text
$speckit-specify Describe the requested behavior and affected users
$speckit-plan State the actual Doca modules, packages and constraints
$speckit-tasks
$speckit-analyze
$speckit-implement
$speckit-converge
```

憲法はすでに確立されている。明確化とチェックリストのスキルは、必要に応じて選択可能である。標準的/軽度の作業では、全工程フローコマンドを実行することなく、階層化された記録を直接使用することができる。アップストリームの汎用ワークフローは、レビューゲートとともにインストールされている。上記の順序は、Docaの適切なワークフローと既存のユーザー認可に基づいている。汎用プロンプトは、互換性の判断やメッセージの送信、公開、デプロイの認可を行うものではない。

必要なときに既存の機能を明示的に選択する：

```sh
SPECIFY_FEATURE_DIRECTORY=specs/001-sdd-adoption bash .specify/scripts/bash/check-prerequisites.sh --json --require-spec --require-tasks --include-tasks
bash .specify/scripts/bash/resolve-template.sh spec-template
```

機能ポインタが `.specify/feature.json` checkout-local状態は無視されます。それをブランチやプロジェクトのベースラインとして共有しないでください。アップストリームのスクリプト/テンプレートは変更されません。カスタマイズしてください。 `templates/overrides/`チェッカーがバンドルされたアップストリームのハッシュを確認する。プロジェクトのテンプレートはこれに対して作成されている。 `specs/<number>-<name>/`別の場所を意図して使用する場合は、相対的なリンクを調整する。

<a id="status-and-evidence"></a>

## 状況と証拠

| 状況 | 意味 |
| --- | --- |
| `draft` | 範囲や決定はまだ準備中です |
| `accepted` | 範囲が合意されました。具体的な互換性承認は別途記録されます。 |
| `implemented` | スコープ内のコード/タスクが完了したが、検証はまだ進行中または部分的な状態である |
| `verified` | すべての受け入れIDは、指定された検証範囲内で結果が記録されています。 |
| `superseded` | 歴史的記録；その代替品を指摘する |

検証済みのタスク、解決されていない受け入れ、または保留中/失敗した結果にはマークしないこと。歴史的に検証済みの仕様は現在のコードを再検証するものではない。現在の契約は現在の動作の源泉であり、代替デザインやリンクの置換にはラベルを付ける。既存の仕様、契約、受け入れ記録はそのパスと日付を保持する。モジュールインデックスは入力ポイントであり、後追いの受け入れではない。

<a id="checks-and-prs"></a>

## チェックとPRs

`pnpm sdd:check` 番号付きスペックディレクトリ、レベル/ステータス、必要なレコード、受け入れ/タスクの追跡可能性、完了した検証、インストールされたアップストリームハッシュを検証する。 `pnpm test:sdd` 正のケースと負のケースをカバーし、孤立した上流スクリプト/テンプレートの使用も対応する。 `pnpm docs:check` 実際の文書やモジュールインデックスリンク、またインストールされたスキルやプロジェクトテンプレートも含めて検証します。

PR機関は、実際の値を持つこれらの独立した行を宣言する。

```text
SDD-Level: full
SDD-Spec: specs/001-sdd-adoption/spec.md
```

光の変化を利用する `SDD-Level: light` そして `SDD-Spec: none`すべてのPRが満たされる `Problem`, `Behavior`, `Impacts` そして `Verification` セクション。SDD GitHubワークフローは、開かれた、編集された、同期されたリクエストのPRメタデータをチェックし、mainディレクトリ上のリポジトリ記録も確認します。これは実行されます。 `pull_request`読み取り専用の権限であり、秘密情報はありません。宣言されたリスク、人間の同意、またはテスト結果が真実かどうかはチェックされず、構造や参照のみが確認されます。メンテナがこれらの主張をレビューします。ワークフローではブランチ保護の設定は行われず、マージ時にそれを要求するのはリポジトリの設定です。

<a id="evaluate-the-first-changes"></a>

## 最初の変化を評価する

次の3〜5回の実際の変更については、検証や軽微なPRに簡潔な観察事項を追加してください。具体的には、調査の労力、レビューで見逃された要件、実装後の再作業、記録管理のコストなどです。測定可能な場合は期間を記載し、そうでない場合は「測定されていない」と記載してください。可能な限り同様の変更を比較し、観察された負担に応じてテンプレートの深さを調整してください。Spec Kitのインストール自体は、不具合率の改善や納期の短縮には寄与しません。
