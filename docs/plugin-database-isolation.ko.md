# 공유 플러그인 비즈니스 데이터베이스

[简体中文](plugin-database-isolation.zh-CN.md)

모든 플러그인은 코어 데이터베이스와는 별개의 호스트 관리형 비즈니스 데이터베이스를 공유합니다. PostgreSQL은 배포를 위해 하나의 데이터베이스/계정 설정이 필요하며, 호스트는 각 플러그인의 스키마와 테이블을 자동으로 생성합니다. SQLite은 설정이 필요 없으며 자동으로 공유 파일을 생성합니다. 플러그인들은 변경되지 않은 상태로 계속 사용됩니다. `storage.sql.v1` SDK, 스키마 버전 1 및 `dataVersion`연결 문자열, 드라이버 또는 파일 시스템 경로가 없는 상태로.

<a id="configuration-and-isolation"></a>

## 구성 및 격리

SQLite는 기본적으로 `<DOCA_SQLITE_PATH>.plugins.db`. `DOCA_PLUGIN_DATABASE_PATH` 선택적으로 다른 영구적인 로컬 파일을 선택합니다. 이 파일의 모드는 0600입니다. 각 물리 테이블에는 `plugin_<SHA256(plugin ID), first 56 hex>__` 전제 조건: SDK 테이블 이름은 변경되지 않습니다. 인메모리 호스트는 각 호스트 연결에 대해 하나의 공유 인메모리 플러그인 데이터베이스를 사용합니다. 공유 파일과 핵심 데이터베이스, 개인 파일 저장소를 함께 백업하세요. SQLite는 단일 호스트 옵션으로 유지됩니다.

PostgreSQL은 하나의 운영자 설정된 비즈니스 데이터베이스와 로그인 계정을 사용합니다. 계정 권한은 배포 운영자가 선택합니다; 일반 계정, 슈퍼유저, 관리자 속성 또는 멤버십을 가진 역할, 그리고 코어에 사용되는 동일한 계정이 허용됩니다. 이 계정은 효과적이어야 합니다. `CONNECT` 그리고 `CREATE` 그 비즈니스 데이터베이스에 플러그인 스키마를 생성할 수 있는 특권이 있다. `USAGE` 그리고 `CREATE` 그것에 `public` 공유 마커를 초기화하는 스키마. 데이터베이스 수준 `CREATE` 스키마 수준을 부여하지 않음 `CREATE`; PostgreSQL 17/18은 기본적으로 일반 비소유자 역할에 후자 권한을 부여하지 않습니다. 참조하세요. [PostgreSQL 스키마 권한](https://www.postgresql.org/docs/18/ddl-schemas.html#DDL-SCHEMAS-PRIV)SQL 플러그인을 활성화하기 전에 이를 한 번 설정하세요:

```dotenv
DOCA_PLUGIN_DATABASE_URL=postgresql://doca_plugins:replace-me@postgres:5432/doca_plugins
DOCA_PLUGIN_DATABASE_POOL_MAX=4
```

새로운 배포의 경우, 다음과 같은 선택적 전용 계정 예시가 스토어를 설정합니다. `psql` (비밀번호를 변경합니다). 적절한 권한을 가진 기존 계정도 직접 설정할 수 있습니다:

```sql
CREATE ROLE doca_plugins LOGIN PASSWORD 'replace-me';
CREATE DATABASE doca_plugins;
REVOKE ALL ON DATABASE doca_plugins FROM PUBLIC;
GRANT CONNECT, CREATE ON DATABASE doca_plugins TO doca_plugins;
\connect doca_plugins
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO doca_plugins;
```

기존 배포에 대해서는 그 역할, 데이터베이스, 데이터를 유지합니다. 초기화 보고서가 누락된 경우 `USAGE`/`CREATE` 에 `public`데이터베이스 소유자로서 연결하세요. **플러그인 비즈니스 데이터베이스** 그리고 실행하세요 `GRANT USAGE, CREATE ON SCHEMA public TO doca_plugins;`설정된 역할 이름을 사용하여, 플러그인 스키마를 생성할 때 데이터베이스가 없다는 오류가 발생할 경우 `CREATE`, 승인 `CREATE ON DATABASE doca_plugins TO doca_plugins` 소유자로서, 권한을 수정한 후 다시 시작을 시도하세요. 제거, 재설정 또는 데이터 변환은 필요하지 않습니다. 호스트는 자동으로 권한을 부여하지 않습니다. 이러한 권한 부여는 전용 플러그인 비즈니스 데이터베이스에만 적용됩니다. 기존의 공유 마커는 필요하지 않습니다. `CREATE` 에 `public` 다시. 연결 문자열/비밀번호와 원시 SQL 오류는 플러그인 응답에서 숨겨져 있으며, 이러한 수정된 호스트 설정 진단 정보는 명확하게 보고됩니다.

호스트가 자동으로 생성합니다 `plugin_<SHA256(plugin ID), first 56 hex>` 첫 번째 선언에 대한 스키마. 모든 플러그인은 호스트 인스턴스당 하나의 연결 풀을 공유합니다. `DOCA_PLUGIN_DATABASE_POOL_MAX` 1에서 20까지의 정수이며, 기본값은 4입니다. 이 풀과 코어/AI/웹호크 풀, 인스턴스 수를 서버 연결 예산에 포함하세요. 모든 복제본은 동일한 공유 비즈니스 데이터베이스를 사용해야 합니다. 다른 플러그인을 추가할 때는 데이터베이스, 역할 또는 연결 항목이 필요하지 않습니다. SQL 저장소가 없는 플러그인은 이 URL이 필요하지 않습니다.

설정된 비즈니스 데이터베이스는 URL이 동일하더라도 코어와는 별개여야 합니다. 호스트는 상승된 역할 속성, 역할 참여 여부 또는 코어 테이블 권한을 검사하지 않으며 데이터베이스 계정 권한도 변경하지 않습니다. 운영자는 PostgreSQL 보조 권한을 사용하는 계정을 제한할지 여부를 결정합니다. 호스트는 데이터베이스/역할을 생성하지 않으며 코어 스토리지로 전환되지도 않습니다. PostgreSQL 트랜잭션은 트랜잭션 로컬 스키마를 설정하며, 풀링된 연결은 다른 플러그인의 범위를 유지하지 않습니다. 삭제 제거는 제거된 플러그인의 선언된 테이블과 설치 마커만 삭제하고, 다른 플러그인 스키마/데이터 및 공유 스토어는 그대로 유지됩니다.

운영자 관리형 계정 정책은 2026-10-16에 승인되었습니다. 이는 0.1.26–0.1.29 버전에서 도입된 계정 권한 거부 기능을 대체합니다. 기존의 형식-3 선언, 마커, 세대 및 데이터 버전은 변환 없이 그대로 유지되며, 업그레이드로 인해 데이터나 권한이 변경되지 않습니다. 호스트를 되돌리면 기존의 계정 제한이 복구되어 관리자 로그인이 다시 거부될 수 있습니다. 되돌리기를 계획할 때 기존 데이터베이스, 데이터 및 설정을 그대로 유지해야 합니다. 아래의 형식-2 업그레이드 절차는 변경되지 않습니다.

이는 호스트가 소유한 SDK 서비스를 통한 격리입니다. 플러그인은 신뢰할 수 있는 Node.js 프로세스에서 실행되며, 비즈니스 역할 공유는 프로세스나 운영체제 샌드박스가 아닙니다.

핵심은 사용자, 문서, 권한, 보안 감사, 원시 AI 사용량, 플러그인 레지스트리/아카이브 참조, 네임스페이스 기록, 암호화된 자격 증명, 개인 객체 참조 및 내구성 객체 쓰레기 의도를 보존합니다. 파일 및 자격 증명 소유권/권한, 핵심 DDL 및 `schema_baseline.id` 변하지 않음.

## 정확한 저장 형식 및 수명 주기

호스트 선언은 형식 3을 사용합니다.`storageVersion: 3`, 처음에 `schema: null`). 공유된 루트 마커는 `_doca_shared_plugin_database` 형식 3으로. 각 플러그인의 `_doca_plugin_store` 마커는 정확한 ID, 생성 번호, 데이터 버전 및 표준 스키마를 기록합니다. 마커 검증 및 범위 기반 내부 검사 기능을 통해 관련 없는 데이터가 도입되는 것을 방지합니다. 공유 파일, 네임스페이스 또는 이전에 선언된 테이블이 누락된 경우 거부되며, 이는 결코 조용히 재생성되지 않습니다. URL/파일을 변경해도 데이터가 이동되지 않으며, 스키마가 기록된 후에는 빈 대체물도 거부됩니다.

첫 번째 선언은 코어 네임스페이스를 잠그고, 플러그인 네임스페이스, 비즈니스 테이블 및 마커를 하나의 비즈니스 트랜잭션에서 생성한 후, 코어 트랜잭션에 선언을 기록합니다. 중단된 코어 커밋 후 재시도 시 정확한 커밋된 비즈니스 마커와 실제 구조만을 허용합니다. 다른 스키마 정의, 타입/기본값/유효성, 주요/유일한 제약 조건 및 예상치 못한 테이블은 거부됩니다. 사용자 트랜잭션 콜백은 한 번 실행되며 완료 후 만료됩니다. 비즈니스 커밋 후 코어 커밋 실패는 불확실한 결과로 비즈니스 익명성/재읽기가 필요하며, 콜백은 재생되지 않습니다.

코어 네임스페이스 락은 비즈니스 커밋을 통해 유지되므로, 제거 작업은 허가된 쓰기 작업을 기다립니다. 비즈니스 제거 hook이 먼저 실행됩니다. 성공할 경우, 코어 레지스트리 트랜잭션이 생성 과정을 차단하고 설치 선택 및 자격 정보를 지우며, 개인 객체 정리 작업을 큐에 넣습니다. 사용자 파일, 권한, 영수증 및 릴리스 아카이브는 그대로 유지됩니다. hook 실패 시 설치는 유지되며, 외부 hook의 효과는 되돌릴 수 없습니다.

비즈니스 정리 작업은 보존된 선언을 기반으로 한 영구적인 의도를 사용하여 핵심 커밋을 따릅니다. 스타트업 단계에서는 정기적인 정리 작업, 제거 및 재설치 시도가 반복됩니다. 정리 작업에서는 선언된 테이블을 삭제하기 전에 삭제된 객체와 마커를 확인합니다. 알 수 없는 테이블이나 불일치하는 마커는 부분 삭제 없이 정리 작업을 거부합니다. PostgreSQL은 idempotent 재시도를 위해 빈 네임스페이스를 남겨두고, SQLite은 공유 파일을 남깁니다. 재설치 시에는 정리 작업을 기다린 후 객체 번호를 증가시키고 빈 비즈니스 테이블을 생성합니다. 분산된 원자적 커밋이나 자동 클러스터 작업은 제공되지 않으며, 각 인스턴스를 다시 시작해야 합니다.

## 0.1.25에서 승인된 업그레이드

소유자가 승인했습니다. **이전 버전에서 일반적인 제거 후 재설치를 진행하며 플러그인 데이터는 이동되지 않습니다.**0.1.25 버전은 플러그인별 파일/데이터베이스를 사용하며 형식 2를 지원합니다. 상태 없는 플러그인을 포함한 형식-2 설치는 코어 조정 작업 전에 거부됩니다. 구버전입니다. `DOCA_PLUGIN_DATABASE_DIR` 그리고 `DOCA_PLUGIN_DATABASES_JSON` 설정은 명시적으로 거부됩니다. 오래된 저장소 리더, 자동 데이터 변환, 듀얼 쓰기 또는 오래된 데이터베이스/파일의 자동 삭제 기능은 없습니다.

1. 원본 핵심 데이터베이스, 모든 오래된 플러그인 데이터베이스/파일, 개인 파일 저장소, 설정 및 원본 자격 증명 마스터 키를 백업하세요.
2. 이전 호스트에서는 일반적으로 모든 외부 비즈니스 플러그인을 제거하고 잔여 정리 작업을 처리했습니다. 이는 의도적으로 그들의 개인 비즈니스 기록, 암호화된 자격 증명 및 개인 객체를 삭제하는 것을 의미합니다. 다시 설치한 후 플러그인을 재설정하고 외부 계정의 재설정이 필요합니다. 핵심 데이터와 일반 사용자 파일은 그대로 유지됩니다.
3. 모든 호스트 인스턴스를 중단하세요. 기존의 플러그인별 설정을 삭제하세요. PostgreSQL의 경우, 빈 공유 비즈니스 데이터베이스와 운영자가 선택한 로그인을 프로비저닝/구성하세요; SQLite의 경우, 자동 공유 파일을 사용하거나 경로를 설정하세요. 이전의 저장소/백업은 복구 증거로 보관하세요.
4. 새로운 호스트를 기존의 핵심 데이터베이스, 일반 파일 및 원본 마스터 키에 배포합니다. 플러그인을 다시 설치하고 모든 인스턴스를 재시작합니다. 호스트는 빈 개인 비즈니스 데이터부터 시작하여 각 플러그인을 공유 비즈니스 데이터베이스에 자동으로 연결합니다.

제거가 실패하면 이전 호스트에서 해결하세요. 시작 시 남아있는 설치가 거부되면 그 호스트로 돌아가 제거를 완료하세요; 핵심 데이터베이스를 절대 초기화하지 마세요. 이미 제거된 네임스페이스 기록은 남아 있으며, 명시적으로 재설치하면 그 생성 번호가 증가합니다. 0.1.25 이전의 네임스페이스 기록 처리 방식은 그대로 유지되며, 오래된 비즈니스 데이터는 읽지 않습니다. 남아있는 동일 위치의 데이터도 포함됩니다. `plugin_<56 hex>` 더 오래된 버전의 테이블들은 여전히 검토가 필요하며 자동으로 삭제되지 않습니다.

새로운 데이터가 저장되기 전에, 설치 전 상태로 복구하려면 원본 코어/플러그인/파일 백업과 기존 코드/설정도 함께 필요합니다. 취소된 외부 권한은 다시 연결해야 할 수 있습니다. 새로운 데이터가 저장된 후에는 새로운 데이터베이스/파일을 보존하고 별도의 복구 계획을 합의해야 합니다; 기존 백업을 복원하면 이후 데이터가 삭제될 수 있습니다. 기존 호스트는 형식 3을 읽을 수 없습니다. 기존 및 새로운 호스트의 혼합 운영은 지원되지 않습니다.
