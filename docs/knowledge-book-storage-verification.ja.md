<a id="automatic-startup-upgrade-in-0124"></a>

## 0.1.24で自動起動アップグレードが可能

すべての古いホストを停止し、SQL、プライベートストレージ、設定をバックアップしてください。0.1.22世代のリリースから0.1.24を開始します。 `doca-2026-10-09-history-storage-v1` 全体のスキーマを現在のDDLと自動的に比較する。計画が審査を通過すると、スキーマロックトランザクションが宣言された追加内容を調整し、目標となる生成結果を記録する。古いSQLで生成された結果、実行、人間によるタスクを含む、すべてのビジネス行やパブリケーションポインタは変更されない。既存の0.1.23のオブジェクトストレージデータはバイト単位で正確に保持される。手動のブックコマンドは不要であり、別途のクリーニングや自動変換、レガシーランタイムリーダーも追加されない。残存する古いブック結果は、利用可能になるまで手動で処理する必要がある場合がある。

すべての構造/生成の変更は、エラーが発生した場合に元に戻ります。繰り返し/同時起動時もすべての行が保持されます。不明な、以前の、または中断された生成は、データが変更されることなく停止します。関連性のない不明なテーブルについては、依然として確認が必要です。すべてのデータを保持し、アップグレード後の書き込みは、いかなるバックアップ復元時でも行います。すべてのホストとウェブインスタンスを一緒に更新します。

以下の既存のメンテナンスコマンドは、古い生成された結果を利用可能なネイティブ形式で保持する必要がある場合はオプションのままです。初回起動前にアップグレードを実行してください。スキーマの一致によりソース生成が変更されます。以下の歴史的検証により、残りのSQL JSONの自動適応ではなく、オプションの変換が行われることが確認されます。

自動整列の証拠：SQLite/PostgreSQL 17/18で実際にリリースされた0.1.22のファイチャントは、114のビジネステーブルの各行と20のSQLボディをすべて保持した。新しいネイティブオブジェクトは、繰り返し/同時起動後でも読み取り可能であった。PostgreSQL 17/18は、ロールバックや厳格なレガシーボディの拒否を含む91の回帰ケースをすべて通過した。詳細は [検証](verification/book-schema-startup-2026-10-13/verification.json).

<a id="maintenance-commands"></a>

## メンテナンスコマンド

これらの変更内容と既存のデプロイ環境を含む新しいホストビルドを使用してください。リリース済みです。 `smartdoca/doca:0.1.22` 変換ソースであり、新しいコマンドは含まれていません。すべてのホストを停止し、SQL（SQLite WALを含む）、プライベートオブジェクト、設定をバックアップします。元のマスターキーを保持し、IDとバックエンド設定を保存します。すべてのホストとWebビルドを一緒に更新します。

このコマンドは、初期化なしで既存のデータベースを開きます。デフォルトモードでは完全な読み取り専用の事前処理が行われます。適用には… `--apply --hosts-stopped` 新しいリカバリマニフェストパスもあります。マニフェストはモード0600を使用し、ボディミラーなしで元のフットプリント、オーナーID、サイズ、ハッシュを保持します。

```sh
pnpm knowledge-books:storage upgrade
pnpm knowledge-books:storage upgrade --apply --hosts-stopped --manifest /secure/book-upgrade.json
```

ただ、 `doca-2026-10-09-history-storage-v1` 受け入れられます。以前の世代は、まず正確なサポートされた歴史変換を完了しなければなりません。書籍タスクの実行、不明なデータ形式、破損したデータ、およびレビューが必要な構造的違いのブロック変換を、部分的な書き込みなしで行います。不明なジョブをキャンセルしたり、歴史的フィールドを作成したり、SQLをクリアしたりするのではなく、特定の条件を解決します。

中断後、通常の起動時には進捗の生成が受け付けられない。同じマニフェストパスで同じコマンドを再実行する。変換されたバイト数は依然としてそのマニフェストと一致しなければならず、マニフェストを変更しても変更されたデータを無視することはできない。完了後、起動時には何も受け付けられない。 `doca-2026-10-12-book-payload-storage-v1`独立した心拍数により、起動後の未処理の通知が調整されます。完了した歴史的タスクは再代入されません。歴史的な出力やエラーは保持されます。

現在のロールバックは空でないものを拒否する `knowledge_book_batch_checkpoints` 変更前：彼らの参照には、別途承認された保存/復元計画が必要です。チェックポイントを削除したり、生成/構造チェックを回避したりしないでください。参照してください。 [チェックポイントの保持と復元](knowledge-book-generation-performance.ja.md#deployment-retention-and-recovery)以下の歴史的な往復データはバッチチェックポイントよりも前のものであり、任意の現在値から0.1.22へのダウングレードを検証していません。

適切なロールバックのためにすべてのホストを停止し、新しいバックアップおよび復元マニフェストを保持する。すべてのオブジェクトを事前読み取りし、元のバイトを確認する。ロールバックではアップグレード後の書き込みも復元し、クラウドオブジェクトや復元資料も保持する。

```sh
pnpm knowledge-books:storage rollback
pnpm knowledge-books:storage rollback --apply --hosts-stopped --manifest /secure/book-rollback.json
```

中断されたロールバックが元のマニフェストに戻ります。すべてのJSONが復元され、検証された後、4つのストレージ拡張テーブルのみが削除され、レビューされたフットプリント/旧世代のデータが記録されます。目標は前の0.1.22ホストです。任意の古い文書履歴のロールバックが行われる前に、完全なブックロールバックが行われます。解放されたSQLiteページは自動的にファイルを縮小することはなく、自動的なVACUUM処理も行われません。

実際のソース画像は `smartdoca/doca:0.1.22`、画像ID `sha256:a5316eb01bf25b0d89801139de85d34a35528be376699c4981ab8a09fd14f04c`その実際の実行者は、公開されたものの、失敗したり、出版待ちの合成タスクを生成した。生産データベースやユーザーディスクリプトはアクセスされていない。

各SQLite/PostgreSQL 17/PostgreSQL 18のファイルには、20個の非空の元データが含まれていました。明示的なアップグレード、2回の通常の起動、および明示的なロールバックにより、全20個の元JSONバイトシーケンスとハッシュが確認され、状態、エラー、設定、および人間のタスクが保持されました。記録は以下の通りです。 `docs/verification/knowledge-book-storage-plan-2026-10-12/actual-roundtrip*.json`.

メタデータはオブジェクト、参照、操作、依存関係を記述するものであり、物理的なSQLページ/インデックス/WALやバックアップの測定値ではない。この合成的な表現は繰り返し出てきて、実際のコスト削減効果を明らかにすることはできない。

回帰ケースには、制限されたデータ区間、エスケープ/Unicode、本内での共有と本間の隔離、競合するアップロード、中断/再開始、破損、部分DDLなしでの未知形式の拒否、新しい書き込みのロールバック、SQLのみの要約、キャッシュ権限の解除、ゴミ処理/消去、遅れたアップロードのクリーンアップが含まれます。CI PostgreSQLマトリックスには、知識ブックとペイロードのテストも含まれています。

<a id="operational-boundaries"></a>

## 運用上の境界

ホストのプライベートローカル/S3設定は、公開のボディURLやモジュール所有の認証情報なしで再利用されます。SQLデータとオブジェクトを一貫したセットとしてバックアップします。欠落した/破損したオブジェクトは明示的に失敗し、参照は保持されます。空のボディは利用できないコンテンツの代わりにはなりません。

クリーンアップは到達不可能なオブジェクトのみを削除します。ゴミ箱は参照を保持し、永久消去ではそれらを解放します。ライブアップロードの依存関係は保護され、失敗した/遅れたアップロードは再試行用の永続的なキーを保持します。完了したジャーナルは、同時に行われる物理的なアップロードをのみ保持し、インストールされた依存関係はオブジェクト/エッジに残ります。歴史的TTLは追加されません。

最終チェック：126件のSQLite関連スイートが通過し、その後、最終エンドポイント/権限チェックを経て60件のブック/ペイロードスイートが通過した。PostgreSQL 17/18関連の68件のスイートも通過し、両エンジンで最終的な11件のペイロードスイートも通過した。型チェック、Webビルド、ドキュメントリンク、diffの空白チェックも通過した。 `docs/verification/knowledge-book-storage-plan-2026-10-12/verification.json`ハートビートとオブジェクトのクリーンアップは独立したスケジューリングを使用するため、クラウドリクエストがハートビートの調整を占有することはありません。
