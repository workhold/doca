## Одна текущая целевая структура

Последняя версия DDL `packages/db/src/create-schema.ts` И его структурные помощники – это единственная целевая структура. Использование новых созданий и проверка обновлений. `createCurrentStructure`Не существует последовательности SQL-миграций при выпуске для обычных добавочных изменений.

Сохраняйте соответствующие типы Kysely. `packages/db/src/schema.ts` Соответствует этой DDL. `schemaEvolution` Это список разрешенных добавлений таблиц/столбцов в обрабатываемых таблицах в рамках поддерживаемой совместимости, а не набор исторических SQL-скриптов. Добавление деклараций не гарантирует изменение типов или безопасную конвертацию данных. Не удаляйте декларации, необходимые для поддерживаемой старой структуры, без согласования с изменениями в поддержке.

`schema_baseline.id` определяет генерацию совместимости, а не каждую версию. Нынешняя генерация — `doca-2026-10-12-book-payload-storage-v1`Утверждено [Согласование схемы знаний-книги](knowledge-book-payload-storage-plan.md) Опубликовано 0.1.24 startup align `doca-2026-10-09-history-storage-v1` Базы данных обрабатываются с помощью обычного средства согласования DDL, после чего запись целевой структуры производится в той же транзакции. Все существующие бизнес-строки, включая результаты работы SQL-кодов и указатели публикаций, остаются нетронутыми. Не происходит автоматиченой конвертации данных, очистки или использования специальных инструментов для чтения данных; оставшиеся старые результаты требуют ручной обработки. Запись структуры целевой базы данных производится автоматически, но читаемость старого формата JSON не обеспечивается. Возможность оффлайн-обслуживания остается доступной перед запуском, если необходимо сохранить старые результаты в нативном формате объектов. Существующие механизмы истории и механизмы переключения конвертации также сохраняются.

Цель — обновление напрямую от поддерживаемой старой структуры к текущей целевой структуре без повторного выполнения вмешающихся скриптов обновления. Одного лишь соответствующего генерации недостаточно: структурные и семантические различия также должны соответствовать согласованной политике. Это не гарантирует обновления для каждой исторической или ручно модифицированной базы данных. Значительное несовместимое изменение может привести к новой генерации только после согласия по вопросам отклонения, какой-либо явной конвертации, сохранения и восстановления.

## Согласование начальных данных

Стартап приобретает базу данных/схему и сравнивает установленную структуру с референсной структурой, созданной на основе текущих DDL. Инспекция охватывает колонки, типы данных, значения по умолчанию, первичные/внешние/уникальные/контрольные ограничения и индексы. PostgreSQL использует временные таблицы, локальные для сессии; SQLite использует отдельную базу данных в памяти. Ни одна из референсных структур не использует документы пользователя.

Нулевость столбца проверяется через `pg_attribute.attnotnull` в PostgreSQL. PostgreSQL 18 также записывает таблицу-столбец `NOT NULL` ограничения в `pg_constraint`Эти дублирующие записи исключаются из сравнения табличных ограничений. Это позволяет добавлять необходимые столбцы, одобренные ранее, не учитывая их новые свойства. `NOT NULL` Входные данные как изменения несвязанных ограничений. Согласно утвержденной политике выравнивания столбцов, существующую непустоту можно выровнять с помощью команды ALTER COLUMN после проверки существующих строк; изменения первичных/ключевых/проверочных ограничений все еще требуют обзора. См. PostgreSQL [18](https://www.postgresql.org/docs/18/catalog-pg-constraint.html) и [17](https://www.postgresql.org/docs/17/catalog-pg-constraint.html) каталоги.

`schemaEvolution` Объявляются новые таблицы и поля, проанализированные. Дополнительные поля, допускающие значение null, и требующиеся поля с исторически установленными значениями могут быть добавлены автоматически при явном объявлении. Также можно создать новые обычные индексы. Допустимое значение представляет собой историченое бизнес-решение; его никогда не должен придумывать реконфигулятор. Требующиеся новые поля без таких значений, изменения типов/значений/ограничений, не поддерживаемые, проверка уникальных индексов, удаление и неизвестные объекты приводят к конкретным последствиям. `SchemaReviewRequired` Планирование перед применением любых постоянных изменений. Нет автоматического удаления или сброса.

## Утвержденное выравнивание родных столбцов (0.2.10)

Владелец согласил на расширение типа varchar в PostgreSQL и синхронизацию стандартных параметров DDL и возможности отсутствия значений. SQLite синхронизирует возможность отсутствия значений только через встроенный оператор ALTER COLUMN. Если стандартные изменения не поддерживаются, запуск приложения прекращается; не происходит пересоздания таблиц, изменения параметров writable_schema, заполнение значений или автоматический переход на более простой режим работы. Будущие изменения в исторической бизнес-семантике все еще требуют согласия перед изменением текущих DDL. Основная политика явно предусматривает согласованность изменений; строгая проверка и существующие механизмы конвертации данных в физическом хранилище сохраняют свои собственные правила.

Каждое отличие классифицируется перед постоянным DDL. PostgreSQL блокирует затронутые таблицы перед проверкой старых строк; SQLite использует существующую транзакцию записи/схемы. NULL, который препятствует использованию поля NOT NULL, неподдерживаемое отличие, неизвестный триггер/вид SQLite или неудачная повторная проверка отклоняют весь процесс, включая любые другие одобренные добавления/индексы. Все принятые атрибуты и записи о размере данных коммитятся вместе. Существующие значения по умолчанию никогда не перезаписывают старые строки, а отмена поля NOT NULL не изменяет первичные/внешние/уникальные/контрольные ограничения. Атрибуты collation, identity и generated-column не разрешены для автоматических изменений.

Текущий целевой размер поля assets.purpose в PostgreSQL — varchar(32), что достаточно для существующего значения 18 символов ai_image_candidate; SQLite сохраняет своё определение varchar(16), при этом не накладывается ограничение по длине. Новые созданные и временные каталоги в PostgreSQL используют тот же специфичный для движка DDL. При запуске теперь можно увеличить размер varchar(16) в PostgreSQL без удаления или обрезки строк; любой более большой размер, требующий уменьшения, отклоняется. Компатibilitась генерация остаётся неизменной.

Проверка создает изолированные базы данных с использованием версии 0.2.9, коммита 655e7ecf71274417d2cf5f352f9151612c702859, сохраняя все 131 оригинальный хэш таблиц в SQLite и PostgreSQL 17/18. Различия в каталоге PostgreSQL ограничиваются длиной 16→32; в SQLite ничего не изменено. Отдельные проблемы связаны с возможностью отсутствия значений, поведением значений по умолчанию, строками родительских/дочерних строк, неизменными страницами/идентификаторами строк в SQLite, повторной/конкурирующей выполнением, отклонением значений NULL/типа/сжатия/неизвестных объектов и откатом транзакции. Смотрите… [предоставить доказательства](verification/ui-image-ark-plan-2026-10-23.md)Перед развертыванием выполните резервное копирование и поддерживайте все хосты на одной версии; автоматическое понижение версии или гарантия смешанных версий не предусмотрены.

## Необходимый процесс разработки и выпуска

1. Определить пострадавшие старые версии, генерацию схем, пути кодирования, сохраненные строки и форматы. Объяснить, какие различия сохраняются, добавляются, отклоняются или явно конвертируются, включая исторические значения, валидацию и восстановление; достичь согласия в соответствии с правилами совместимости репозитория.
2. Обновить последнюю структуру данных и соответствующие типы. Огласить только одобренные и допустимые добавления. `schemaEvolution`Семантиченая конвертация происходит через отдельно утвержденный механизм; обычные обновления должны продолжать использовать общую цель и реконфигулятор.
3. Добавьте или скорректируйте изолированные регрессионные элементы для пострадавших старых структур, содержащих репрезентативные существующие строки. Проверьте сохраненные значения, новые стандартные параметры, пустые новые таблицы в соответствии с условиями, повторное/совместное запуск, а также неизмененные данные/структуру, когда проверка или валидация не позволяют произвести обновление. Убедитесь, что ранее установленные поля не могут быть снова созданы без сигнала после их потери.
4. Выполните регрессию согласования SQLite и матрицу PostgreSQL 17/18. `.github/workflows/database-upgrade.yml` Осуществляется управление схемами и папками PostgreSQL; новые бизнес-изменения должны добавлять свои соответствующие случаи. Один проход через SQLite не гарантирует совместимость с PostgreSQL, а обратный переход к последней схеме также не обеспечивает реальной обновки версии, выпущенной в реальности.
5. Перед выпуском создайте изолированную старую базу данных с использованием затронутой версии, а затем обновите её с кандидатом на выпуск. Проверьте сохраненные бизнес-данные и затронутые функции после обновления и перезапустите систему. Запишите тестированные версии, движки базы данных и ограничения материалов в записях проверки выпуска и обновления.

Используйте синтетические учетные записи и изолированные тестовые базы данных/документы. `tests/database.ts` Создаёт и очищает изолированную схему PostgreSQL для каждого фиксированного элемента. Никогда не запускать разрушительные фиксированные элементы или проверки редактирования совместной работы в отношении данных пользователя. Прочитайте соответствующие контракты совместной работы/плагинов, когда происходит изменение в этих областях.

Контракт и его китайская версия должны соответствовать процессу реализации.
