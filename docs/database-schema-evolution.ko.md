# 데이터베이스 업그레이드 계약

데스크톱 기능에 빈 공간이 추가됨 `desktop_auth_flows` 그리고 `desktop_sessions` 현재의 DDL을 통한 테이블들 `schemaEvolution`호환성 생성을 변경하거나 브라우저/모바일 세션을 변환하지 않고도, 원격 전용 데스크톱 클라이언트는 이전의 체험판을 보존합니다. `local-v1` 열거나 이동시키지 않고 데이터를 사용하기. 참조 [데스크톱 클라이언트](desktop-client.ko.md) 그리고 [기능 검증](../specs/006-desktop-client/validation.md)데스크톱 자격 증명이 발급된 후 애플리케이션을 다운그레이드하려면 별도로 합의된 보존 및 승인 계획이 필요합니다.

[简体中文](database-schema-evolution.zh-CN.md)

승인된 사용자 그룹 추가는 이 계약 및 호환성 생성 기능을 유지합니다: 7개의 비어 있는 그룹/멤버십/초대/ACL 테이블과, 오직 합병된 그룹에만 초기화된 독립적인 디렉터리 정책이 포함됩니다.`system/member/revision=1`). 사용자 설정은 비어 있게 시작됩니다. 역사적인 개인/링크 보너스, 초대장, 공개 설정 및 사용자 디렉터리 정책은 변경되지 않으며, 변환이나 멤버별 보너스 실현도 없습니다. 설치된 구성 행은 조용히 다시 생성되지 않습니다. 모든 서버와 웹을 함께 업데이트합니다; 다운그레이드는 별도의 보존/복구 검토가 필요합니다. 참조 [그룹 규칙](user-groups.ko.md), [출시 노트](releases/0.2.28.md) 그리고 [SQLite/PostgreSQL 17/18 검증](verification/user-groups-2026-10-30.md).

이것은 Doca의 프로젝트 전체에 적용되는 미래의 핵심 데이터베이스 변경에 관한 계약입니다. 개발 및 검토 과정에서는 이 계약을 준수해야 하며, 공유 폴더 배포에만 국한되지 않습니다. 테이블, 필드, 인덱스, 제약 조건, 초기화 또는 영속화된 데이터 형식을 변경하기 전에 이 계약을 반드시 읽어야 합니다. [AGENTS.md](../AGENTS.md) 실행 전에 구체적인 호환성 계획에 합의해야 하며, 이에는 역사적 기록의 의미, 데이터 보존, 검증 및 복구에 관한 내용도 포함됩니다. 아래의 조정 메커니즘은 이미 합의되었으나, 새로운 비즈니스 호환성 결정은 별도의 합의가 필요합니다.

## 현재 목표 구조

최신 DDL이에요. `packages/db/src/create-schema.ts` 그리고 그 구조 도우미가 유일한 대상 구조입니다. 신규 생성 및 업그레이드 검사는 사용됩니다. `createCurrentStructure`일반적인 추가적인 변경 사항에 대해서는 릴리스별 SQL 마이그레이션 순서가 없습니다.

해당 Kysely 유형을 유지하세요. `packages/db/src/schema.ts` 이 DDL과 일치합니다. `schemaEvolution` 이는 지원되는 호환성 버전 내에서 검토된 테이블/컬럼 추가 항목의 허용 목록이며, 과거의 SQL 스크립트 모음이 아닙니다. 선언을 추가해도 타입 변경이나 데이터 변환이 안전해지지 않습니다. 아직 지원되는 오래된 구조에 필요한 선언을 삭제하지 않고는 그에 따른 지원 변경에 동의하지 않으면 안 됩니다.

`schema_baseline.id` 모든 출시가 아닌 호환성 세대를 식별합니다. 현재 세대는 `doca-2026-10-12-book-payload-storage-v1`. 승인된 [지식-북 스키마 정렬](knowledge-book-payload-storage-plan.md) 0.1.24 스타트업 알리언 버전 출시됨 `doca-2026-10-09-history-storage-v1` 일반적인 현재 DDL 조정기로 데이터베이스를 처리한 후, 동일한 트랜잭션 내에서 대상 구조를 기록합니다. 기존의 비즈니스 행들, 즉 오래된 SQL 결과와 출판 포인터도 변경되지 않습니다. 자동적인 구조 변환, 정리 또는 레거시 런타임 리더가 없으며, 남아있는 오래된 결과는 수동으로 처리해야 합니다. 대상 구조는 설치된 구조를 기록하지만, 오래된 JSON의 읽기 가능성은 보장되지 않습니다. 시작 전에 기존의 선택적 오프라인 바이트 정확한 유지보수 기능이 여전히 사용 가능하며, 이 기능은 기존의 객체 형식으로 결과를 보존해야 할 경우에 필요합니다. 기존의 명시적 역사 및 중단된 변환 게이트도 그대로 유지됩니다.

목표는 중간 릴리스 스크립트를 다시 실행하지 않고 지원되는 오래된 구조에서 현재 목표 구조로 직접 업그레이드하는 것입니다. 단순한 일치된 생성만으로는 부족하며, 구조적 및 의미적 차이도 합의된 정책을 충족해야 합니다. 이는 모든 역사적 또는 수동으로 수정된 데이터베이스에서 업그레이드가 가능하다는 보장은 아닙니다. 심각한 호환되지 않는 변경 사항은 거부, 명시적인 변환, 보존 및 복구에 대한 합의가 이루어진 후에야 새로운 생성을 도입할 수 있습니다.

## 스타트업 조정

스타트업은 데이터베이스/스키마를 잠금 처리하고, 현재 DDL로 생성된 참조와 비교합니다. 검사는 컬럼, 타입, 기본값, 주요/외부/유일/체크 제약 조건 및 인덱스를 포함합니다. PostgreSQL은 세션별 임시 참조 테이블을 사용하고, SQLite는 별도의 메모리 내 데이터베이스를 사용합니다. 두 경우 모두 사용자 문서를 사용하지 않습니다.

컬럼의 nullability는 검사됩니다. `pg_attribute.attnotnull` PostgreSQL에서입니다. PostgreSQL 18은 테이블-컬럼도 기록합니다. `NOT NULL` 제약 조건들 `pg_constraint`; 이러한 중복된 항목은 테이블 제약 조건 비교에서 제외됩니다. 이로 인해 승인된 필수 컬럼 추가는 새로운 항목으로 처리되지 않고 가능해집니다. `NOT NULL` 무관한 제약 조건 변경으로 인한 항목 변경. 승인된 컬럼 정렬 정책으로, 기존 행을 검증한 후 네이티브 ALTER COLUMN을 사용하여 기존의 nullability를 정렬할 수 있습니다. 주요/키/체크 제약 조건 변경은 여전히 검토가 필요합니다. PostgreSQL을 참조하세요. [18](https://www.postgresql.org/docs/18/catalog-pg-constraint.html) 그리고 [17](https://www.postgresql.org/docs/17/catalog-pg-constraint.html) 카탈로그.

`schemaEvolution` 새로운 테이블과 필드가 검토되었음을 선언합니다. Nullable 필드와 문자열 형식의 기존 기본값을 가진 필드는 명시적으로 선언될 때 자동으로 추가될 수 있습니다. 새로운 일반 인덱스도 생성될 수 있습니다. 기본값은 과거의 비즈니스 결정에 따라 정해지며, 이는 조정자에 의해 만들어져서는 안 됩니다. 그러한 기본값이 없는 필드나 지원되지 않는 타입/기본값/제약 조건 변경, 유일 인덱스 검증, 제거 및 알 수 없는 객체는 구체적인 결과를 초래합니다. `SchemaReviewRequired` 지속적인 변경이 적용되기 전에 계획을 세워야 합니다. 자동적인 삭제나 초기화는 없습니다.

| 차이 | 스타트업 행동 |
| --- | --- |
| 빈 데이터베이스 | 현재 구조와 초기 시스템 행을 생성합니다. |
| 누락된 테이블을 검토했습니다. | 테이블과 그에 선언된 인덱스를 생성합니다. 역사적 백펌은 추론되지 않습니다. |
| nullable 컬럼 또는 승인된 리터럴 기본값이 있는 필수 컬럼을 검토했습니다. | 열을 추가합니다; 기존 행들은 합의된 역사적 값을 받습니다. |
| 기존 테이블에 일반적인 비유일 인덱스가 누락됨 | 인덱스를 생성하고 구조를 다시 확인하세요. |
| PostgreSQL의 varchar 길이가 증가하거나 기존의 기본값/null 가능성이 달라짐 | 네이티브 ALTER COLUMN을 사용하여 정렬하고, 기존의 모든 값을 유지하며, 강화하기 전에 NULL이 없는지 확인합니다. |
| SQLite의 nullability는 다릅니다. | bundled SQLite 3.53.4의 기본 ALTER COLUMN 방식을 따릅니다. 먼저 기존 행을 검증합니다. 테이블 교체나 외래키 비활성화는 없습니다. |
| SQLite 기본 설정이 다름; 타입 변환/길이 축소; 기본/외부/유일/체크 제약 조건 또는 인덱스 정의가 다름 | 리뷰 계획을 보고하고, 지속적인 변경이 있을 때 멈춰야 합니다. |
| 필요한 컬럼에는 승인된 역사적 값이 없습니다; 기존 테이블에 새로운 고유 인덱스 생성; 이름 변경 또는 삭제; 알 수 없는 테이블; 유지되는 비즈니스 의미론 변경 | 별도로 승인된 보존/변환 계획이 필요합니다. 파괴적이거나 의미적 업그레이드를 무시하고 적용해서는 안 됩니다. |

기존 행의 경우, 새로운 필드가 무엇을 의미하는지와 그 값이 이전의 비즈니스 행동을 어떻게 보존하는지 설명해야 합니다. 새로운 레코드의 기본값과 과거 행의 기본값은 다를 수 있습니다. 권한, 공유, 자격 증명 및 리소스 제한은 더 오래된 행에 편리한 값을 채워서 조용히 해제되어서는 안 됩니다. 이름 변경은 데이터 보존을 위해 검토되어야 하며, 필드를 삭제하고 다시 생성하는 것으로 위장되어서는 안 됩니다.

SQL 구조가 동일한 경우, 구조적 비교로는 변경된 JSON 형식이나 비즈니스 의미를 파악할 수 없습니다. 개발자들은 여전히 그러한 호환성 결정들을 검토하고 합의된 유효성 검사/변환 또는 생성 게이트를 구현해야 합니다. 깔끔한 구조적 비교이더라도 의미적 호환성을 증명하는 것은 아닙니다.

최신 설치된 테이블/컬럼 크기가 교체됨 `schema_baseline.structure_json` 성공적인 조정 후. 이전에 설치된 테이블이나 필드가 사라지는 경우, 원래 자동으로 도입된 것이라도 데이터 손실 가능성이 보고됩니다. 플러그인 비즈니스 테이블은 ...에 존재합니다. [핵심 시스템과는 별개의 공유 비즈니스 데이터베이스](plugin-database-isolation.ko.md)호스트 저장 형식 3은 0.1.25 형식 2을 대체합니다. 활성 상태의 기존 설치는 지속적인 변경 전에 거부되며, 일반적으로 이전 호스트에서 제거된 후 개인 데이터 마이그레이션 없이 재설치해야 합니다. 핵심 DDL 및 호환성 생성은 변경되지 않습니다. 남아있는 기존 설치는... `plugin_<56 hex characters>` 표는 검토가 필요한 미지의 표입니다: 시작 시 이를 보존하고 구조적 변경 전에 중단됩니다. 업그레이드 전에 이전 호스트에서 완전한 정상적인 제거 작업을 수행하세요; 자동 삭제나 데이터 마이그레이션은 없습니다. 플러그인 비즈니스 데이터 버전은 여전히 자체 공개 저장 계약을 사용합니다.

승인된 모든 변경 사항과 피해트 기록은 트랜잭션적이며 커밋 전에 다시 확인됩니다. 실패한 작업은 전체 시도를 되돌립니다. 다시 시작하면 데이터와 설정된 값이 보존됩니다. 검토가 필요한 차이점은 별도로 승인된 데이터 보존/변환 계획이 필요하며, 시작 과정에서는 파괴적인 우회 방법이 제공되지 않습니다.

어떤 지속적인 DDL이 적용되기 전에 전체 계획이 분류됩니다. 만약 한 가지 차이가 검토가 필요하다면, 그 경우 다른 자동 변경 사항은 적용되지 않습니다. PostgreSQL은 스키마 잠금을 획득한 후 새로 카탈로그 읽기를 수행하므로, 동시에 실행 중인 호스트들은 이전에 커밋된 업그레이드를 볼 수 있습니다. 유효하지 않은 기록된 피해트도 시작을 중단시킵니다.

<a id="approved-native-column-alignment-0210"></a>

## 승인된 원본 열 정렬 (0.2.10)

소유자는 동일한 varchar 유형의 PostgreSQL 확장 및 현재 DDL 기본 설정과 nullability의 동기화를 승인했습니다. SQLite는 native ALTER COLUMN을 통해서만 nullability를 동기화합니다. 지원되지 않는 기본 설정 변경은 시스템 시작을 중단시킵니다; 테이블 재구축, writable_schema 수정, 값 보충 또는 자동 하위그레이드 기능은 없습니다. 과거 비즈니스 의미 체계에 대한 향후 변경 사항도 현재 DDL을 변경하기 전에 동의가 필요합니다. 핵심 정책은 명시적으로 정렬을 가능하게 합니다; 엄격한 검사 및 기존의 오프라인 책 저장소 변환 게이트는 각자의 정책을 유지합니다.

모든 차이점은 지속적인 DDL 이전에 분류됩니다. PostgreSQL은 오래된 행을 확인하기 전에 영향을 받는 테이블을 잠급니다; SQLite는 기존의 쓰기/스키마 트랜잭션을 사용합니다. NOT NULL을 방지하는 NULL, 지원되지 않는 차이점, 알려지지 않은 SQLite 트리거/뷰, 또는 실패한 재검토는 다른 경우에 승인된 추가 항목/인덱스를 포함한 전체 시도를 거부합니다. 모든 허용된 속성과 피해프트 기록은 함께 커밋됩니다. 기존의 기본 설정은 오래된 행을 다시 작성하지 않으며, NOT NULL을 삭제해도 주요/외부/유니크/체크 제약을 변경하지 않습니다. 콜렉션, 식별자, 생성된 컬럼 속성은 자동 변경에 대해 허가되지 않았습니다.

PostgreSQL의 현재 assets.purpose 값 목표는 varchar(32)이며, 기존의 18자리 ai_image_candidate 값에 충분합니다. SQLite는 varchar(16)로 선언하지만, 그 길이에 대해서는 강제하지 않습니다. 새로 생성된 것과 임시 PostgreSQL 참조 카탈로그는 동일한 엔진 특정 DDL을 사용합니다. 시작 시에는 배포된 PostgreSQL varchar(16)를 삭제하거나 행을 잘라내지 않고 확장할 수 있으며, 축소가 필요한 더 큰 설치 길이는 거부됩니다. 호환성 생성 과정은 변함이 없습니다.

검증은 0.2.9 소스 커밋 655e7ecf71274417d2cf5f352f9151612c702859를 사용하여 격리된 데이터베이스를 생성하며, SQLite와 PostgreSQL 17/18에서의 모든 131개 원본 테이블 해시를 보존합니다. PostgreSQL 카탈로그의 차이점은 목적 길이가 16→32로 제한되며, SQLite는 변경되지 않습니다. 별도의 문제는 네이티브 nullability/default 동작, 부모/자식 행, 변경되지 않은 SQLite 루트 페이지/rowid, 반복적/동시 실행, NULL/type/shrink/unknown-object 거부 및 트랜잭션 롤백에 관한 것입니다. 자세한 내용은...을 참조하십시오. ## 승인된 브라우저 도우미 추가

첫 번째 릴리스에서는 현재의 DDL을 통해 7개의 빈 테이블이 추가됩니다. `schemaEvolution`, 변경하지 않고 `doca-2026-10-12-book-payload-storage-v1`: `browser_clipper_profiles`, `browser_clipper_connections`, `browser_clipper_activations`, `browser_clipper_receipts`, `browser_clipper_assistant_sessions`, `browser_clipper_web_sessions`, 그리고 `browser_clipper_login_codes`모든 원본 문서, 권한 및 설정 행은 그대로 유지됩니다.

출시 전에 소유자는 v1 활성화 패키지 / 180일 토큰을 웹사이트 세션 기반 인증으로 교체하는 것을 명시적으로 승인했습니다. 기존 v1 설정, 활성화 및 토큰은 변환 없이 거부됩니다. 처음 5개 테이블, 기존 자격 증명 열/기록, 프로필 캡처, 영수증 및 대화 내용은 보존되며, 기존 활성화 기록은 무효화됩니다. 새로 생성된 2개 테이블은 비어 있게 시작되며 추론된 보조금을 받지 않습니다. 기존 모바일, MCP 및 비즈니스 플러그인 인증은 별도로 유지됩니다.

공개 사이트 설정은 엄격한 버전 2입니다. 60초간의 코드와 SHA-256 검증자 챌린지를 통해 10분간의 접근 권한을 얻으며, 이는 정확한 웹사이트 세션 및 설치 연결에 종속됩니다. 로그아웃이나 세션 취소는 접근 권한을 무효화하며, 연결 취소는 명시적으로 복구될 때까지 자동 재승인을 차단합니다. 브라우저 원산지 작업 ID는 같은 대화 내에서 일반 웹사이트 작업과 취소를 구분합니다. 수락된 문서와 이미지는 로그아웃, 자격 증명 교체, 취소로도 절대 삭제되지 않습니다.

그것 [로그인 수락 기록](verification/browser-clipper-login-2026-10-21/README.md) SQLite / PostgreSQL 17/18에서 실제로 배포된 0.2.6 버전의 장치들에 대한 업그레이드: 124개의 기존 테이블 해시가 유지되며, 7개의 빈 테이블이 추가되고, 반복/동시 시작이 발생합니다. 별도의 장치들은 출시 전 v1 행을 유지하면서 빈 세션/코드 테이블을 추가하고, v1 접근을 거부하며, 부분적 쓰기 없이 검토가 필요한 차이점도 거부합니다. 데이터베이스, 파일 볼륨, 자격 증명 마스터 키를 백업한 후 서버, 웹, 확장 기능을 함께 업데이트합니다. 다운그레이드에는 별도로 승인된 보존 및 승인 계획이 필요하며, 기존 바이너리는 기존 자격 증명 처리를 복원할 수 있습니다. 기존 인증 어댑터, 자동 변환, 테이블 제거, 데이터 재설정은 도입되지 않습니다.

## 승인된 독립적 MCP 실행 (2026-11-01)

소유자가 승인했습니다. `ai_jobs.session_id`, `ai_jobs.model_id` 그리고 `mcp_contexts.session_id` 네이티브 속성 정렬을 사용하여 불필요한 값을 제거하고, 빈 값을 추가함 `ai_task_resources` 현재의 DDL을 통해 대장을 처리함 `schemaEvolution`기존 값은 복원되거나 변환되지 않습니다. 호환성 생성은 변경되지 않습니다. 새로운 MCP 작업에는 대화/모델 연관성이 없습니다; 실제 제공자 호출은 자체 사용 사실을 유지합니다. 역사적인 MCP 대화는 저장되지만 채팅 입력 지점에서 제외되며, 다시 시작되거나 변환되지 않습니다. 파일, 보조금, 운영 영수증 및 보안 감사 자료는 그대로 유지됩니다. SDK 0.2.0 및 AI 서비스 v2는 조정된 호스트/Web/플러그인 업데이트가 필요하며, 기존 인터페이스 어댑터나 자동 다운그레이드는 없습니다. 업그레이드 전에 백업을 수행하고, 별도로 검토된 복구를 위해 나중에 작성된 내용을 보관하십시오. 참조하십시오.
