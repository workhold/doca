# 플러그인을 설치하고 배포합니다.

0.1.26는 사용합니다. [공유 플러그인 비즈니스 데이터베이스](plugin-database-isolation.ko.md)핵심 부분과는 분리된 형태로, 자동 네임스페이스가 제공됩니다. 이는 0.1.25에서 출시된 플러그인별 데이터베이스를 대체합니다. 업그레이드를 위해서는 이전 호스트에서 일반적인 제거 후 재설치가 필요하며, 플러그인 데이터는 마이그레이션되지 않습니다.

[中文](plugin-deployment.zh-CN.md)

승인된 [관리형 저장소 계약](plugin-horizontal-scaling.ko.md) 필요로 함 `doca.storage: "host"` 호스트가 소유한 지속성도 포함됩니다. 정적 거부, 관리되는 SQL 및 개인 객체가 구현되었습니다. 자격 증명은 SDK 소스 0.1.8에 내보내집니다; 임시 작업 공간과 클러스터 작업 소진 문제는 여전히 해결되지 않았습니다. 플러그인은 로컬/원격 백엔드를 선택하지 않으며 비즈니스 데이터 디렉토리도 받지 않습니다.

관리자들은 사용합니다 **관리자 → 플러그인** 공식 스토어를 둘러보고, 로컬 ZIP 파일을 업로드하여 플러그인을 설치, 업그레이드, 활성화, 비활성화 또는 제거할 수 있습니다. 변경 사항은 원하는 설치 형태로 저장되며 각 인스턴스의 다음 재시작 시에 적용됩니다. 페이지에는 전역 목표와는 별도로 해당 인스턴스의 실행 중인 버전이 표시됩니다. 현재 제거 작업은 필요한 비즈니스 정리 핸들을 호출한 후 구조 마커를 지웁니다. 핸드 실패 시 설치는 그대로 유지됩니다. 호스트 관리형 프라이빗 스토어 정리는 생성 차단 및 내구성 있는 객체 쓰레기 기록을 사용하며, 비즈니스 작업 소진은 아직 구현되지 않았습니다. 플러그인 파일 시스템 삭제는 금지됩니다. 설치된 플러그인의 업그레이드는 여전히 동일한 절차가 필요합니다. `doca.dataVersion`플러그인은 초기화 과정에서 실제 데이터베이스 구조를 확인합니다.

```dotenv
DOCA_PLUGIN_STORE_URL=https://store.smartdoca.cc
DOCA_PLUGINS_DIR=/data/plugins
```

매장 주소는 설정 가능한 HTTP(S) 원본입니다. 원격 서비스 가용성을 별도로 확인하세요; 사용할 수 없는 매장은 로컬 업로드 및 설치된 플러그인을 사용할 수 있게 합니다. 비어 있음 `DOCA_PLUGINS_DIR` 돌아간다 `${DOCA_DATA_DIR:-./data}/plugins`작업 디렉터리에 대해서만 호스트가 견고한 데이터베이스/객체 저장소를 설정합니다. business-data-directory 환경 변수는 플러그인과 관련이 없으며, 플러그인의 API는 호스트가 로컬에 저장하나 원격에 저장하나를 결코 노출하지 않습니다.

제공된 Compose 배포에 대해서는 배포 디렉터리에서 실행하세요:

```sh
docker compose restart doca
```

여기서, `doca` 서비스 이름은 무엇인가요? `services` 안에 `compose.yaml`; 컨테이너 이름은 다를 수 있습니다. 서비스 이름을 변경한 경우, 그대로 사용하세요. `doca` 서비스 이름을 포함한 명령어에서.

다중 인스턴스 배포에서 모든 인스턴스를 재시작하세요. 다른 배포 유형의 경우 해당하는 슈퍼바이저를 사용하세요. UI는 프로세스를 재시작하지 않습니다. 롤링 재시작 중에는 트래픽을 줄이거나 플러그인 API가 변경된 경우 친화성 설정을 사용하세요. V1은 무정지 혼합 버전 API를 제공하지 않습니다.

## 저장소 개선 사항 적용 (2026-10-03, SDK 소스 0.1.8)

`@smartdoca/plugin-sdk/storage` 현재 설치용 제품을 수출하고 있습니다. `pluginDatabaseToken` (`storage.sql.v1`) 그리고 `pluginObjectStorageToken` (`storage.objects.v1`). 데이터베이스 하위 집합은 명시적 스키마 버전 1이며, 텍스트/int32/double 컬럼, 기본/유일 제약 조건, 구조화된 select/insert/update/remove 작업 및 한 번 실행되는 콜백을 포함한 트랜잭션이 있습니다. SDK 소스 0.1.8은 추가로 내보내기도 합니다. `pluginCredentialToken` (`storage.credentials.v1`): 서버 전용 암호화된 CRUD, 메타데이터 및 수정 검사. 참조 [자격증 API](plugin-credentials.ko.md)연결, 외래 키, 일반적인 SQL, upsert 및 작업 공간은 내보내지 않습니다. 비즈니스 SQL은 코어와는 별개의 공유 호스트 관리 데이터베이스를 사용합니다: 테이블 프리픽스가 있는 하나의 SQLite 파일 또는 자동 플러그인 스키마와 공유 연결 풀이 있는 하나의 PostgreSQL URL/계정입니다. 프로세스 격리은 구현되지 않았습니다. 참조하세요. [저장 설정 및 업그레이드 전 삭제 계약](plugin-database-isolation.ko.md).

논리적 데이터베이스는 사용 `plugin:<pluginId>`, 사용자 파일의 소유권 및 개인 객체 사용 `plugins/<pluginId>`, 그리고 ZIP 파일을 풀어주는 것 `host/plugin-releases/<sha256>.zip`완전히 불변한 ZIP 바이트들은 환경에 설정된 파일 저장소에 저장됩니다. 공유 데이터베이스에는 레지스트리 버전 2, 아카이브 참조 및 신뢰할 수 있는 파일 해시 인덱스가 저장되어 있습니다. 확인된 캐시 접근은 ZIP 파일을 다시 다운로드하지 않습니다. 모든 인스턴스는 수동으로 재시작됩니다. 새로운 호스트 기준은 더 오래된 데이터베이스/포맷/SDK 패키지를 거부하고 그 데이터를 보존하며, 마이그레이션이나 대체는 없습니다. 자세한 내용은... [정확한 구현 및 제한 사항](unified-storage-implementation.md).

## 배포 및 파일 시스템

모든 인스턴스는 동일한 호스트 데이터베이스를 사용합니다. PostgreSQL은 분산 배포 방식으로 적합합니다. 데이터베이스는 원자적 목표 레지스트리와 불변 아카이브 참조를 저장하며, 로컬 업로드를 포함한 전체 ZIP 파일들은 설정된 공유 파일 저장소에 존재합니다. 각 인스턴스에는 개인용 쓰기 가능한 캐시가 있습니다.

```text
/data/plugins/
  .releases/<sha256>/          verified immutable releases
  .staging/                   temporary extraction
  .imports/                   retained offline folder imports
```

스타트업은 공유 아카이브에 모든 파일을 검사하고, 누락되거나 손상된 파일을 복구한 후에야 플러그인을 불러들입니다. npm 종속성은 설치하지 않으며, 소스 코드를 컴파일하거나 스토어에 연락도 하지 않습니다. 누락되거나 손상된 공유 아카이브는 스타트업을 방해합니다. 불변 릴리스가 포함된 공유 데이터베이스 메타데이터와 설정된 파일 저장소를 모두 백업해야 합니다. 호스트는 관리되는 플러그인 기록, 개인 객체, 사용자 파일 참조 및 자격 증명도 백업합니다. 다중 인스턴스 지속적인 서버는 공유되어야 하며, 디렉터리 이름은 분산 데이터베이스가 아닙니다.

실행 중인 인스턴스 간에 플러그인 캐시 디렉터리를 공유하지 마세요. 한 인스턴스에서 설치한 플러그인을 다른 인스턴스로 수동으로 복사할 필요가 없습니다. 로드 밸런서 라우팅을 처리하기 위해 공유 아카이브에서 과거 버전의 브라우저 자산도 요청에 따라 복원할 수 있습니다.

오프라인 설치: 인스턴스가 중지된 상태에서 전체 릴리스를 수행합니다. `<DOCA_PLUGINS_DIR>/<plugin-id>/`시작 시, 패키지가 되어 공유 레지스트리에 게시되며, 그 후 다른 위치로 이동됩니다. `.imports/`다른 경우는 재시작 시 동기화됩니다. 정기적인 관리에서는 ZIP 업로드를 사용해야 합니다. 루트 npm 매니페드나 소스 로딩 호환성 경로는 없습니다.

지역 ZIP 코드와 매장 ZIP 코드는 동일한 레이아웃과 검사 방식을 가지고 있습니다. 사용하세요. [저장 프로토콜 및 패키지 명세서](plugin-store-protocol.ko.md)프로그램 파일, 쓰기 가능한 비즈니스 데이터 및 자격 정보는 별도로 유지되어야 합니다. 추출 과정 중에는 스크립트가 실행되지 않아야 합니다. 완전한 실행에 필요한 종속성도 실제 파일 형태로 제공되어야 하며, pnpm 링크는 배포 가능한 파일이 아닙니다.

## 생명주기 및 보존

호스트는 코드를 임포트하기 전에 SDK 범위, 중복 ID, 데이터 버전 및 플러그인 의존성을 확인합니다. 설정은 전역적이며, 요청 식별자와 권한은 호스트가 소유합니다. 관리자는 수정 확인을 사용하여 서로 충돌하는 관리자들이 서로를 덮어쓰는 대신 다시 시도하도록 합니다. 운영팀은 보안 감사 이벤트를 생성합니다.

비활성화 및 제거는 재시작 시 적용됩니다. 그동안 기존 프로세스는 여전히 기존 플러그인을 제공합니다. 기존 코드 캐시와 불변 아카이브는 실행 인스턴스 및 재설치를 위해 보존됩니다; v1에서는 자동 아카이브 정리 기능이 없습니다. 비활성화/shutdown은 지속적인 상태를 보존합니다. 사용자 첨부파일, 문서 페이로드, 기타 비즈니스 참조 및 파일 영수증은 자동으로 삭제되지 않습니다; 관리되는 개인 상태 정리는 호스트가 직접 처리하며 여전히 클러스터 코오롤리터가 필요합니다. 취소는 응답 인스턴스의 시작 선택을 복원합니다; 이는 다른 프로세스의 즉시 롤백이 아닌 새로운 전 세계적인 목표 상태 변화입니다.

실제 플러그인 초기화 실패가 여전히 시작을 중단시킵니다. SDK 및 종속성 호환성 문제는 아래와 같이 개별적으로 처리되며, 플러그인 관리 기능은 작동합니다. 핫 언인스톨, 클러스터 완료 대시보드, 네이티브 모바일 동적 코드 설치 기능은 없습니다.

유효성 검사는 격리된 데이터베이스와 임시 디렉터리를 사용합니다. 참조하세요. [상점 수락](plugin-store-protocol.ko.md#cross-repository-acceptance).

<a id="compatibility-failure-isolation"></a>

## 호환성 실패 격리

불호합하는 SDK 범위나 사용할 수 없는 필수 종속성으로 인해 영향을 받는 비즈니스 플러그인이 격리됩니다. 호스트 플러그인과 관련 없는 플러그인들이 시작되며, Admin → Plugins에서 이유를 설명하고 업그레이드를 요청합니다. 설치된 선택 항목, 아카이브, 비즈니스 데이터 및 자격 정보는 보존됩니다. 기존 패키지는 변환되지 않고 기존 SDK 코드는 실행되지 않습니다. 새로운 온라인 설치도 여전히 불호합하는 패키지를 거부합니다. 완전한 오프라인 설치 폴더는 원래의 정체성을 유지하며 동일한 격리를 받습니다.

오래된 패키지는 등록한 모든 비즈니스 정책을 정적으로 선언하지 않습니다. 이 인스턴스에는 활성화되었지만 사용할 수 없는 플러그인이 있으므로, 기존 플러그인 정책 검사에 포함된 작업은 503을 반환합니다. 로그인, 읽기 및 플러그인 관리 기능은 여전히 사용 가능합니다. 호환되는 패키지로 업그레이드하거나 해당 플러그인을 명시적으로 비활성화한 후 모든 인스턴스를 재시작하여 이 보호 기능을 제거하세요. 누락된 플러그인 권한 소스는 계속해서 인증을 거부합니다. 호환되지 않는 SDK 코드는 제거 하이킹을 실행할 수 없으니 먼저 업그레이드하세요. 단계적 호환 업그레이드는 SDK와 호환되지 않는 패키지로 되돌릴 수 없습니다. 대체 패키지는 dataVersion과 기존 비즈니스 구조를 유지해야 합니다.

격리는 인스턴스별로만 적용되는 진단 상태이며, 레지스트리나 데이터베이스 스키마의 변경 사항은 아닙니다. 손상된 아카이브, 유효하지 않은 메타데이터, 코어 장애 및 실제 생명주기 오류는 여전히 명시적으로 실패합니다. 데이터 마이그레이션이나 애플리케이션의 하위 호환화는 이루어지지 않습니다.
