# 知識ブック生成の性能とバッチチェックポイント

[简体中文](knowledge-book-generation-performance.zh-CN.md)

2026-10-19。ユーザーは新しいチェックポイントテーブルとプライベートパーシステンシングフォーマットを明確に承認しました。実装は、プロダクションが展開されなかったその承認実行での孤立データで検証されました。報告された15万文字、8時間のプロダクション実行はローカルでは利用できませんでした。これらのテストでは、その具体的な原因やプロダクション時間を予測することはできません。

<a id="execution-improvements"></a>

## 実行の改善

計画された記述サイズは、有料リクエスト前にモデル出力予算に対してバッチごとに請求されます。文字割り当て、正確な請求範囲、制限された修復措置、明確な失敗の記録は引き続き適用されます。独立したレビュー統合作業は既存の2人の作業者制限の下で行われ、秩序とすべての否定的な検査結果が保持されます。単一の観察には、冗長な統合呼び出しは不要です。全書の受け入れと必要な品質ゲートは引き続き有効です。

以前は、プロセスの再起動を経ても完全なノードだけが生き残りました。現在は、概要作成、クレームの割り当て、抽出、書き込み、整理、品質レビューを含む未完了のノード内でも完全に有効なリクエストが生き残ります。完全なホスト分割決定も保存されるため、過大な親ノードを再び要求する必要はありません。部分的なモデルストリームは決して保存されません。

<a id="approved-persistence-contract"></a>

## 承認された永続性契約

- 空のものを追加する `knowledge_book_batch_checkpoints` 最新のDDLを通じてテーブル `schemaEvolution` 既存の状態で `doca-2026-10-12-book-payload-storage-v1` 生成。古い行は変換されたり埋め戻されたりしない。歴史的な完全ノードの再利用と、既存のレガシーボディ境界は変わらない。
- 別のプライベートを使用する `knowledge_book_batch_checkpoint_ref` v1マーカーとバッチ所有者、既存の不変オブジェクトコーデック、アップロードジャーナル。大規模な結果はSQLの外側に保持される。既存のノード/実行/リリース参照制約、公開されたv1構成/アーティファクトフォーマットは変更なし。
- 各リクエストを元の実行/ノード、フローズンされた設定、ノードの入力、ソースバージョン/コンテンツハッシュと重み、現在の候補、非秘密モデルの設定、アルゴリズムバージョン、および正確なリクエスト範囲に結び付ける。 `scope_hash`, `plan_hash`, `input_hash` そして `batch_key` アイデンティティを厳守する。ランでバッチをコピーしないこと。
- 検証済みの完全な結果や完全なホスト分割決定のみを保持する。否定的な判断や詳細な診断情報も保存する。最終的な集計、図表の検証、ソースの承認、割当数や出版の承認は依然として適用される。
- 読み取り、生成、トランザクショナルインストールの結果を得る前に、ソース権限と有効なリースを再確認する必要がある。競合するインスタンスは一つの不変の勝者をインストールする。アップロード中にキャンセルや権限/リースの喪失が発生するとインストールができない。
- 内部 `evidenceInventory` ソースタイトル/テキストのコピーなしで、ソースロケーター、バージョン、ハッシュ値、ウェイト、権限参照を保存する。モデルフィンガープリントには、APIキー、エイリアス、価格は含まれず、プロバイダー、モデル、エンドポイント、APIモード/バージョン、入力/出力予算、ツール設定が含まれる。
- 既存の明示的なレジストリフローを通じたコンテンツ修復により、新しいコンテンツ範囲が確立され、旧チェックポイントは再利用せずに保持される。同じ範囲内でのモデルやアルゴリズムの変更には新たな実行が必要である。不明なバージョン、破損、無効な結果、または欠落したオブジェクトは回復を阻害し、静かに再生成や変換を引き起こすことはない。

これらは新しいプライベートチェックポイントであり、古い結果形式用のアダプターではありません。バッチチェックポイントがない既存の行は、未完了のノードが新しいリクエストを実行するまで、完全なノードの動作を維持します。

<a id="deployment-retention-and-recovery"></a>

## デプロイ、保持、復元

データベースとプライベートオブジェクトストアをバックアップし、元の認証マスターキーを保持し、実行者を停止し、すべての実行者とガベージコレクターを一緒に更新する。スキーマ調整では、空のテーブルをトランザクション的に追加し、生成バンプなしでその影響範囲を記録する。古い実行者やコレクターと新しいものが混在している場合はサポートされていない。なぜなら、古いコードでは新しい参照を保護できないからだ。

`DOCA_BOOK_BATCH_CHECKPOINTS` デフォルトで `on`; のみ `on` そして `off` 受け入れられ、無効な値はデータベースを開く前に起動に失敗する。変更後、再起動する。現在のバイナリでは、 `off` すべてのチェックポイント行とオブジェクトピンを保持しながら、不完全なノードを再実行する。品質ゲートを迂回したりデータを変更したりはしない。失敗、破棄、一致しないスコープはチェックポイントを削除しない。永久的なブックの削除は、既存の明示的な削除パスを通じてその参照を解放する。

オフラインでのデータ保存ロールバックでは、変更前の既存のチェックポイントを破棄する。バイナリの降格、バックアップの復元、またはチェックポイントの変換には、別途承認された保存および復元計画が必要である。この制限を回避するために、行、オブジェクト、またはテーブルを削除しないこと。

<a id="verification"></a>

## 検証

完全な合成パイプラインが2回目の書き込みバッチで失敗し、全体の実行環境を置き換えて再開する。書き込み要求の総数は2から3に増加し、4ではない。そして、42件のクレームが受け入れと公開を経て完了する。他のテストでは、長文形式の計画/割り当て、負の診断情報、分割決定が復元される。実際のファイルストレージテストでは、1回のバッチがコミットされ、SIGKILLによってプロセスが終了する。新しいプロセスとリースにより、最初のバッチが0回のプロデューサー呼び出しで復元され、欠けているバッチのみが一度実行される。

実際にリリースされたもの `smartdoca/doca:0.2.3` 孤立したSQLiteとPostgreSQL 17/18の試合データを作成した画像です。アップグレードすると、過去の13個のテーブルの記録のハッシュ、node/run/releaseのバイトデータ、出版ポインタ、および生成情報がすべて保持されます。新しいテーブルは空の状態から始まります。詳細は… [確認記録](verification/knowledge-book-checkpoints-2026-10-19/README.md) コマンド、結果、制限について。
