# 共有プラグインビジネスデータベース

[简体中文](plugin-database-isolation.zh-CN.md)

すべてのプラグインは、コアデータベースとは別の、ホストが管理するビジネスデータベースを共有します。PostgreSQLではデプロイのために1つのデータベース/アカウント設定が必要で、ホストは自動的に各プラグインのスキーマとテーブルを作成します。SQLiteでは設定は不要で、自動的に共有ファイルが作成されます。プラグインは変更されずに使用を続けます。 `storage.sql.v1` SDK、スキーマバージョン1 `dataVersion`接続文字列、ドライバー、ファイルシステムパスなしで。

<a id="configuration-and-isolation"></a>

## 構成と隔離

SQLiteはデフォルトで `<DOCA_SQLITE_PATH>.plugins.db`. `DOCA_PLUGIN_DATABASE_PATH` 任意に別の永続的なローカルファイルを選択します。このファイルのモードは0600です。各物理テーブルには `plugin_<SHA256(plugin ID), first 56 hex>__` プレフィックス：SDKテーブル名は変更されません。インメモリホストでは、各ホスト接続ごとに1つの共有インメモリプラグインデータベースが使用されます。共有ファイルをコアデータベースおよびプライベートファイルストレージと共にバックアップしてください。SQLiteは単一ホストオプションとして残ります。

PostgreSQLは、1つのオペレーターが設定するビジネスデータベースとログインアカウントを使用します。アカウントの権限はデプロイオペレーターが選択します。通常のアカウント、スーパユーザー、管理機能を持つロールやメンバーシップ、およびコア用に使用される同じアカウントが受け入れられます。このアカウントは有効である必要があります。 `CONNECT` そして `CREATE` そのビジネスデータベースにおける特権により、プラグインスキーマを作成できる。 `USAGE` そして `CREATE` それに `public` 共有マーカーを初期化するためのスキーマ。データベースレベル `CREATE` スキーマレベルを付与しない `CREATE`PostgreSQL 17/18では、デフォルトで通常の非所有者ロールには後者が付与されません。詳細は参照してください。 [PostgreSQLスキーマ権限](https://www.postgresql.org/docs/18/ddl-schemas.html#DDL-SCHEMAS-PRIV)SQLプラグインを有効にする前に、これらを一度設定してください。

```dotenv
DOCA_PLUGIN_DATABASE_URL=postgresql://doca_plugins:replace-me@postgres:5432/doca_plugins
DOCA_PLUGIN_DATABASE_POOL_MAX=4
```

新しいデプロイの場合、以下のオプションの専用アカウントの例がストアを設定します。 `psql` （パスワードを変更する）。適切な権限を持つ既存のアカウントも直接設定できます。

```sql
CREATE ROLE doca_plugins LOGIN PASSWORD 'replace-me';
CREATE DATABASE doca_plugins;
REVOKE ALL ON DATABASE doca_plugins FROM PUBLIC;
GRANT CONNECT, CREATE ON DATABASE doca_plugins TO doca_plugins;
\connect doca_plugins
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO doca_plugins;
```

既存のデプロイについては、その役割、データベース、データを保持します。初期化レポートが欠落している場合は `USAGE`/`CREATE` 〜の上で `public`データベースのオーナーとして接続する **プラグインビジネスデータベース** そして走る `GRANT USAGE, CREATE ON SCHEMA public TO doca_plugins;`設定されたロール名を使用して。プラグインスキーマを作成する際にデータベースが見つかりませんというエラーが発生する。 `CREATE`、授与 `CREATE ON DATABASE doca_plugins TO doca_plugins` 所有者として。権限を修正した後に起動を再試行する。アンインストール、リセット、データ変換は不要です。ホストは自動的に権限を付与しません。これらの権限付与は、専用プラグインビジネスデータベースにのみ適用されます。既存の共有マーカーには必要ありません。 `CREATE` 〜の上で `public` 再び。接続文字列/パスワードや生のSQLエラーはプラグインの応答から隠されており、これらの修正されたホスト設定診断情報は明示的に報告される。

ホストが自動的に作成する `plugin_<SHA256(plugin ID), first 56 hex>` 最初の宣言におけるスキーマ。各プラグインは、各ホストインスタンスごとに1つの接続プールを共有する。 `DOCA_PLUGIN_DATABASE_POOL_MAX` 1から20までの整数で、デフォルトは4です。このプール、コア/AI/Webhookプール、およびインスタンス数をサーバー接続予算に含めます。すべてのレプリカは同じ共有ビジネスデータベースを使用しなければなりません。別のプラグインを追加する際には、データベース、ロール、または接続エントリは必要ありません。SQLストレージを持たないプラグインは、このURLを必要としません。

設定されたビジネスデータベースは、URLが同じログインを使用していても、コアとは別である必要があります。ホストは高レベルの役割属性、役割メンバーシップ、コアテーブルの権限を検査せず、データベースアカウントの権限も変更しません。オペレーターはPostgreSQLのグレードでアカウントを制限するかどうかを決定します。ホストはデータベース/役割を作成せず、決してコアストレージに切り替えることはありません。PostgreSQLトランザクションはトランザクションローカルスキーマを設定します。プール接続は他のプラグインのスコープを保持しません。アンインストールは、削除されたプラグインの宣言されたテーブルとインストールマーカーのみを検査し削除します。他のプラグインのスキーマ/データや共有ストアは残ります。

オペレーターが管理するアカウントポリシーは2026-10-16に承認されました。これは、0.1.26～0.1.29で導入されたアカウント権限拒否機能の代替です。既存のフォーマット-3の宣言、マーカー、世代、データバージョンは変換せずに保持され、アップグレードによってデータや権限が変更されることはありません。ホストをロールバックすると古いアカウント制限が復元されるため、管理者のログインが再び拒否される可能性があります。ロールバックを計画する際は、既存のデータベース、データ、設定を保持してください。以下のフォーマット-2のアップグレード手順は変更されていません。

これはホストが所有するSDKサービスによる隔離です。プラグインは信頼できるNode.jsプロセス内で実行され、ビジネスロールの共有はプロセスやオペレーティングシステムのサンドボックスではありません。

コアは、ユーザー、文書、権限、セキュリティ監査、生のAI使用状況、プラグインレジストリ/アーカイブ参照、名前空間記録、暗号化された認証情報、プライベートオブジェクト参照、持続可能なオブジェクトガベージインテントを保持します。ファイルおよび認証情報の所有権/権限、コアDDL、 `schema_baseline.id` 変わらない。

<a id="exact-storage-format-and-lifecycle"></a>

## 正確な保存形式とライフサイクル

ホスト宣言はフォーマット3を使用する`storageVersion: 3`、最初は `schema: null`）。共有のルートマーカーは `_doca_shared_plugin_database` フォーマット3。各プラグイン `_doca_plugin_store` マーカーはその正確なID、生成日、データバージョン、および正規化されたスキーマを記録します。マーカーの検証と範囲内のインスペクションにより、関連のないデータの採用が防がれます。共有ファイル、名前空間、または以前に宣言されたテーブルが欠けている場合は拒否され、それらは決して静かに再作成されることはありません。URL/ファイルを変更してもデータは移行せず、スキーマが記録された後は空の代替物の送信も拒否されます。

最初の宣言はコア名前空間をロックし、プラグイン名前空間、ビジネステーブル、マーカーを一つのビジネストランザクションで作成し、その後コアトランザクションに宣言を記録します。中断されたコアコミット後の再試行では、正確にコミットされたビジネスマーカーと実際の構造のみが受け入れられます。異なるスキーマ定義、型/デフォルト/有効性、プライマリ/ユニーク制約、予期しないテーブルは拒否されます。ユーザートランザクションのコールバックは一度実行され、完了後に期限が切れると処理が終了します。ビジネスコミット後にコアコミットが失敗すると、ビジネスイデミポネシティ/リードバックが必要な不確定な結果となり、コールバックは再実行されません。

コア名前空間ロックはビジネスコミットによって保持されるため、アンインストールは承認された書き込みを待ちます。ビジネスアンインストールホックが先に実行されます。成功した場合、コアレジストリトランザクションが生成をフェンシングし、インストール選択と認証情報をクリアし、プライベートオブジェクトのクリーンアップをキューに追加します。ユーザーファイル、権限、受領書、リリースアーカイブは保持されます。ホックが失敗した場合、インストールは保持され、外部ホックの効果は元に戻すことができません。

ビジネスクリーンアップは、保持された宣言を永続的な意図として使用してコアコミットを実行する。スタートアップ時や定期的なクリーンアップ、アンインストールや再インストールの試行も再試行される。クリーンアップでは、削除された生成物やマーカーを確認した後で宣言されたテーブルを削除する。不明なテーブルや一致しないマーカーは、部分的な削除なしでクリーンアップを拒否される。PostgreSQLはイデムポテント再試行のために空の名前空間を残す。SQLiteは共有ファイルを残す。再インストール時はクリーンアップを待ち、生成番号を増やし、空のビジネステーブルを作成する。分散型原子コミットや自動クラスタタスクの消滅は保証されていない。各インスタンスを再起動する必要がある。

<a id="approved-upgrade-from-0125"></a>

## 0.1.25からの承認されたアップグレード

所有者が承認した **以前のバージョンでの通常のアンインストール後、プラグインデータを移行せずに再インストールする**0.1.25のリリースでは、プラグイン別のファイル/データベースとフォーマット2を使用する。ステートレスでないプラグインを含むフォーマット2のインストールは、コアレシオリエーションの書き込み前に拒否される。非現行のもの `DOCA_PLUGIN_DATABASE_DIR` そして `DOCA_PLUGIN_DATABASES_JSON` 設定は明確に拒否されている。古いデータベース・ファイルの読み取り機能、自動データ変換、二重書き込み、または古いデータベース・ファイルの自動削除機能はない。

1. 元のコアデータベース、すべての古いプラグインデータベース/ファイル、プライベートファイルストレージ、設定、および元の認証マスターキーをバックアップする。
2. 前のホストでは、通常、すべての外部ビジネスプラグインをアンインストールし、保留中のクリーンアップを処理していました。これにより、プラグインのプライベートビジネス記録、暗号化された認証情報、プライベートオブジェクトが意図的に破棄されます。再インストール後、プラグインを再設定し、外部アカウントを再設定します。コアデータと通常のユーザーファイルは残ります。
3. すべてのホストインスタンスを停止する。古いプラグインごとの設定を削除する。PostgreSQLの場合は、空の共有ビジネスデータベースとオペレーターが選択したログインをプロビューズ/設定する。SQLiteの場合は、自動共有ファイルを使用するか、そのパスを設定する。古いストア/バックアップは復旧の証拠として保持する。
4. 新しいホストを、既存のコアデータベース、通常のファイル、元のマスターキーに対して展開します。プラグインを再インストールし、すべてのインスタンスを再起動します。ホストは、空のプライベートビジネスデータから始めて、各プラグインを共有ビジネスデータベースに自動的に接続します。

アンインストールが失敗した場合は、以前のホストで解決してください。起動時に残存のインストールが拒否された場合は、そのホストに戻ってアンインストールを完了させてください。コアデータベースをリセットしないでください。既に削除された名前空間の履歴は残り、明示的な再インストールによってその生成番号が増加します。0.1.25以前の名前空間の履歴の処理方法は変わらず、古いビジネスデータは読み取られません。残存するコロケーションもあります。 `plugin_<56 hex>` さらに古いバージョンのテーブルはまだレビューが必要であり、自動的に削除されることはありません。

新しい書き込みが行われる前に、未インストール前の状態に復元するには、元のコア/プラグイン/ファイルのバックアップや旧コード/設定を一致させる必要があります。取り消された外部権限の再設定が必要になる場合もあります。新しい書き込みが行われた後は、新しいデータベース/ファイルを保持し、別の復元計画を合意する必要があります。旧バックアップを復元すると、後からのデータが破損する可能性があります。旧ホストはフォーマット3を読み取ることができません。旧ホストと新ホストの混在運用はサポートされていません。

## 検証

`scripts/verify-plugin-database-isolation-upgrade.ts` 実際にリリースされたものと共に、合成された保持コアデータとフォーマット2のプライベートプラグインデータを作成する `smartdoca/doca:0.1.25` 画像。保持されているコア行/宣言を変更せずに拒否を確認し、従来の旧ホストをアンインストールし、同じコアデータベースを再開し、空の共有ストレージに再インストールします。隔離されたSQLiteおよびPostgreSQL 17/18で実行します。管理型ストレージテストでは、プラグイン間の同じ論理名、共有物理ストレージ/プール、再起動、同時実行スコープ、ロールバック、古い世代、欠落したストレージ、再試行可能なクリーンアップも対象です。これらのチェックは、本番環境での展開や混合バージョン操作を確立するものではありません。
