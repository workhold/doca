# 파일 저장 및 업로드

타우리 데스크톱 클라이언트는 선택된 원격 호스트의 스토리지를 사용합니다. 이전의 시도도 마찬가지입니다. `local-v1` 프로필은 열거나 이동시키지 않고 보존됩니다. 보기 [데스크톱 클라이언트](desktop-client.ko.md).

[中文](storage.zh-CN.md)

이 모듈은 아바타, 라이브러리 커버, 문서 이미지 및 첨부파일을 저장합니다. 편집기와 관리자 페이지는 업로드 API를 공유합니다. 문서 본체는 안정적인 자산 ID를 저장합니다. 리소스 어댑터는 권한이 부여된 URL을 해결합니다. 짧은 수명의 CDN 서명은 문서에 저장되지 않습니다.

<a id="environment-configuration"></a>

## 환경 설정

필요한 파일 저장이 선택되었습니다. `DOCA_FILE_STORE_ID` 그리고 `DOCA_FILE_STORES_JSON`두 환경 예시 모두 사용됨 `/data/storage`출시된 컨테이너의 영구 볼륨과 일치하도록 합니다. 소스 개발을 위해 복사하세요. `.env.example` 그리고 로컬 루트를 컴퓨터의 절대 쓰기 가능한 디렉터리로 설정하세요. Compose는 사용합니다. `docker.env.example`데이터베이스는 안정적인 저장 ID와 객체 참조를 기록하며, 백엔드 자격 정보는 포함하지 않습니다. 관리 페이지는 읽기 전용입니다.

```dotenv
DOCA_FILE_STORE_ID=local
DOCA_FILE_STORES_JSON='{"version":1,"stores":{"local":{"provider":"local","root":"/data/storage"}}}'
```

서비스 사용자만이 쓸 수 있고 정적 웹 트리 밖에서만 쓸 수 있는 전용 영구 디렉터리를 사용하세요. 여러 인스턴스는 동일한 물리적 서버를 공유해야 합니다. 백업은 데이터베이스, 모든 참조된 파일 저장소 및 보호된 배포 설정을 포함합니다. 참조된 스토리지 ID는 계속 설정되어야 하며, 물리적 경로나 버킷을 변경해도 바이트는 이동되지 않습니다.

현재의 스타트업은 최신 DDL과 지원되는 데이터베이스 버전을 조정합니다. 지원되지 않는 버전과 퇴출된 데이터베이스 관리 서버 형식은 자동 변환 없이 차단된 상태로 유지됩니다. 기존 배포는 반드시 이 규칙을 따라야 합니다. [데이터베이스 업그레이드 계약](database-schema-evolution.ko.md) 그리고 [출시 요구사항](releases/0.2.23.md)그들의 저장소, 행 번호 및 원본 자격 증명 마스터 키를 보존합니다.

<a id="docker-uploads-fail-with-eacces"></a>

## Docker 업로드가 EACCES로 실패함

만약 `/api/v1/assets` HTTP 500 을 반환하며 컨테이너 로그가 보고됩니다. `EACCES: permission denied, mkdir '/app/data'`활성 지역 매장을 확인하세요. `root` 안에 `DOCA_FILE_STORES_JSON`이 이미지는 작동합니다. `node` 와서 `/app` 작업 디렉터리로서, Compose는 영구 볼륨을 해당 디렉터리에 마운트합니다. `/data`. 개발 루트와 같은 것 `./data/v1/storage` 해결하기로 결정함 `/app/data/v1/storage`그 쓰기 가능한 볼륨 밖에서.

성공적으로 업로드된 파일이 전혀 없는 매장의 경우, 루트를 설정하세요. `/data/storage`동일한 스토어 ID와 모든 다른 스토어 항목을 유지합니다. 애플리케이션 컨테이너만 다시 생성하여 환경 변경을 적용합니다.

```sh
docker compose up -d --no-deps --force-recreate --pull never --no-build doca
```

매장에 이미 파일이 존재하는 경우, 루트를 변경하기 전에 실제 디렉터리와 데이터베이스를 검사하고 백업해야 합니다. 설정된 위치에 있는 객체 바이트와 기존 키를 보존할 계획을 합의한 후, 기존 다운로드와 새로운 업로드를 확인해야 합니다. 설정 변경은 파일을 이동시키지 않습니다. 경로나 권한 오류를 수정하기 위해 데이터 볼륨을 삭제하거나 데이터베이스를 초기화하지 마세요.

## 명명 공간과 접근

호스트가 객체 경로를 생성합니다. `host/`; 플러그인으로 생성된 일반 파일들은 사용됩니다 `plugins/<pluginId>/`개인적인 플러그인 객체와 불변형 설치 ZIP 파일은 별도의 생성/객체 경로를 사용합니다. `host/plugin-releases/<sha256>.zip`사용자 파일명은 물리적 경로를 결정하지 않습니다. 안정적인 파일/폴더 ID와 호스트 권한은 계속 사용됩니다. `GET /api/v1/assets/:id/content` 접근 권한을 확인합니다; 정적 서버 방식으로는 이를 우회할 수 없습니다. 참조하세요. <a id="s3-and-cdn"></a>

## S3와 CDN

매장이 있는 가게 `provider:"s3"` 필요로 함 `bucket`, `region`, `forcePathStyle` 그리고 `credentials:{accessKeyId,secretAccessKey,sessionToken?}` JSON 환경에서. 선택적 `endpoint` 자격 증명, 서브패스, 쿼리 또는 프래그먼트가 없는 HTTP(S) 루트 원본입니다. HTTP는 신뢰할 수 있는 내부 네트워크의 명시적으로 설정된 엔드포인트를 위해 고안되었으며, 애플리케이션은 DNS를 해석하여 목적지를 프라이빗으로 분류하지 않습니다. 운영자는 이러한 목적지와 네트워크 이그레스를 제어하며, 관리 UI를 통해 자격 증명이나 엔드포인트는 설정되지 않습니다. 버킷은 프라이빗 상태로 유지되며, 호스트와 플러그인 프렉시스에 필요한 읽기/쓰기/삭제 작업만 허용됩니다. 설정 검증은 실제 연결성을 증명하지 않습니다.

공유 컨테이너 네트워크에서 RustFS를 사용할 경우, 프라이빗 버킷을 생성하고 그 S3 API 리스너를 설정하세요 (기본 포트) `9000`, 콘솔 포트 `9001`) 경로 스타일 주소 지정 방식으로. 일치 `region` to `RUSTFS_REGION`, 기본값으로 `us-east-1`:

```dotenv
DOCA_FILE_STORE_ID=cloud
DOCA_FILE_STORES_JSON='{"version":1,"stores":{"cloud":{"provider":"s3","bucket":"doca-files","region":"us-east-1","endpoint":"http://rustfs:9000","forcePathStyle":true,"credentials":{"accessKeyId":"replace-me","secretAccessKey":"replace-me"}}}}'
```

Doca 컨테이너에서 접근 가능한 호스트명이나 내부 주소를 사용하세요. 사이트, 자산 및 CDN 원본도 HTTP(S)를 지원합니다. 자세한 내용은… [RustFS S3 문서화](https://docs.rustfs.com/zh/administration/protocols/s3)이 예시는 새로운 설치를 위한 것입니다; 기존 스토어의 엔드포인트를 변경해도 그 객체는 이동되지 않습니다.

선택적 `cdn:{domain,keyPairId,privateKey}` CloudFront 서명된 URL 프로토콜을 사용합니다. OAC과 서명된 URL이 필요한 신뢰할 수 있는 키 그룹을 가진 프라이빗 S3 원본을 설정해야 합니다. CDN은 객체의 전체 키, 콘텐츠 유형 및 처리 방식을 보존해야 합니다. 환경에는 HTTP(S) 배포 원본과 PEM 서명 키가 포함됩니다. 최신 ACL을 확인한 후, 호스트는 60초 동안 유효한 URL을 발행합니다. 폐기 처리는 새로운 링크를 방지하지만, 기존 링크는 만료될 때까지 사용할 수 있습니다. 다운로드된 바이트는 다시 가져올 수 없습니다.

CDN이 없으면 호스트가 개인 클라우드 파일을 프록시합니다. 저장된 비밀 정보는 브라우저로 전송되지 않습니다. 다른 CDN 서명 프로토콜은 어댑터가 필요하며, 영구적인 공개 URL 대체 옵션은 제공되지 않습니다. 모든 참조되는 스토어 ID를 설정해 두고, 자격 증명을 교체할 때 그 바이트에 대한 접근 권한을 유지해야 합니다. 이는 데이터 마이그레이션이 아닙니다.

<a id="browser-image-caching-and-the-file-cdn"></a>

## 브라우저 이미지 캐싱 및 파일 CDN

문서/코멘트 이미지, 어시스턴트 이미지 및 호스트 프로킷드 아바타/커버는 안정적인 상태를 사용합니다. `/api/v1/assets/:id/content` URL. 스크린샷을 포함한 성공적인 인라인 이미지 응답은 다음과 같이 전송됩니다:

```http
Cache-Control: private, max-age=3600, must-revalidate
Vary: Cookie, Authorization
ETag: W/"object-and-variant-identity-digest"
```

브라우저는 1시간 동안 로컬 사본을 재사용할 수 있습니다. 일단 유효성이 없어지면 `If-None-Match` 재검증합니다: 호스트는 반환하기 전에 현재 접근 권한을 확인합니다. `304` 이미지 바이트가 없음. 원본과 축소판은 다른 ETag를 가짐. 객체 키는 불변이며, 이미지를 교체하려면 새로운 자산이 필요함. 쿠키/인증 설정 변경 시 계정을 전환할 때 별도의 캐시된 응답이 선택됨. 유효성 검사 과정에서 취소는 다시 확인되지 않으며, 다운로드된 바이트는 되돌릴 수 없음. 브라우저는 항목을 삭제할 수 있으며, 재로드/DevTools를 강제로 실행할 수 있음. **캐시를 비활성화** 그들을 우회할 수 있습니다. 이 방식은 추가적인 IndexedDB나 Service Worker를 사용하지 않고 HTTP 캐싱을 활용합니다. 보기 [MDN HTTP 캐싱](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching) 재검증을 위한 것과 비교 `no-store`.

이미지가 없는 AI 첨부 파일 `download=1`쓰레기 같은 예고편과 오류가 남아 있음 `no-store`무단 요청은 얻을 수 없다. `304` 알려진 ETag가 있습니다. 문서 이미지에는 resourceId가 있으며, S3 파일 CDN이 설정되어 있더라도 여전히 호스트 프록시 뒤에 남아 있습니다. 어시스턴트 이미지도 마찬가지로 호스트 프록시 뒤에 남습니다. 생성된 이미지 카드와 인라인 어시스턴트 이미지는 기존의 480픽셀 WebP 축소 이미지를 요청합니다; 이 이미지를 클릭하면 원본이 표시되며, 다운로드도 원본 바이트를 그대로 유지합니다. 비동기적인 축소 이미지 작업이 대기 중이거나 사용할 수 없을 때는 인라인 이미지가 원본을 표시할 수 있습니다.

서명된 파일-CDN 리디렉션이 유지됨 `no-store` 따라서 브라우저는 만료된 60초 기간의 서명을 재사용하지 않습니다. 최종 파일 응답 헤더는 CDN 또는 S3 원본에 있어야 하며, 리디렉션 헤더는 전달되지 않습니다. 현재 새로운 S3 객체는... `Cache-Control: private, max-age=60`; 이 변경은 기존 객체를 다시 작성하지 않습니다.

CloudFront 개인 파일 동작에 대해서는 개인용 S3 원본/OAC, 신뢰할 수 있는 키 그룹 및 60초의 서명 기간을 유지하세요. 설정하세요. **응답 헤더 정책 → 사용자 정의 헤더** to `Cache-Control: private, max-age=60, must-revalidate` 와서 **오버라이드** 기존 및 새로운 객체에 대한 브라우저 응답을 표준화합니다. 사용하세요. **캐싱비활성화** 별도로 에지 캐싱이 계획되지 않았다면, 사용자 정의 정책은 최소 TTL을 0로 설정해야 합니다. 양수의 최소 값은 원본 서버의 설정을 무효화할 수 있습니다. `private/no-store`응답 헤더 정책은 엣지 TTL과는 독립적으로 브라우저에 전달되는 응답에 영향을 미칩니다. 자세한 내용은 AWS 문서를 참조하세요. [응답 헤더 정책](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/modifying-response-headers.html), [캐시 정책 TTL](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cache-key-understand-cache-policy.html) 그리고 [서명된 URL](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html)사이트에 공개적인 장기 저장 캐싱을 절대 적용하지 마세요. `/api/*`.

서명 관련 쿼리 매개변수를 변경하면 다른 브라우저 URL이 생성됩니다. 헤더만 추가해도 서명 간에 재사용이 보장되지 않습니다. 안정적인 문서 이미지 URL은 이러한 제한을 피할 수 있습니다. Edge-캐시 접근과 브라우저-캐시 접근은 별개의 측정값입니다.

수락을 위해서는 DevTools를 끄세요. **캐시를 비활성화**문서를 다시 검토하고 메모리/디스크 캐시 접근을 확인하세요. 조건부 읽기가 무응답을 반환하는지 확인하세요. `304`그런 다음 로그아웃, 권한 거부, 미니아트, 다운로드 및 휴지 예약 미리보기를 확인하세요. 최종 CDN 응답과 리디렉션도 살펴보세요. 쿠키와 서명된 URL은 공개 로그에 저장하지 마세요.

```sh
curl -I -H 'Cookie: doca_session=<session>' https://doca.example.com/api/v1/assets/<asset-id>/content
curl -I -H 'Cookie: doca_session=<session>' -H 'If-None-Match: W/"<first-response-digest>"' https://doca.example.com/api/v1/assets/<asset-id>/content
curl -I 'https://files.example.com/<object-key>?<valid-signature-parameters>'
```

해시된 공개 JS/CSS에는 별도의 1년간 정책이 필요합니다. [배포: 정적 자산](deployment.ko.md#static-assets).

<a id="history-storage-and-offline-upgrade"></a>

## 역사 저장 및 오프라인 업그레이드

데이터베이스는 최신 20개의 전체 비즈니스 스냅샷을 보관합니다. 각 10개로 구성된 이전 스냅샷 그룹은 설정된 파일 저장소(예: S3가 설정된 경우 클라우드 저장소)에서 가장 최신 점을 유지합니다. 한 점은 체크포인트와 독립적인 복구 메타데이터를 포함한 gzip JSON 파일로, 작은 데이터베이스 인덱스가 포함되어 있습니다. 불변적인 업로드와 SHA-256 읽기 성공만이 원자적 인덱스 커밋 및 10개의 데이터베이스 행 제거를 허용하며, 나머지 9개의 점은 의도적으로 샘플링되어 복구할 수 없습니다. 불완전한 그룹과 저장소 장애는 데이터베이스 원본을 유지합니다. 일반적인 페이지화된 목록은 저장소 유형, 객체 키 또는 서명된 URL을 노출하지 않으면서 두 소스의 데이터를 결합합니다.

실시간 체크포인트, 발견된 공동 작업 증분 및 첨부 파일은 샘플링되지 않습니다. 트래시는 역사를 보존하며, 명시적인 영구 리소스 삭제 큐는 한 시간 후의 재활용 및 재검토를 저장합니다. 오래된 recovery_json은 새로운 스키마로 디코딩되지 않거나 현재 기준선으로 채워지지 않습니다. 누락된 복구 메타데이터와 알 수 없는 복구 버전은 여전히 미리보기를 거부합니다. 파일은 envelope v1, 일치하는 해시, 제한된 압축 해제 및 인덱스 합의가 필요합니다. 백그라운드 내구성 있는 작업은 콘텐츠 커밋을 방해하지 않고 실패를 재시도합니다.

현재 세대는 `doca-2026-10-12-book-payload-storage-v1`다음 역사적 유지보수 단계는 정확한 경우에만 적용됩니다. `doca-2026-10-08-knowledge-books-v2` 데이터베이스 (0.1.13 버전 출시): 처음으로 기록됨 `doca-2026-10-09-history-storage-v1`그 후 현재의 시작 프로세스가 승인된 구조 정렬 작업을 수행할 수 있습니다. 모든 호스트를 중단하고 데이터베이스, 파일 저장소 및 설정 정보를 백업한 다음 마스터 키를 보관한 후 다음 명령을 실행합니다:

```sh
pnpm history:upgrade                 # Show requirements; no mutation
pnpm history:upgrade --apply         # Add structure, update baseline and queue work; no immediate sampling
```

업그레이드를 하지 않고 데이터베이스를 재구축하지 마세요. 실패한 업그레이드 트랜잭션은 원래의 데이터베이스를 유지합니다. 직접적인 역사 롤백은 오직...만 허용됩니다. `doca-2026-10-09-history-storage-v1` 또는 전용 중단된 롤백 마커를 사용하되, 현재의 책-페이로드 생성은 아닙니다. 최신 세대 데이터베이스의 경우, 먼저 검토해야 합니다. [책 저장소 복구](knowledge-book-storage-verification.ko.md)저장된 체크포인트 참조는 이전의 롤백을 방해할 수 있습니다. 유효성 검사를 우회하기 위해 기준점을 재라벨링하지 마세요. 자격을 갖춘 역사 생성 데이터베이스의 경우, 보존된 점을 가져오기 전에 모든 인스턴스를 중단하세요.

```sh
pnpm history:rollback --apply --manifest /backup/history-cloud-references.json
```

매니페스트는 새로운 파일이어야 하며 0600 모드로 작성됩니다. 롤백은 클라우드 참조를 저장하고 보존된 포인트를 검증 및 가져온 후 이전 기준으로 돌아갑니다; 클라우드 파일은 보존됩니다. 중단된 롤백은 호스트 시작을 거부하는 전용 마커를 사용하여 가져온 포인트가 다시 샘플링되는 것을 방지합니다. 저장 문제를 해결하고 새로운 매니페스트 경로로 롤백을 다시 실행하세요. 샘플링된 포인트는 완전한 사전 샘플링 데이터베이스 백업이 필요합니다. 사용자 접근용 복원은 현재 에포크, 권한 및 예상Seq 검사를 적용하지만; 서식 있는 텍스트 및 Markdown 복원은 다른 형식은 미리보기 전용으로 유지됩니다.

## 검사 및 권한 확인

- 아바타와 커버는 최대 5MB입니다. PNG, JPEG, WebP, GIF는 파일 헤더를 통해 인식되어 디코딩됩니다. 제한은 2,500만 픽셀입니다. 메타데이터는 제거되고 이미지는 WebP 형식으로 저장됩니다. 아바타는 최대 512px 크기의 정사각형으로 잘려 있습니다. 커버는 최대 1,600px 너비로 됩니다. GIF는 첫 번째 프레임을 유지합니다.
- 문서/AI 첨부파일 업로드 크기는 최대 20 MiB이며 원본 바이트를 보존합니다. 인식된 래스터 이미지는 2500만 픽셀 제한으로 검증됩니다. 아바타/커버/코멘트 이미지 경로는 목적에 맞게 WebP 형식으로 정규화됩니다. 일반 사용자 파일은 2 GiB 제한이 있는 별도의 스트리밍 업로드 API를 사용합니다. SVG와 HTML은 실행 가능한 이미지로 인라인되지 않습니다. 일반 파일은 첨부파일로 제공됩니다. `nosniff` 그리고 샌드박스도 있습니다. 바이러스 스캔 기능은 없습니다.
- 최대 4개의 동시 업로드가 가능하며, 사용자당 10분에 60번의 시도가 허용됩니다. API는 최근 업로드 기록도 확인합니다. 리버스 프록시는 자체적인 바디 크기, 연결 및 저장 제한을 추가해야 합니다. 아직 사용자별 디스크 할당량은 없습니다.
- 아바타 초안은 업로드자가만 읽을 수 있습니다. 이 초안이 바인딩되면 사이트에 로그인한 사용자들이 볼 수 있습니다. 익명 사용자는 볼 수 없습니다. 커버는 라이브러리 ACL을 따릅니다. 바인딩되지 않은 커버 초안은 업로드자가만 읽을 수 있습니다. 첨부파일은 문서 ACL을 따릅니다. 시스템 관리자는 추가적인 읽기 권한이 없습니다. 커버는 관리자가 필요합니다. 첨부파일은 편집자가 필요합니다.
- 객체가 먼저 기록됩니다. 그 후 트랜잭션이 사용자와 리소스의 권한을 다시 확인하고 자산을 기록합니다. 기록에 실패하면 미완료된 객체는 가능한 경우 삭제됩니다. 커버 편집은 리소스 버전을 사용하고, 아바타 편집은 프로필 버전을 사용합니다.
- 완성되었지만 아직 연결되지 않은 아바타와 커버 드래프트는 현재 보관되어 있습니다. 자산 드래프트 정리, 사용자별 할당량, 바이러스 스캔 작업은 아직 완료되지 않았습니다. 일반 사용자 파일 업로드는 32 MiB부터 8 MiB 단위의 여러 부분으로 구성된 S3 멀티파트 지원을 제공하며, 이는 제한된 자산 엔드포인트와는 별개입니다. 충돌로 인해 등록되지 않은 객체가 남을 수 있으므로, 정리 작업 시 모든 자산 참조를 확인해야 합니다. 한 문서가 삭제된다고 해서 공유된 객체를 삭제하지 마십시오.
