## Автоматическое обновление при запуске в версии 0.1.24

Остановите все старые хосты и сделайте резервную копию SQL, приватного хранилища и конфигурации. Начиная с версии 0.1.24 после выпуска версии 0.1.22. `doca-2026-10-09-history-storage-v1` Автоматически сравнивается весь схема с текущим DDL. Когда план проходит проверку, транзакция блокировки схемы согласовывает объявленные добавления и записывает целевое создание. Каждый бизнес-строка и указатель публикации остается нетронутым, включая старые результаты, генерированные SQL, запуски и человеческие задачи. Существующие данные объектов версии 0.1.23 сохраняются без изменений. Не требуется ручной команды для обработки, не нужно отдельное очищение, автоматиченая конвертация или использование старого рендер-программного обеспечения. Остатки старых результатов могут требовать ручной обработки перед тем, как они станут пригодными для использования.

Все изменения в структуре/генерации откатываются при ошибке. Повторные/конкурирующие запуски сохраняют все строки. Неизвестные, ранее существовавшие и прерванные генерации останавливаются без изменения данных; не связанные неизвестные таблицы все равно требуют проверки. Сохранять все данные и записи после обновления во время восстановления резервных копий. Обновлять все хост- и веб-инстансы одновременно.

Существующие команды обслуживания остаются опциональными, если необходимо сохранить старые результаты в пригодном нативном формате. Выполните обновление перед первым запуском; схема изменяет процесс генерации исходных данных. Проверка исторических данных показывает, что речь идет о опциональной конвертации, а не о автоматической адаптации оставшегося SQL JSON.

Доказательства автоматического выравнивания: фактически выпущенная версия 0.1.22 фиксированных данных для SQLite/PostgreSQL 17/18 сохраняет каждую строку из 114 бизнес-таблиц и все 20 SQL-объектов; новые нативные объекты остаются читаемыми после многократного/конкурирующего запуска. PostgreSQL 17/18 прошли 91 тест на регрессию, включая откат и строгое отклонение старых SQL-объектов. См. [проверка](verification/book-schema-startup-2026-10-13/verification.json).

## Команды по обслуживанию

Используйте новую версию хоста, содержащую эти изменения и существующую среду развертывания. Опубликовано. `smartdoca/doca:0.1.22` Это источник конвертации и не содержит нового команды. Остановите все хосты и сделайте резервную копию SQL (включая SQLite WAL), приватных объектов и конфигурации. Сохраните оригинальный мастер-ключ, сохраните идентификаторы и конфигурацию backend. Обновите все хосты и веб-сборки одновременно.

Команда открывает существующую базу данных без инициализации. По умолчанию используется полный читовый режим предварительного анализа. Применение требует `--apply --hosts-stopped` И также новый путь для восстановления манифеста. Манифесты используют режим 0600 и сохраняют оригинальную структуру, идентификационные данные владельцев, размеры и хеш-коды без отражения содержимого.

```sh
pnpm knowledge-books:storage upgrade
pnpm knowledge-books:storage upgrade --apply --hosts-stopped --manifest /secure/book-upgrade.json
```

Только `doca-2026-10-09-history-storage-v1` Принимается. Предыдущие версии должны сначала завершить конвертацию истории, поддерживаемой системой. Выполняются задачи с книгами, неизвестные форматы данных, поврежденные данные и конвертация блоков с необходимыми проверками структуры без частичных записей. Решается конкретные проблемы, а не отменяются неизвестные задачи, создание исторических полей или очистка SQL.

После прерывания обычный запуск отклоняет генерацию прогресса. Повторите тот же команду с тем же путем манифеста. Преобразованные байты должны соответствовать этому манифесту; замена манифеста не позволяет обойти измененные данные. По завершении запуск принимает только `doca-2026-10-12-book-payload-storage-v1`Независимое сердцебиение приводит в порядок оставшиеся уведомления после запуска; завершенные исторические задачи не восстанавливаются. Исторические результаты и ошибки сохраняются.

Текущий процесс откатки отклоняет непустые данные. `knowledge_book_batch_checkpoints` До модификации: их ссылки требуют отдельно утвержденного плана сохранения/восстановления. Не удаляйте контрольные точки и не обходите проверки генерации/структуры. Смотрите [Сохранение и восстановление контрольной точки](knowledge-book-generation-performance.ru.md#deployment-retention-and-recovery)Историческое путешествие в обратном направлении доходит до периода контрольных точек и не проверяет произвольные снижения версии с текущей до 0.1.22.

Завершите работу со всеми хостами для возможности возврата к предыдущему состоянию, сохраните новый манифест резервного копирования и восстановления. Проведите предварительную проверку каждого объекта и подтвердите его оригинальные байты. Возврат к предыдущему состоянию также восстанавливает записи, сделанные после обновления, и сохраняет объекты в облаке и материалы для восстановления.

```sh
pnpm knowledge-books:storage rollback
pnpm knowledge-books:storage rollback --apply --hosts-stopped --manifest /secure/book-rollback.json
```

Прерванный процесс возврата данных возобновляется с первоначальным манифестом. После восстановления и проверки все данные в формате JSON восстанавливаются, а только четыре таблицы, связанные с хранением данных, удаляются, а отмечается размер файла и информация о старой версии данных. Цель – предыдущая версия хоста 0.1.22. Полный процесс возврата данных происходит до любого дополнительного процесса возврата более старых данных. Освобожденные страницы SQLite не автоматически уменьшают размер файла; процедура VACUUM также не выполняется.

<a id="operational-boundaries"></a>

## Операционные границы

Приватная локальная/S3 конфигурация ведущего используется повторно без публичных URL-адресов или учетных данных, принадлежащих модулям. Бэкап SQL и объектов выполняется в единой структуре. Отсутствующие или поврежденные объекты отказываются от обработки, при этом сохраняются ссылки на них; пустые объекты никогда не могут заменить недоступный контент.

Очистка удаляет только недоступные объекты. Компоненты “Куча” сохраняют ссылки; постоянная очистка отбрасывает их. Зависимости, связанные с живым загрузкой, защищены, а неудачные или запоздалые загрузки сохраняют долговые ключи для повторных попыток. Завершенные журналы сохраняют только те параллельные физические загрузки, которые потеряны, в то время как установленные зависимости остаются в объектах и ребрах. Никакой исторический TTL не добавляется.

Финальная проверка: сборка 126-ситуационных модулей для SQLite прошла, за ней следует сборка 60-ситуационных модулей для книг/пayload после окончательной проверки конечных точек и разрешений. Обе сборки 68-ситуационных модулей для PostgreSQL 17/18 прошли, а также финальные 11-ситуационные модули для payload прошли на обоих движках. Проверки типов, разработка веб-сайта, ссылки на документацию и проверки пробелов в тексте также прошли. Смотрите. `docs/verification/knowledge-book-storage-plan-2026-10-12/verification.json`Сердцебиение и очистка объектов используют независимое расписание, так что запросы в облаке не занимают время для согласования сердцебиения.
