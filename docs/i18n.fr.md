# Langues d’interface

Doca 0.3.0 prend en charge huit langues d’interface. Chaque langue possède son catalogue de messages et utilise les mêmes clés stables en anglais. Le [contrat d’origine en anglais](https://github.com/workhold/doca/blob/main/docs/i18n.md) décrit les règles appliquées par le projet et les éditeurs.

<a id="language-codes"></a>

## Codes de langue

| Code | Langue | `html lang` |
| --- | --- | --- |
| `zh` | Chinois simplifié | `zh-CN` |
| `en` | Anglais | `en` |
| `zh-Hant` | Chinois traditionnel | `zh-Hant` |
| `ja` | Japonais | `ja` |
| `fr` | Français | `fr` |
| `ko` | Coréen | `ko` |
| `es` | Espagnol | `es` |
| `ru` | Russe | `ru` |

Le chinois simplifié est la langue initiale du site. L’administrateur peut modifier la langue par défaut. Les visiteurs et les utilisateurs sans préférence `ui.locale` voient la langue du site. La préférence enregistrée dans le compte est prioritaire.

Les écritures via l’API exigent un code canonique du tableau. Lors de la résolution des langues régionales ou système, `zh-TW`, `zh-HK`, `zh-MO` et `zh-Hant` désignent le chinois traditionnel. Pour les autres langues prises en charge, seul le sous-code de langue principal est utilisé. Une valeur enregistrée inconnue laisse l’espace de travail utiliser la langue par défaut du site.

Le choix du compte est enregistré dans l’état de page `ui.locale`. Le client Web conserve également `doca.locale` dans `localStorage`, et le client mobile enregistre la préférence sur l’appareil. L’assistant peut modifier `ui.locale` via la fonction existante `page_state`.

À chaque chargement, l’écran de connexion Web utilise d’abord la langue définie par l’administrateur. Le sélecteur applique immédiatement la langue choisie pour la visite en cours. Après la connexion, la préférence du compte et la langue par défaut du site déterminent la langue de l’espace de travail.

<a id="host-catalog"></a>

## Catálogo des hôtes

Les catalogues sont disponibles `packages/i18n`. Le catalogue en anglais `en` C’est la source des clés. Toutes les autres langues doivent couvrir exactement les mêmes clés.

```ts
t("account.expires", { date })
// en: Expires {date}
// zh: 到期时间：{date}
```

- Les clés sont des lettres anglaises en minuscules avec des points, regroupées par zone, par exemple `nav.trash` et `settings.language`.
- Les placeholders sont `{name}`Ne divisez pas une phrase et ne concaténez pas les parties.
- Les pluriels sont utilisés `files.count.one` et `files.count.other`L'appel est encore en cours `t("files.count", { count })`L’anglais utilise `one` quand `count === 1` et `other` Sinon. Les Chinois peuvent utiliser la même phrase pour les deux.
- Une traduction manquante utilise l’anglais, puis la clé elle-même.
- Utilisez le nom propre de chaque langue dans les sélecteurs. Les labels natifs proviennent de `localeNames`.
- Dates et tri `Intl` pour l’étiquette de langue active.
- Les titres de documents, le texte intérieur, les commentaires, les e-mails, les noms de fichiers et les entrées utilisateur ne sont pas traduits.

L’application web utilise `useI18n()` pour `locale`, `t`, et `setLocale`. Ant Design et Ant Design X suivent cette tendance `locale`. Le bureau et les appareils mobiles utilisent les catalogues hôte. L’extension de navigateur conserve sa langue pour ce navigateur. Les contributions utilisant le contrat de plugin bilingue utilisent son champ en anglais dans les six nouvelles langues.

Les erreurs de serveur visibles par l’utilisateur, non codées, sont toujours des phrases en chinois. Les nouvelles erreurs de validation utilisent un code stable, comme `invalid_locale`Et l’interface le traduit. Les erreurs des API existantes ne sont pas toutes converties dans cette version.

La nouvelle génération d’images par l’IA, la connexion des modèles et les erreurs des travailleurs utilisent un enveloppe de présentation explicite, serialisée dans les champs de texte d’erreur existants :

```ts
{ type: "system_error", version: 1, code: "image_edit_failed", data: { status: 422 } }
```

Seuls les erreurs de système nouvellement produites et explicitement codées utilisent ce format. Le texte d’erreur historique, les messages, les résultats des outils, les raisonnements et le contexte du prompt stocké sont lus littéralement ; ne les scannez, ne les traduisez, ne les convertissez ni ne les migrez. Les erreurs non taguées restent inchangées. Le web et les appareils mobiles partagent… `systemErrorMessage` lecteur `@doca/i18n`Les erreurs liées aux tâches marquées sont utilisées `useI18n().t`Les nouveaux erreurs HTTP utilisent le système de localisation choisi par le même fournisseur. Les codes inconnus affichent une erreur générique cataloguée, tandis que les envois mal formés ou non supportés restent inchangés.

`AppError.message` Et la serialisation des erreurs face au modèle reste inchangée. Les métadonnées de présentation se trouvent en dehors de l’objet d’erreur, dans un WeakMap. Les points de contrôle liés à l’échec de l’image portent une raison structurée distincte, afin que l’échec ultérieur de la tâche puisse être affiché sans modifier les réponses canoniques du outil. Le langage de l’interface ne est jamais ajouté au message système, aux définitions d’outil ou à l’histoire rejouée, ce qui préserve le préfixe du modèle en cache lorsque l’utilisateur change de langue.

C’est la politique de lecture convenue pour les anciens textes plain et les nouveaux erreurs codées ; il n’y a pas de migration de données historiques ou de schémas de base de données. Un rollback doit empêcher toute nouvelle écriture dans l’enveloppe tout en conservant le lecteur d’enveloppe et tous les données stockées.

<a id="persisted-system-state"></a>

## État du système persistant

Les bases de données, les points de contrôle des tâches, les flux d’événements et les réponses de l’API stockent des codes anglais stables et des paramètres structurés. Ils ne stockent pas de phrase de présentation dans une langue quelconque. Les applications web et mobiles transforment le code en titre, description et nom de phase conformément au catalogue actuel.

```ts
{ code: "folder_available", data: { name: "Research" } }
t("ai.progress.event.folderAvailable", { name: event.data.name })
```

Les phases, les événements, les approbations et les raisons d’erreur stockés en tant que statut suivent cette règle. Comparez les codes, par exemple `phase === "completed"`Ne comparez pas le résultat. `t(...)` Ou une étiquette en chinois ou en anglais. Les entrées utilisateur, les réponses du modèle, les titres de documents, les noms de fichiers et les sources web restent tels qu’ils sont. Ne réécrivez pas le contenu naturel en code.

<a id="editor-subpackages"></a>

## Sous-pakages éditeur

Un sous-package éditeur conserve sa propre copie d’interface. Il ne charge pas le catalogue de Doca ni ne lit l’état des pages de Doca.

Le présentateur passe :

```tsx
<RichTextEditor locale={locale} />
```

`locale` C’est une chaîne de caractères. Les éditeurs installés acceptent les huit codes de la table. Une locale de paquet non reconnue se tourne vers l’anglais.

1. Ajouter un optionnel `locale?: string`. Lorsqu’il est omis, affichez `zh`, en correspondance avec l’interface chinoise actuelle.
2. Les clés sont des identifiants anglais stables tels que `toolbar.bold` et `find.replaceAll`.
3. Fournir un catalogue complet des mêmes clés pour chaque langue pris en charge.
4. Les placeholders sont `{name}`. Les comptes utilisent `key.one` et `key.other`, sélectionné par `count`.
5. Changer `locale` Mettre à jour les boutons, les menus, les placeholders et les indications. Il ne reconstruit pas le document, le Y.Doc, l’adaptateur de collaboration ou la liste des plugins.
6. Optionnel `messages?: Record<string, string>` Peut annuler les traductions individuelles. Les clés manquantes utilisent toujours la traduction intégrée.
7. Le texte, les formules et les valeurs de cellule que l’utilisateur a écrits dans le document ne sont pas traduits.

Après que les types du paquet installé incluent `locale`, l’animateur passe la situation actuelle `locale` au site de montage. Ne le placez pas `locale` Dans une dépendance qui reconstruit le document, Y.Doc, l’adaptateur de collaboration ou la liste des plugins.

<a id="add-a-language"></a>

## Ajouter une langue

1. Ajouter le code à `locales`, et le `html lang` valeur.
2. Ajoutez un catalogue d'hôtes avec exactement les clés en anglais.
3. Ajoutez le nom de la langue elle-même, par exemple `locale.ja`.
4. Ajoutez le locale Ant Design correspondant dans l’application web.
5. Ajoutez le même catalogue de langues dans chaque sous-package éditeur.
6. `ui.locale` Accepte le nouveau code, car la validation donne le même résultat. `locales` liste.
