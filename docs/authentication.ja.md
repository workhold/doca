# 認証、登録承認、アカウント連携

リモート専用デスクトップクライアントは、有効期限のない、ブラウザで承認された別のホスト認証情報を追加します。詳細は [デスクトップクライアント契約](desktop-client.ja.md)既存のブラウザ/モバイルセッションは、その有効期限と保存規則を維持します。

[中文](authentication.zh-CN.md)

これは、スペースも組織ツリーもない現在のDocaに適用されます。ローカルアカウント、外部のIDプロバイダ、登録承認、およびログイン方法の切り替えを含みます。

<a id="boundary"></a>

## 境界

1人のDocaユーザーは複数のログインアイデンティティをリンクできます。文書、権限、アバター、設定は常に安定して存在します。 `users.id`アカウントはメール、表示名、電話番号で統合されません。本人は元のアカウントにログインし、新しい身元を意図的にリンクさせます。

この設計では、プロフィールデータとログイン情報を分離し、暗黙のメール照合ではなく明示的なリンクを使用しています。アカウントの作成と有効化は別々であり、保留中のレビュー状態が可能です。既存のアカウントは他の認証サービスに移行されることはなく、Docaは外部のAuthentikサービスに依存していません。

管理者は自分専用のフルページシェルを使用する：ナビゲーション、スクロール領域、そしてワークスペースへの戻り方。アカウント設定には独自のナビゲーションが用いられる。視覚言語はDocaのものが保持される。

<a id="three-registration-policies"></a>

## 3つの登録ポリシー

「Admin」「Sign-in and registration」の下で、各項目は別々に設定されます。

| エントリー | 新規ユーザーはいない | 自動登録 | 承認が必要 |
| --- | --- | --- | --- |
| サイトパスワード | 登録は終了しました | 登録後にサインインできます | 保留中のユーザーが作成されました |
| エンタープライズOIDC | 既にリンクされたアイデンティティのみがログインできます | 最初のログインでユーザーが作成されます | 最初のログインにより、保留中のユーザーが作成されます |
| Google、GitHub、WeChat、QQ | 既にリンクされたアイデンティティのみがログインできます | 最初のログインでユーザーが作成されます | 最初のログインにより、保留中のユーザーが作成されます |

既にリンクが設定されているアクティブユーザーは「閉鎖された登録」によってブロックされず、別のアイデンティティをリンクすることも可能です。管理者が作成したユーザーは即座にアクティブになります。保留中のユーザーにはサイトセッションがなく、文書やWebSocketを開くことができません。管理者は専用の登録審査ページを使用して承認または拒否を行います。通常のユーザーの有効/無効設定では保留中のアカウントを承認することはできません。承認後、その人は再びログインします。古い承認フローは有効になりません。

外部登録およびすべてのIDプロバイダは無効になっています。パスワード入力は利用可能であり、IDプロバイダの障害が管理者をロックすることはありません。連絡確認、電話コードログイン、パスワード復元機能が存在します。コード送信と試行制限は共有データベースを使用します。パスワードログインおよび公開ボットのIP制限は、Redisが設定されている場合はRedisや共有カウンターを使用せず、プロセスローカルカウンターを使用します。SMSには独自のアドミニストレーションロールがあり、第三者ソースがカテゴリポリシーを無効にすることができます。

サインイン方法が変更されると、サーバーはすべてのアクティブなユーザーと管理者を、有効な方法、確認済みの連絡先、パスワード識別子、プロバイダの認証情報と照合します。変更後に利用可能な方法がない場合、保存は拒否されます。管理者は「ユーザーにサインイン方法の追加を要求する」項目から新しい方法を選択できます。その後、ユーザーがサイトを開く際には、確認またはリンクを行う必要があります。全員が完了した後にのみ、古い方法は閉じられます。方法の追加はデフォルトでは必須ではありません。

<a id="identity-providers"></a>

## アイデンティティプロバイダー

- **OIDC SSO。** 標準的なディスカバリー、例えばKeycloakやauthentikです。 `openid-client` 6.8.8、認可コードとPKCE S256、状態、nonce、IDトークンの署名チェック、および発行者、視聴者、有効期間のチェック。クライアント認証は `client_secret_post`プライベートキーのJWT、mTLS、SAMLはサポートされていません。単純なOAuth 2はOIDC設定ではありません。
- **Google。** 修正済み、発見済み `https://accounts.google.com`、範囲 `openid profile`出典がメールを宣言したら、メールも送ってください。
- **GitHub。** 認可コードに加えてPKCE S256 `read:user`安定した数値IDはこれから得られる `/user`メールが送信されるとき、 `user:email` 確認されたメールアドレスを読みます。
- **WeChat。** ウェブサイトQRコード `snsapi_login`バインディングではApp IDの下でOpenIDを使用します。UnionIDはアカウントを統合しません。これは公式アカウントのページ、ミニプログラム、またはモバイルアプリのログインではありません。
- **QQ.** ウェブサイトOAuth。トークンと `me` JSONを使用すると、プロファイルが読み込まれます。 `me.client_id` 設定と一致する必要があります。

WeChatとQQのアダプターは、シミュレーションされた応答を用いて実装・テストされています。これらは実際のプラットフォームでは受け入れられません。すべての外部プロバイダは、そのプラットフォームからアプリケーションと認証情報が必要です。このフローにおけるWeChatとQQはPKCEを送信せず、OIDC PKCEと同等ではありません。

DocaはSSOクライアントのみです。OIDCプロバイダーとしての機能は提供されますが、SAMLやグローバルSSOログアウトや取り消しの同期機能は実装されていません。IDプロバイダーでのアカウントの無効化によって、既に発行されたDocaセッションは取り消されません。ブラウザセッションのデフォルトは24時間ですが、設定可能です。 [ログイン期間](configuration.ja.md#login-lifetime)既存のセッションは保存された有効期限を維持します。サイト管理者がユーザーを無効にするか、後続のIdPのライフサイクルイベントが必要です。

<a id="deployment"></a>

## デプロイ

1. 各プラットフォームで申請を登録してください。設定されたHTTP(S)を使用してください。 `DOCA_ORIGIN`プロキシは設定されたホストを保持します。
2. 「プラットフォーム設定」の「サービス認証情報」の「SSO」セクションに、認証情報名とクライアントシークレットを追加し、許可されるカスタムSSOオリジンを設定します。このシークレットはデータベースに保存され、保存時に有効になり、再表示されません。
3. IDプロバイダを追加する：表示名、OIDC用の発行者、クライアントまたはアプリID、および認証情報IDを指定します。有効化を解除し、保存して、コールバックURLをコピーします。
4. そのURLをプラットフォームの許可リストに正確に追加してください。 `https://doca.example.com/api/v1/auth/providers/<UUID>/callback`各プロバイダーには独自のURLがあります。任意の返信URLは受け付けられません。
5. 登録ポリシーを設定し、プロバイダを有効にします。プロフィールページからリンクするかログアウトし、サインインをテストします。うまくいくまで、元の管理者方法を使用し続けます。

Google、GitHub、WeChat、QQのHTTPSホストはデフォルトで許可されています。OIDC発行者内の各ホスト、およびディスカバリーによって返される認可、トークン、JWKS URLでは、1行につき1つの完全なオリジンとして、カスタムSSO許可オリジンにリストされる必要があります。リダイレクトは禁止されています。明示的に許可リストに載っている自ホスト型プロバイダはHTTPを使用できます。OIDCではこの場合、HTTPディスカバリーやエンドポイントも許可されます。運用者は許可リストとエグレスポリシーを共に管理します。変更可能で信頼できないDNSや任意のプライベートアドレスを信頼しないでください。

タイプ、発行者、クライアントIDは不変の名前空間です。新しい発行者やアプリケーションは新しいプロバイダーとなります。ユーザーが自らそれにリンクします。古いIDを別のプロバイダーに使わないでください。名前、認証ID、有効状態はバージョンオプティミスティックロックを使用し、古い認可フローを無効化します。プロバイダーを無効にすると、そのソースしか持っていないユーザーがログインできなくなります。まず別のリンクを設定してください。管理者が古い方法を置き換え、「ユーザーにログイン方法の追加を要求する」と設定しない限り、新しいログイン方法は強制されません。

<a id="security-flow"></a>

## セキュリティフロー

1. 同じオリジンからのPOSTは、ランダムな状態、ブラウザの認証情報、ノンス、PKCE検証器で処理を開始します。リンクの設定により、管理者が設定した個別のセキュリティチェックが完了します。その認証情報は5分間のみ使用可能です。
2. サーバーには、状態のハッシュ、ブラウザの認証情報、そして10分間のフローが保存されます。フロークッキーはHttpOnlyであり、SameSite=Laxです。メインクッキーはHttpOnlyであり、SameSite=Strictで、HTTPSではSecureになっています。
3. コールバックではプロバイダー、状態、ブラウザの認証情報を確認し、フローを一度実行し、アイデンティティを検証します。ログにはコールバックのクエリパラメータ、コード、トークン、またはプロバイダーのエラーベースを記録しません。
4. ブラウザがリダイレクトされます `/#/auth/complete`同じオリジンからのPOSTが完了し、厳格なセッションが復元されます。リンクは依然として、それを開始したユーザーとセッションであり、セキュリティチェック用の認証情報も有効でなければなりません。
5. トランザクションはフローを消費し、プロバイダのバージョン、一意な識別子の所有権、登録ポリシー、およびユーザー状態をチェックします。Pending状態ではセッションは発行されません。Active状態ではDocaセッションのみが発行されます。

第三者のアクセス用および更新トークンは保存されません。対象、当時の表示名、およびリンクのメタデータが保存されます。ソース側で指定されたHTTP(S)アバターURLが表示される場合があります。サーバーはそれを無作為に取得しません。アップロードされたアバターは依然としてサイトのストレージを使用します。

解除には最新の認証が必要であり、最後の利用可能な方法を削除することはできません。無効になったプロバイダや資格情報がないアカウントは、その最後の方法には含まれません。パスワードのないアカウントは、最新の認証後にサイトのパスワードを設定できます。既にパスワードがあるアカウントは、通常のパスワード変更を利用します。公開ユーザーIDとローカルログインは、一つの意味のある一意な文字列です。ソースが適切なIDを提供しない場合、ユーザーが自分でIDを提供する必要があります。名称としてUUIDは生成されません。内部ユーザーのUUIDは安定して保持されます。

<a id="database"></a>

## データベース

現在のベースラインにはこれらのアイデンティティ構造が含まれています。それ自体ではユーザーを作成したり、パスワードをリセットしたりすることはありません。

- `settings.registration_review` 既存の登録スイッチを使用して。 `sso_registration` そして `social_registration` 閉じられている、自動的、または承認済みです。修正ロックが共有されています。
- `account_flows` 一度限りのセキュリティチェック認証情報を保存する。このセッションはそれほどの証明ではない。
- `auth_providers` 設定、不変の名前空間、バージョンを保存します。秘密情報は保存されません。 `type` さらに、発行者とクライアントIDは一意です。
- `auth_identities` 地図 `user_id` 〜に `provider_id` さらに `subject`そのペアはユニークです。 `user_id` さらに `provider_id` ユーザーごと、プロバイダーごとに1つのアイデンティティを許可します。
- `auth_flows` 10分間の使い捨てフローです。 `stage` 開始、交換、または検証が行われる。完了時にそれを削除する。新しいフローが開始されると、期限がクリアされる。

<a id="http"></a>

## HTTP

接頭辞は `/api/v1`文章はOriginと一致していなければならない。

| ルート | 誰 | 行動 |
| --- | --- | --- |
| GET /auth/providers | 公共 | 認証情報（id、name、type）を持つプロバイダーを有効にする |
| GET /admin/auth | 管理者 | 3つのポリシー、修正、プロバイダー、準備状態、コールバックURL。秘密はありません。 |
| GET/PUT /admin/accounts/policy | 管理者 | パスワード、電話とメールでのログイン、パスワードアカウントの種類、および `forcedLoginMethod`各アクティブユーザーが1つ以上の利用可能な方法を持っていることを確認する |
| PUT /admin/auth/policy | 管理者 | `{revision,local,sso,social}` 閉じた状態、自動的に、または承認された状態 |
| POST /admin/auth/providers | 管理者 | `{type,name,issuer,client_id,credential_ref,enabled,version:0}` |
| PUT /admin/auth/providers/:id | 管理者 | 同じフィールド、現在のバージョン。不変のフィールドは変更できない |
| POST /auth/providers/:id/start | `{intent:"login"\|"link"\|"security"\|"replace"}` | 返却 `{url}` そしてフロークッキーです。リンクには最新の認証が必要です。 |
| GET /auth/providers/:id/callback | プロバイダー | 身元を確認し、その後このオリジンにリダイレクトする |
| POST /auth/complete | 検証済みのフローを消費する | ステータスはアクティブ、リンクされている、または保留中です。アクティブな問題はセッションを開始します。 |
| GET /me/identities | ログイン済み | ローカルログイン、パスワードがあるか、リンクがあるか、それらが利用可能か。対象やトークンはない。 |
| POST /auth/reauth | ログイン済み | `{password}` このセッションの最近の検証時間を更新する |
| POST /auth/password/setup | 最近の確認 | `{password}` 12～128文字以内、初回設定のみ、他のセッションは無効化される |
| DELETE /me/identities/:id | 最近の確認 | 解除リンク。最後の利用可能な方法は保護されています。 |
| GET /admin/users?status=pending | 管理者 | フィルターとページがアクティブ、保留中、または無効状態 |
| GET /admin/registration-reviews | 管理者 | ページングされた保留中/承認済み/拒否されたレビュー |
| POST /admin/registration-reviews/:id | 管理者 | `{decision:"approved"\|"rejected",message?}` |
| PATCH /admin/users/:id | 管理者 | 通常のアクティブ/無効ユーザーのみ；レスポンス待ち409 |

`POST /auth/register` 追加する `status`「Pending」は、その人に待つように言い、登録をしてくれない。

<a id="tests"></a>

## テスト

`tests/identity.test.ts` 実際の環境でRSA署名されたシミュレーションされたOIDC応答を使用する `openid-client` パスです。これにはPKCE、署名、ノンニュース、発行者、クッキー、繰り返しや期限切れのコールバック、セッションバインディング、ポリシー、承認、および解除が含まれます。ソーシャルアダプターはシミュレートされたHTTPを使用します。これはベンダーのレビューや公共ネットワークのテストではありません。

SQLiteと孤立したPostgreSQLデータベースは、現在のスキーマに対して完全な回帰処理を実行します。実際のIDプロバイダー、HTTPSプロキシ、アカウント復元には、それぞれ独自の承認が必要です。

<a id="september-2026-module-split"></a>

## 2026年9月のモジュール分割

アイデンティティは生きている `packages/core/src/modules/identity`プロトコルアダプターは生きている `apps/server/src/adapters/identity-providers.ts`カスタムOAuth 2認可コードおよびPKCEアダプターを使用することで、HTTP(S)オリジン許可リスト内にあるエンドポイントや安定したIDフィールドを設定できます。これはOIDCとは別物です。通常のOAuthトークンはIDトークンとして扱われません。

各ソースの `profile_config` 登録フィールド、その出所、および編集可能か同期可能かを宣言する。プロフィールが不完全な場合は、 `/auth/complete` 返却 `needs_profile` 完全なセッションを生成することはありません。必要なプロファイルや連絡先確認資格証明書を提出した後も、登録や承認は続行されます。ユーザー名の一意性、およびプロバイダーと対象の結合は独立しています。重複した名前はアカウントを統合しません。カスタムプロトコル設定は作成後、別のアイデンティティ名前空間を指すことはできません。
