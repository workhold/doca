# Общая бизнес-база данных плагинов

[简体中文](plugin-database-isolation.zh-CN.md)

Все плагины используют один бизнес-базу данных, управляемый хостом, отдельный от основной базы данных. Для развёртывания PostgreSQL требуется одна конфигурация базы данных/аккаунта; хост автоматически создает схемы и таблицы каждого плагина. SQLite не требует конфигурации и автоматически создает один общий файл. Плагины продолжают использовать базу данных без изменений. `storage.sql.v1` SDK, версия схемы 1 и `dataVersion`Без строк подключения, драйверов или путей файловой системы.

<a id="configuration-and-isolation"></a>

## Конфигурация и изоляция

SQLite по умолчанию `<DOCA_SQLITE_PATH>.plugins.db`. `DOCA_PLUGIN_DATABASE_PATH` По желанию выбирается другой постоянный локальный файл. Режим доступа файла — 0600. Каждый физический таблица имеет… `plugin_<SHA256(plugin ID), first 56 hex>__` Префикс; имена таблиц SDK остаются неизменными. Хосты в памяти используют один общий база данных плагинов в памяти на каждую подключение хоста. Сделайте резервную копию общей файла вместе с основной базой данных и частным хранилищем файлов. SQLite остается вариантом для одного хоста.

PostgreSQL использует один бизнес-база данных, обслуживаемый оператором, и учетную запись. Права на учетную запись выбираются оператором развертывания; принимаются обычные учетные записи, суперпользователи, роли с административными атрибутами или членства, а также такая же учетная запись, используемая для критических задач. Учетная запись должна иметь действительные права. `CONNECT` и `CREATE` Привилегии для этой базы данных предназначены для создания схем плагинов, плюс `USAGE` и `CREATE` на нем `public` Схема для инициализации общей метки. На уровне базы данных `CREATE` не предоставляет на уровне схемы `CREATE`PostgreSQL 17/18 по умолчанию не предоставляют этот режим обычным ролям, не являющимся владельцами. См. [Права схемы PostgreSQL](https://www.postgresql.org/docs/18/ddl-schemas.html#DDL-SCHEMAS-PRIV)Необходимо настроить это один раз перед включением плагинов SQL:

```dotenv
DOCA_PLUGIN_DATABASE_URL=postgresql://doca_plugins:replace-me@postgres:5432/doca_plugins
DOCA_PLUGIN_DATABASE_POOL_MAX=4
```

Для нового развертывания следующие опциональные положения, касающиеся специального аккаунта, предоставляют магазин. `psql` (Заменить пароль). Также можно напрямую настроить существующий уполномоченный аккаунт.

```sql
CREATE ROLE doca_plugins LOGIN PASSWORD 'replace-me';
CREATE DATABASE doca_plugins;
REVOKE ALL ON DATABASE doca_plugins FROM PUBLIC;
GRANT CONNECT, CREATE ON DATABASE doca_plugins TO doca_plugins;
\connect doca_plugins
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO doca_plugins;
```

Для существующего развертывания сохраняйте его роль, базу данных и данные. Если отсутствуют отчеты инициализации. `USAGE`/`CREATE` на `public`Подключитесь в качестве владельца базы данных к **бизнесная база данных плагинов** и запустить `GRANT USAGE, CREATE ON SCHEMA public TO doca_plugins;`, используя настроенное имя роли. Если создавать схему плагина, возникает сообщение о отсутствии базы данных `CREATE`, предоставить `CREATE ON DATABASE doca_plugins TO doca_plugins` как владелец. Повторно запустите приложение после исправления прав; не требуется удаление, сброс или конвертация данных. Хост не автоматически предоставляет привилегии. Эти привилегии применяются только к специализированной бизнес-базе данных плагинов. Существующие общие метки не требуют `CREATE` на `public` Опять. Связи, пароли и ошибки чистого SQL остаются невидимыми в ответах плагина; эти диагностические данные, связанные с конфигурацией хоста, отображаются явно.

Ведущий автоматически создает `plugin_<SHA256(plugin ID), first 56 hex>` Схемы первой декларации. Каждый плагин использует один пул соединений для каждой инстанции хоста; `DOCA_PLUGIN_DATABASE_POOL_MAX` Это целое число от 1 до 20, по умолчанию 4. В бюджет подключения к серверу включите этот набор, наборы для ядра/ИИ/webhook и количество инстансов. Все реплики должны использовать один и тот же общий бизнес-базу данных. При добавлении другого плагина не требуется никаких баз данных, ролей или записей подключений. Плагины без хранения данных в SQL не требуют этого URL.

Настроенная бизнес-база данных должна быть отдельной от корневой, даже если оба URL используют один и тот же логин. Хост не проверяет атрибуты повышенного ролевого статуса, членства в ролях или привилегии корневой таблицы, и не изменяет разрешения учетных записей базы данных. Операторы решают, следует ли ограничивать учетные записи с помощью PostgreSQL-гарантий. Хост не создает базы данных/роли и никогда не переключается на корневое хранилище. Транзакции PostgreSQL устанавливают схему локальной транзакции; пул соединений не сохраняет сферу действия другого плагина. Удаление устанавливает и удаляет только таблицы и метки установки удаленного плагина; другие схемы/данные плагина и общий хранилище остаются.

Политика учетной записи, управляемая оператором, была утверждена 16.10.2026. Она заменяет систему отклонения привилегий учетной записи, введенную в версиях 0.1.26–0.1.29. Существующие декларации формата-3, метки, поколения и версии данных сохраняются без преобразования; никакие данные или разрешения не изменяются при обновлении. Повторное откатывание системы восстанавливает старые ограничения учетной записи, поэтому вход администратора может быть отклонен снова. При планировании отката необходимо сохранить существующую базу данных, данные и конфигурацию. Процедура обновления до формата-2 остается неизменной.

Это изоляция через сервисы SDK, принадлежащие хосту. Плагины выполняются в надежном процессе Node.js; совместное использование бизнес-роли не является процессом или сумбрадом операционной системы.

Ядро сохраняет пользователей, документы, права доступа, аудит безопасности, использование чистой ИИ, реестр/архивы плагинов, записи пространственных имен, зашифрованные учетные данные, ссылки на приватные объекты и долговечные намерения объектов. Владение/права на файлы и учетные данные, основные DDL и `schema_baseline.id` остается неизменным.

<a id="exact-storage-format-and-lifecycle"></a>

## Точный формат хранения и жизненный цикл

Заявления хоста используют формат 3`storageVersion: 3`, изначально `schema: null`). Общий маркер корня `_doca_shared_plugin_database` С форматом 3. Каждый плагин `_doca_plugin_store` Маркер записывает свой точный ID, номер генерации, версию данных и канонический схему. Валидация маркера и интроспекция с учетом ограничений предотвращают применение несвязанных данных. Отклоняются отсутствующие общие файлы, пространства имён или ранее объявленные таблицы; их никогда не восстанавливают без каких-либо уведомлений. Изменение URL/файла не приводит к миграции данных, а пустой замена отклоняется, как только схема была зарегистрирована.

Первое объявление блокирует ядро пространство имён, создаёт пространство имён плагина, бизнес-таблицы и маркер в одном бизнес-транзакции, затем записывает объявление в ядро транзакции. Повторная транзакция после прерванного ядерного коммита принимает только точный коммитированный бизнес-маркер и реальную структуру. Различные определения схем, типы/по умолчанию/недоступность, первичные/уникальные ограничения и неожиданные таблицы отклоняются. Кallback-транзакции пользователя выполняются один раз и обрабатывают истечение срока после завершения. Бизнес-коммит, последовавший за неудачей ядерного коммита, является неопределённым исходом, требующим бизнес-идемпотентности/повторного прочтения; callback-транзакции не повторяются.

Ключ к ядру пространства имен хранится в результате бизнес-коммита, поэтому удаление записи ожидает одобренных записей. Сначала выполняется хук удаления бизнес-решения. При успехе транзакция реестра ядра останавливает процесс генерации, очищает параметры установки и учетные данные, а также отправляет задачу очистки приватных объектов. Пользовательские файлы, права, квитанции и архивы релиза остаются. При неудаче хука установка сохраняется; влияние внешних хуков невозможно отменить.

Очистка бизнес-системы осуществляется с использованием основного коммита, при этом сохраненные данные служат подтверждением целевого состояния системы. При запуске или периодической очистке, а также при попытках удаления и установки система повторно пробует выполнить процедуры очистки. Очистка проверяет, удалены ли необходимые таблицы и метки, прежде чем удалять объявленные таблицы. Неизвестные таблицы или несоответствующие метки приводят к отказу в очистке без частичного удаления. PostgreSQL оставляет пустой пространство имён для имплемпотентных повторных попыток; SQLite оставляет общий файл. Повторная установка ждет завершения процедуры очистки, увеличивает номер генерации и создает пустые таблицы бизнес-системы. Не предусмотрено никакого распределенного атомарного коммита или автоматического выполнения задач кластера; необходимо перезапускать каждую инстанцию.

<a id="approved-upgrade-from-0125"></a>

## Утвержденный апгрейд от 0.1.25

Владелец согласился. **Обычное удаление предыдущей версии, за которым следует переустановка, без миграции данных плагина**Опубликованная версия 0.1.25 использует файлы/базы данных для каждого плагина и формат 2. Установки активного формата-2, включая статeless-плагины, отклоняются до записи в основной реконфигурации. Устаревший `DOCA_PLUGIN_DATABASE_DIR` и `DOCA_PLUGIN_DATABASES_JSON` Настройки отклоняются явно. Не предусмотрено устройство для чтения старых данных, автоматиченая конвертация данных, двойное запись или автоматическое удаление старых баз данных/файлов.

1. Сделайте резервную копию оригинальной базы данных, всех старых баз данных/файлов плагинов, личного хранилища файлов, конфигурации и оригинального главного ключа учетных данных.
2. На предыдущем хосте обычно удаляются все внешние бизнес-плагины и решаются все оставшиеся задачи очистки. Это намеренно уничтожает их личные бизнес-записи, зашифрованные учетные данные и приватные объекты. Плагины перенастроены, а внешние учетные записи переобучены после повторной установки. Основные данные и обычные пользовательские файлы остаются.
3. Остановите все инстансы хоста. Удалите старые настройки для каждого плагина. Для PostgreSQL предоставьте/настройте пустую общую бизнес-базу данных и учетную запись, выбранную оператором; для SQLite используйте автоматическую общую файловую систему или настройте её путь. Сохраняйте старые хранилища/бэкапы в качестве доказательства восстановления.
4. Разверните новый хост против существующей основной базы данных, обычных файлов и оригинального мастер-ключа. Перезапустите плагины и каждую инстанцию. Хост автоматически присоединяет каждый плагин к общей бизнес-базе данных, начиная с пустых приватных бизнес-данных.

Если удаление не проходит, решите проблему на предыдущем хосте. Если запуск отклоняется из-за остаточной установки, вернитесь на тот хост, чтобы завершить удаление; никогда не сбрасывать основную базу данных. История имён пространства, уже удалённых, остаётся, а явное повторное установление увеличивает её возраст. Существующее обработка истории имён пространства, очищенной до версии 0.1.25, сохраняется; она не читает старые бизнес-данные. Остаточные колокальные данные… `plugin_<56 hex>` Таблицы из более старых версий все еще требуют проверки и не удаляются автоматически.

Перед новыми записями для восстановления в состояние до установки необходимо сопоставить оригинальные копии ядра/плагина/файлов и старый код/конфигурацию. Отозванные внешние разрешения могут потребовать переподключения. После новых записей сохраняйте новые базы данных/файлы и договоритесь о отдельном плане восстановления; восстановление старых копий приведет к утрате последующих данных. Старые хосты не могут читать формат 3. Мультиплатформенная работа старых и новых хостов не поддерживается.

## Проверка

`scripts/verify-plugin-database-isolation-upgrade.ts` Создается синтетические данные основного ядра и данные приватного плагина формата-2 с реально выпущенными данными `smartdoca/doca:0.1.25` Изображение. Оно проверяет отклонение без изменения сохраненных основных строк/деклараций, обычную дистанционную удалку старого хоста, повторное открытие той же основной базы данных и переустановку в пустой общей память. Запустите его на изолированном SQLite и PostgreSQL 17/18. Эти проверки не предусматривают внедрение в производственную среду или работу с смешанными версиями.
