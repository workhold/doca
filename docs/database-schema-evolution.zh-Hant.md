# 資料庫升級規範

[English](database-schema-evolution.md)

已批准的使用者組增量沿用本規範及當前相容代際：七張組/成員/邀請/授權空表，及獨立組搜尋策略表，首次安裝明確初始化為僅所在組（`system/member/revision=1`），使用者覆蓋為空。歷史個人/連結授權、邀請、公開設定及使用者目錄策略不變，不轉換、不復制組成員為個人授權。已安裝配置行丟失不靜默重建。所有服務例項與 Web 同步更新，降級保全及恢復另行評審。見[組許可權規則](user-groups.zh-Hant.md)、[發行說明](releases/0.2.28.zh-CN.md)及 [SQLite/PostgreSQL 17/18 驗證](verification/user-groups-2026-10-30.md)。

這是 Doca 後續核心資料庫改動統一遵守的開發、評審與釋出規範，適用於表、欄位、索引、約束、初始化及持久化資料格式，並非只針對本次共享資料夾升級。[AGENTS.md](../AGENTS.md) 要求在實施前明確並確認具體相容方案，包括歷史欄位值的業務含義、資料保留、驗證與恢復。這套結構對比升級機制已經確認；新的業務相容決策仍需單獨確認。

<a id="只维护一个最新目标结构"></a>

## 只維護一個最新目標結構

`packages/db/src/create-schema.ts` 及其結構輔助函式中的最新 DDL 是唯一目標結構。新庫建立和舊庫升級檢查共用 `createCurrentStructure`，普通增量升級不累積逐版本 SQL 遷移指令碼，也不按應用版本逐級重建歷史結構。

`packages/db/src/schema.ts` 中的 Kysely 型別須與 DDL 一致。`schemaEvolution` 只宣告當前支援的相容代際內已審定的新增表和欄位，不儲存歷史 SQL；寫入宣告不代表型別變化或資料轉換已經安全。仍受支援的舊結構需要這些宣告時，不得在未確認支援範圍變化前移除。

`schema_baseline.id` 表示相容代際，不是每次發行的版本號。當前為 `doca-2026-10-12-book-payload-storage-v1`，普通新增表和欄位不調整它。既有顯式歷史儲存升級和中斷回退檢查保留，因為它們改變了持久化歷史資料的語義。

目標是讓受支援的舊結構直接對齊最新目標，不依賴中間版本的指令碼。但代際相同還不夠，結構和語義差異也必須符合已確認策略，不能承諾任意歷史庫或手工修改的庫均可升級。重大不相容變化須先確認拒絕範圍、必要的顯式轉換、資料保留與恢復方案，再決定是否建立新代際。

<a id="启动时对比与处理"></a>

## 啟動時對比與處理

啟動先取得資料庫或 schema 的結構鎖，再比較已安裝結構與最新 DDL 生成的參考結構。檢查覆蓋欄位、型別、預設值、是否允許空值、主鍵、外來鍵、唯一和檢查約束及索引。PostgreSQL 使用會話臨時參考表，SQLite 使用獨立記憶體庫，參考結構不會使用使用者文件。

PostgreSQL 透過 `pg_attribute.attnotnull` 校驗欄位空值約束。PostgreSQL 18 還會在 `pg_constraint` 中記錄欄位 `NOT NULL`，表約束比較須排除這份重複記錄，避免把已審定的必填欄位新增誤判成額外約束變化。已確認的欄位對齊策略允許在校驗舊行後，用原生 ALTER COLUMN 對齊空值約束；主鍵、外來鍵、唯一和檢查約束變化仍需確認。參見 PostgreSQL [18](https://www.postgresql.org/docs/18/catalog-pg-constraint.html) 和 [17](https://www.postgresql.org/docs/17/catalog-pg-constraint.html) 的目錄說明。

| 差異 | 啟動行為 |
| --- | --- |
| 空資料庫 | 按最新結構建立，並初始化系統記錄。 |
| 已審定且缺少的表 | 建立表及宣告的索引，不推斷或補造歷史記錄。 |
| 已審定的可空欄位，或具有已確認字面量預設值的必填欄位 | 擴充套件欄位，為已有行補齊已確認的歷史值。 |
| 已有表缺少普通非唯一索引 | 建立索引並複核結構。 |
| PostgreSQL 同型別 varchar 長度擴大，或已有欄位預設值、空值約束不同 | 原生 ALTER COLUMN 對齊；舊值不改，改為必填前校驗不存在 NULL。 |
| SQLite 空值約束不同 | 使用內建 SQLite 3.53.4 的原生 ALTER COLUMN，先校驗舊行；不替換表、不關閉外來鍵。 |
| SQLite 預設值不同；型別轉換、長度縮小；主鍵、外來鍵、唯一或檢查約束、索引定義變化 | 報告待確認計劃，在持久化修改前停止。 |
| 必填欄位沒有已確認的歷史值；已有表新增唯一索引；重新命名或刪除；未知表；持久化業務語義變化 | 需要另行確認資料保留或轉換方案，不靜默執行破壞性或語義升級。 |

新增欄位必須說明它對已有行的業務含義，以及如何保留原有行為。新建記錄的預設值和歷史記錄的補充值可以不同；對比器不能自行猜測。許可權、分享、憑證和資源限制不能因為給舊記錄補一個方便的值而被靜默放開。重新命名須按資料保留處理，不能偽裝成刪掉舊欄位再新建欄位。

SQL 結構相同時，對比器無法檢測 JSON 格式或業務含義變化。開發者仍須評審這些相容決策，實施已確認的校驗、轉換或代際檢查，不能用結構對比透過來證明語義相容。

升級成功後，`schema_baseline.structure_json` 只記錄最新已安裝的表和欄位清單，替換舊清單，不累積遷移歷史。曾經安裝的表或欄位丟失時，應按可能的資料丟失報告，不能當成新欄位自動重建並重置配置。外掛業務表現已存放於[共享外掛業務庫](plugin-database-isolation.zh-Hant.md)。殘留舊 `plugin_<56位十六进制>` 表作為未知表要求審查：啟動保留資料並在持久化結構變更前停止。須先在舊宿主正常解除安裝再升級，不自動刪表或遷移；外掛業務資料版本繼續使用自身公開儲存約定。 0.1.26 使用與核心庫分開的[外掛共享業務資料庫](plugin-database-isolation.zh-Hant.md)，宿主格式 3 取代已釋出 0.1.25 格式 2；有效舊安裝在持久化寫入前被拒絕，須先在舊版正常解除安裝再重灌，不遷移私有資料。核心 DDL 和相容代次不變。

先分類整個升級計劃，再執行持久化 DDL。只要其中一項需要確認，本次就不執行其他自動項。檢查、已接受的修改、結構複核和最新清單記錄都在結構鎖保護的事務中完成，任何失敗整體回滾。重複啟動須保留原資料和使用者設定；記錄的結構清單損壞時也停止啟動。系統不提供透過刪庫、重置資料或跳過檢查來強行升級的方式。

PostgreSQL 獲得結構鎖後須讀取最新目錄，讓併發宿主能看到前一個已提交的升級結果，不能使用等待鎖之前的舊快照。

## 已確認的原生欄位對齊（0.2.10）

使用者已確認 PostgreSQL 可自動擴大同型別 varchar 長度，並對齊最新 DDL 的預設值及空值約束；SQLite 僅用原生 ALTER COLUMN 對齊空值約束，預設值變化仍停止啟動。不重建或替換表，不直接編輯 writable_schema，不補造舊值，不自動降級。後續當前 DDL 涉及歷史業務語義的變化仍須事先確認。核心策略顯式啟用欄位對齊，嚴格結構校驗和現有知識冊離線轉換門檻保留各自策略。

持久化 DDL 前先分類整個計劃；PostgreSQL 在校驗舊值前鎖定受影響的表，SQLite 沿用已有寫事務和結構鎖。有 NULL 無法改為必填、任何不支援的差異、未知 SQLite 觸發器或檢視、複核失敗，都會拒絕本次全部修改，包括其他已允許的欄位、表和索引新增。欄位對齊與最新結構清單在同一事務提交。修改預設值不改已有行；移除 NOT NULL 不代表允許修改主鍵、外來鍵、唯一或檢查約束。排序規則、identity 和生成列屬性不屬於自動處理範圍。

PostgreSQL 的 assets.purpose 最新目標是 varchar(32)，以儲存現有 18 字元 ai_image_candidate；SQLite 保持原 varchar(16) 宣告，SQLite 本身不按此宣告限制長度。新庫和 PostgreSQL 臨時參考目錄共用相同的引擎目標 DDL。啟動可將已釋出庫的 varchar(16) 無損擴到 32；已安裝長度更大、需要縮小的結構仍拒絕。不刪除或截斷舊值，相容代際不變。

釋出驗證使用已釋出 0.2.9 原始碼 655e7ecf71274417d2cf5f352f9151612c702859 建立 SQLite、PostgreSQL 17/18 隔離庫，131 張原表的資料雜湊全部保留。PostgreSQL 目錄僅 purpose 長度 16→32；SQLite 結構不變。獨立迴歸覆蓋原生預設值/空值約束處理、父子表資料、SQLite 根頁與行號不變、重複/併發執行、有 NULL、型別變化、縮小和未知物件拒絕，以及事務回滾。詳見[發行核驗](verification/ui-image-ark-plan-2026-10-23.md)。部署前備份並統一更新所有宿主；不引入自動降級或混合版本保證。

<a id="后续开发与发布流程"></a>

## 後續開發與釋出流程

1. 明確受影響的舊版本、相容代際、程式碼路徑、已有資料及持久化格式。說明哪些差異保留、新增、拒絕或顯式轉換，列出歷史值、驗證和恢復方案，按倉庫相容規則取得確認。
2. 修改最新 DDL 和對應型別，只在 `schemaEvolution` 中宣告已審定、對比器支援的新增項。語義轉換使用另行確認的機制；普通升級繼續共用目標結構與對比器。
3. 為受影響舊結構補充或調整隔離迴歸樣本，包含代表性的已有行。檢查原值保留、新欄位預設值、適用時的新表為空、重複與併發啟動、需確認或驗證失敗時結構和資料均未被部分修改，以及曾安裝欄位丟失時不能被靜默重建。
4. 執行 SQLite 結構迴歸和 PostgreSQL 17、18 矩陣。`.github/workflows/database-upgrade.yml` 已執行 PostgreSQL 結構和資料夾用例；後續業務改動須增加自己的相關用例。SQLite 透過不能替代 PostgreSQL 驗證，從最新結構反向刪欄位也不能單獨證明實際舊版本可升級。
5. 釋出前使用受影響的已發行舊版本建立隔離資料庫，再用候選版本升級。驗證業務資料保留、受影響功能和升級後的重啟，將實際覆蓋的版本、資料庫引擎及重要限制記入發行驗證和升級說明。

使用合成賬號和隔離測試資料庫、文件。`tests/database.ts` 為每個 PostgreSQL 樣本建立並清理獨立 schema，不得在使用者庫上執行破壞性樣本或協同編輯測試。涉及協同或外掛契約的改動還須遵守相應專項約定。

本規範、中英文版本和實現須同步。新增自動處理行為、支援範圍變化及語義例外應一起完成確認、實現、文件和驗證。文件中的未來能力說明不代表當前對比器已經支援。

## 已確認的系統 Logo 新增欄位（0.2.24）

使用者已確認將系統 Logo 放在 `settings`。最新 DDL 與 `schemaEvolution` 宣告可空的 `settings.site_logo` 文字欄位，相容代際不變。新建和歷史記錄都以 `NULL` 表示沿用當前預設圖示；現有站點設定、版本號、正文、許可權和配置值全部保留。不新增 `account_settings` 記錄，不轉換歷史 JSON。已配置值採用嚴格的 `{version:1,png:<base64>}` 格式，內容為驗證後的 PNG，每邊不超過 256 畫素。未知版本、多餘欄位和損壞圖片原樣保留並拒絕讀取，也禁止透過正常介面覆蓋或恢復預設來繞過檢查。僅管理員明確上傳或恢復預設才會修改已識別配置，使用站點設定的共享版本號，安全審計與修改同事務提交。

隔離 SQLite、PostgreSQL 17/18 均驗證了從正式釋出的 0.2.23 結構升級，包括全部 131 張原有表的資料雜湊、歷史 NULL、已配置圖片保留、重複/併發啟動、需要審查時不發生部分新增，以及已安裝欄位隨後丟失時拒絕重建。見 [Logo 驗證記錄](verification/site-logo-2026-10-28.md)。服務端和 Web 需同步更新。舊程式現有的結構審查會拒絕新增欄位，因此不支援自動回退啟動；應保留欄位、資料庫、檔案卷、原配置及後續寫入，另行評審恢復，不得刪列或用舊備份覆蓋後續資料來繞過審查。此前將 Logo 放進 `account_settings` 的提議未實施。

<a id="部署与恢复"></a>

## 部署與恢復

已獲同意的[知識冊批次檢查點](knowledge-book-generation-performance.zh-Hant.md)透過最新 DDL 和 `schemaEvolution` 新增空的 `knowledge_book_batch_checkpoints` 表，保持 `doca-2026-10-12-book-payload-storage-v1` 代際。既有 node/run/release 行、引用約束、v1 格式、許可權和釋出指標不變，不猜測或回填歷史結果。獨立的私有檢查點 v1 格式嚴格校驗。[驗證記錄](verification/knowledge-book-checkpoints-2026-10-19/README.md)覆蓋實際已釋出 0.2.3 在 SQLite、PostgreSQL 17/18 建立的資料升級、記錄及正文位元組保留、重複/併發啟動和拒絕時無部分寫入。所有執行器與垃圾回收例項一起更新；舊二進位制無法保護新的檢查點引用。存在檢查點時，離線正文儲存回滾會在修改前停止，需另行批准保全方案。

部署前備份資料庫。啟用新資料夾限制前須更新所有宿主例項：舊宿主不執行新的人數限制和邀請確認，不能混用新舊版本。這個已審定的增量變化無需調整相容代際，也無需離線遷移命令。

保留原資料庫與檔案卷、部署身份和 `DOCA_CREDENTIAL_MASTER_KEY`。結構增量相容不自動代表可以混用新舊應用或安全降級，應按實際業務行為評估。

啟動升級失敗時，事務保留原結構和原資料。成功升級後若要恢復舊應用行為，須單獨確認資料保留與恢復方案；恢復升級前備份會丟失之後的寫入，應先保留新增記錄。不要刪除資料庫來繞過待確認差異。

已有隔離驗證覆蓋 SQLite 和 PostgreSQL 17、18 的舊結構及已有資料、空的新表、可空和必填預設欄位、重複與併發啟動、預設值及空值約束變化、外掛資料保留、已安裝欄位丟失拒絕。0.1.22 還使用實際 0.1.20 映象建立 PostgreSQL 18 舊庫後再升級。資料夾用例覆蓋通知、工單、確認授權、實時許可權、過期和併發名額校驗；這些記錄不替代未來改動自己的驗收。
