# プラグインをインストールし、展開する

0.1.26はaを使用しています [共有プラグインビジネスデータベース](plugin-database-isolation.ja.md)コアから分離され、自動的な名前空間を持つ。0.1.25でリリースされたプラグインごとのデータベースを代替する。アップグレードには、以前のホストで通常のアンインストールと再インストールが必要であり、プラグインデータは移行されない。

[中文](plugin-deployment.zh-CN.md)

承認された [管理型ストレージ契約](plugin-horizontal-scaling.ja.md) 必要とされる `doca.storage: "host"` ホスト所有の永続性。静的拒否、管理されたSQL、プライベートオブジェクトが実装されている。認証情報はSDKソース0.1.8でエクスポートされる。一時的なワークスペースやクラスタータスクの消滅は未解決の問題である。プラグインはローカル/リモートバックエンドを選択したり、ビジネスデータディレクトリを受け取ったりできない。

管理者は使用する **Admin → プラグイン** 公式ストアを閲覧し、ローカルのZIPファイルをアップロードして、プラグインをインストール、アップグレード、有効化、無効化、またはアンインストールします。変更内容は所望のインストール状態として保存され、各インスタンスの次の起動時に有効になります。ページには、グローバルターゲットとは別に、回答インスタンスの実行中のバージョンが表示されます。現在のアンインストールでは、必要なビジネスクリーンアップフックが呼び出され、その後構造マーカーがクリアされます。フックが失敗するとインストールは保持されます。ホスト管理のプライベートストアのクリーンアップでは、生成フェンシングと耐久性のあるオブジェクトガベージ記録が使用されます。ビジネスタスクの消費は未実装のままです。プラグインファイルシステムの削除は禁止されています。インストール済みプラグインのアップグレードには、依然として同じ手順が必要です。 `doca.dataVersion`プラグインは初期化時に実際のデータベース構造をチェックします。

```dotenv
DOCA_PLUGIN_STORE_URL=https://store.smartdoca.cc
DOCA_PLUGINS_DIR=/data/plugins
```

店舗のアドレスは設定可能なHTTP(S)オリジンです。リモートサービスの利用可能性を別途確認してください。利用できない店舗でも、ローカルでのアップロードやインストールされたプラグインは使用可能です。空 `DOCA_PLUGINS_DIR` 再び戻る `${DOCA_DATA_DIR:-./data}/plugins`作業ディレクトリに関して。ホストのみが持続可能なデータベース/オブジェクトストレージを設定します。business-data-directory環境変数は存在せず、プラグインのAPIはホストがローカルに保存するかリモートに保存するかを決して明らかにしません。

提供されたComposeデプロイに対しては、デプロイディレクトリ内で実行してください：

```sh
docker compose restart doca
```

ここで、 `doca` サービス名はここです `services` 中に `compose.yaml`; コンテナ名は異なる場合があります。サービス名を変更した場合は、そちらに置き換えてください `doca` サービス名を含むコマンドで。

マルチインスタンスデプロイメント内の各インスタンスを再起動する。他のデプロイメントタイプには適切なスーパーバイザーを使用する。UIはプロセスを再起動しない。ローリング再起動中はトラフィックを減らすか、プラグインAPIが変更された場合はアフィニティを使用する。V1はゼロダウンタイムのマルチバージョンAPIを保証しない。

## ストレージリビジョンを実施（2026-10-03、SDKソース0.1.8）

`@smartdoca/plugin-sdk/storage` 現在、インストール向けの輸出を行っている `pluginDatabaseToken` (`storage.sql.v1`) と `pluginObjectStorageToken` (`storage.objects.v1`). データベースサブセットは明示的なスキーマバージョン1であり、text/int32/double列、プライマリ/ユニーク制約、構造化されたselect/insert/update/remove操作、および一度実行されるコールバックを含むトランザクションが含まれる。SDKソース0.1.8も追加でエクスポートされる。 `pluginCredentialToken` (`storage.credentials.v1`）：サーバー専用の暗号化されたCRUD、メタデータ、レビューチェック。参照 [認証API](plugin-credentials.ja.md)join、 foreign key、generic SQL、upsert、ワークスペースはエクスポートされません。Business SQLでは、コアとは別の共有ホスト管理型データベースが使用されます。表のプレフィックスを持つSQLiteファイル、または自動的なプラグインスキーマと共有接続プールを持つPostgreSQL URL/アカウントが使用されます。プロセス分離は実装されていません。詳細は参照してください。 [ストレージ構成と、アップグレード前にアンインストールする契約](plugin-database-isolation.ja.md).

論理データベースは使用する `plugin:<pluginId>`ユーザーファイルの帰属とプライベートオブジェクトの使用 `plugins/<pluginId>`、そしてZIPファイルを解放する際に使用される `host/plugin-releases/<sha256>.zip`完全に不変のZIPバイトは、環境で設定されたファイルストレージに保存されている。共有データベースにはレジストリバージョン2、アーカイブ参照情報、信頼できるファイルハッシュインデックスが含まれている。検証されたキャッシュヒットは、ZIPファイルを再ダウンロードしない。すべてのインスタンスは手動で再起動される。新しいホストベースラインでは、古いデータベース/フォーマット/SDKパッケージは拒否され、そのデータは保持される。移行やフォールバックは行われない。詳細は… [正確な実装と制限事項](unified-storage-implementation.md).

## 配布とファイルシステム

すべてのインスタンスは同じホストデータベースを使用します。PostgreSQLが分散型デプロイメントの選択肢です。データベースには原子的な希望レジストリと不変のアーカイブ参照が保存されており、ローカルアップロードを含む完全なZIPファイルが設定された共有ファイルストレージに存在します。各インスタンスにはプライベートな書き込み可能なキャッシュがあります。

```text
/data/plugins/
  .releases/<sha256>/          verified immutable releases
  .staging/                   temporary extraction
  .imports/                   retained offline folder imports
```

スタートアップは共有アーカイブに対してすべてのファイルをチェックし、欠落または破損したファイルを復元した後で初めてプラグインをインポートします。npm依存ライブラリのインストール、ソースコードのコンパイル、またはストアへの接続は一切行いません。共有アーカイブが欠落または破損しているとスタートアップが失敗します。不変リリースの含む共有データベースのメタデータと設定されたファイルストアの両方をバックアップする必要があります。ホストは、管理されたプラグイン記録、プライベートオブジェクト、ユーザーファイル参照、認証情報もバックアップします。マルチインスタンスの永続的なサーバーは共有される必要があります。ディレクトリ名は分散型データベースではありません。

ライブインスタンス間でプラグインキャッシュディレクトリを共有しないでください。1つのインスタンスでインストールした場合、別のインスタンスに手動でコピーする必要はありません。また、ロードバランサーのルーティングを処理するために、共有アーカイブから必要に応じて歴史的バージョン化されたブラウザアセットを復元することもできます。

オフラインインストール：インスタンスが停止している間、完全なリリースを適用する `<DOCA_PLUGINS_DIR>/<plugin-id>/`起動時に、パッケージ化され共有レジストリに配信され、その後移動される。 `.imports/`他のケースでは再起動時に同期されます。通常の管理ではZIPアップロードを使用すべきです。root npmマニフェストやソースロード対応のパスはありません。

ローカルのZIPファイルとストアのZIPファイルは同じレイアウトとチェックを使用します。使用してください。 [ストアプロトコルとパッケージ仕様](plugin-store-protocol.ja.md)プログラムファイル、書き込み可能なビジネスデータ、認証情報は別々でなければならない。抽出中にはスクリプトは実行されない。完全な実行時依存関係は実際のファイルとして提供されなければならず、pnpmリンクは配布可能なアーチファクトではない。

<a id="lifecycle-and-retention"></a>

## ライフサイクルと保持

ホストはコードをインポートする前に、SDKの範囲、重複するID、データバージョン、プラグインの依存関係を確認する。設定はグローバルであり、リクエストのアイデンティティと権限はホストが保持する。管理側はレビジョンチェックを使用し、対立する管理者が互いを上書きするのではなく、再試行するようにする。運用部門はセキュリティ監査イベントを作成する。

無効化やアンインストールは再起動時に行われる。その間は、古いプロセスが依然として古いプラグインを提供する。古いコードキャッシュや不変のアーカイブは、実行インスタンスや再インストールのために保持される。v1では自動的なアーカイブのゴミ収集は行われない。無効化/シャットダウンは持続的な状態を保持する。ユーザーアタッチメント、ドキュメントペイロード、その他のビジネス参照、ファイル受領書は自動的に削除されない。管理されたプライベート状態のクリーンアップはホストが行い、クラスターコーディネーターが必要である。キャンセルは応答インスタンスの起動選択を復元する。これは新しいグローバルな望ましい状態の変化であり、他のプロセスの即時ロールバックではない。

実際のプラグイン初期化失敗が起きても起動が停止する。SDKや依存関係の互換性問題は以下のように個別に処理され、プラグイン管理は可能である。ホットアンインストール、クラスター完了ダッシュボード、ネイティブモバイルの動的コードインストール機能はない。

検証には、孤立したデータベースと一時的なディレクトリが使用されます。詳細は [ストア受け入れ](plugin-store-protocol.ja.md#cross-repository-acceptance).

<a id="compatibility-failure-isolation"></a>

## 互換性失敗の隔離

互換性のないSDK範囲や利用できない必要な依存関係により、影響を受けるビジネスプラグインが孤立する。ホストプラグインと関連のないプラグインが起動し、Admin → Pluginsで理由が説明され、アップグレードが求められる。インストールされた選択項目、アーカイブ、ビジネスデータ、認証情報は保持される。古いパッケージは変換されず、古いSDKコードも実行されない。新しいオンラインインストールでも互換性のないパッケージは拒否される。完全なオフラインインストールフォルダは元の識別子を保持し、同じ孤立状態が維持される。

古いパッケージは、登録しているすべてのビジネスポリシーを静的に宣言していません。このインスタンスには有効だが利用できないプラグインがあるため、既存のプラグインポリシーで対象となる書き込みは503を返します。ログイン、読み取り、プラグイン管理は利用可能です。互換性のあるパッケージにアップグレードするか、影響を受けるプラグインを明示的に無効にし、この保護を解除するために各インスタンスを再起動してください。プラグインの権限ソースが不足している場合、認可は引き続き拒否されます。互換性のないSDKコードはアンインストールフックを実行できません。まずアップグレードしてください。段階的な互換性のあるアップグレードは、SDK非互換のパッケージに戻すことはできません。代替パッケージはdataVersionと既存のビジネス構造を保持する必要があります。

孤立はインスタンスローカルの診断状態であり、レジストリやデータベースのスキーマ変更ではありません。破損したアーカイブ、無効なメタデータ、コアの障害、実際のライフサイクルエラーは依然として明確に失敗します。データ移行やアプリケーションのダウングレードは行われません。
