# 知識冊大篇幅生成：效能改動與批次續跑

[English](knowledge-book-generation-performance.md)

2026-10-19。批次檢查點已獲得使用者明確同意並實施，當次使用隔離資料驗證，未部署生產。

<a id="已实施的执行优化"></a>

## 已實施的執行最佳化

- 長文按節寫作在請求前參考配置模型的輸出預算拆分，每批仍最多 12 條判斷。完整字數配額按判斷分配，不截斷正文、程式碼或圖，不放棄引用。單條判斷不可再分時，仍使用現有有限補寫和失敗規則。輸出預算是估算，無法保證供應商永不截斷。
- 獨立的分層質量彙總複用現有兩路併發池，結果按原分組順序交給最終檢查。任一請求失敗時取消並等待另一請求結束。
- 單條質量觀察直接保留原結論、章身份和原因，不再傳送一次內容相同的彙總請求。多條觀察仍經彙總，區域性失敗繼續阻止驗收，最終整冊檢查繼續執行。
- 第一輪執行最佳化未改變存量格式；本輪按已同意方案新增檢查點表和私有物件引用。配置、已釋出成果及歷史節點輸出的 version 1 保持不變。

在隔離模型響應測試中，25 個質量批次產生的三個彙總組由三次序列模型請求變為兩次併發請求加一條原樣保留的觀察。該結果僅證明這一彙總層少一次請求、少兩個序列等待輪次，不能外推為整冊快 3 倍。

使用者描述的 15 萬字、約 8 小時任務位於線上，本地沒有該執行的日誌。尚未復現線上失敗、質量誤判或總耗時，也沒有用線上資料進行寫入或重跑。

<a id="原有浪费与本次范围"></a>

## 原有浪費與本次範圍

此前只在完整節點完成時儲存輸出，節點中途失敗會重做未落盤的批次。本輪新增完整請求結果、規劃和分配的持久化。候選修復仍受當前授權與內容範圍約束；新增批次檢查點不跨執行復制，也不復用發生變化的範圍。

已發現的節點複用、凍結執行繼續和歷史成果讀取規則保持現狀，本次不新增舊成果介面卡、不轉換歷史執行、不調整質量門檻。完整節點輸出仍使用既有原生物件引用；歷史 SQL 正文的現有人工處理邊界不變。

<a id="已同意并实施的具体方案"></a>

## 已同意並實施的具體方案

適用當前 `doca-2026-10-12-book-payload-storage-v1` 相容代際中、結構檢查合格的資料庫；不承諾任意歷史資料庫升級。配置和已釋出成果繼續使用現有 v1 協議。

1. 新增獨立表 `knowledge_book_batch_checkpoints`，儲存知識冊、執行、節點執行、階段、計劃雜湊、批次鍵、輸入雜湊、結果物件引用、建立時間；唯一鍵覆蓋節點執行、計劃雜湊及批次鍵。按專案的 `createCurrentStructure` / `schemaEvolution` 宣告空表，既有行無需預設值或轉換，不增加逐版本遷移鏈，不提升相容代際。
2. 檢查點正文使用獨立的 `knowledge_book_batch_checkpoint_ref` v1 引用及物件儲存，不把大段正文直接存 SQL，不偽裝成已完成節點。物件登記、引用固定和垃圾回收必須識別新的檢查點所有者；不得影響既有 node/run/release 引用及內容。
3. 只儲存完整且透過當前階段結構、覆蓋、引用和圖語法校驗的結果；不儲存半截流響應。質量檢查可以儲存完整的否決結論，否決不是失敗批次丟棄的理由，也不能被複用成透過。
4. 計劃檢查點包括凍結目錄/分配；寫作、編排與逐項驗收按照確定的批次鍵儲存。複用前完整匹配凍結配置、所有輸入/來源版本與內容清單、當前候選內容、階段演算法版本、模型非秘密配置指紋和請求範圍，並重新核驗來源許可權。模型憑據不寫入檢查點。內容修復、變更輸入或模型配置不能借用舊結果。
5. 老執行無批次記錄時繼續使用現有完整節點檢查點；執行尚未完成的節點時才開始記錄新批次。不從日誌或舊輸出猜測哪些批次已完成，不批次回填或轉換歷史資料。完整舊節點及釋出指標原樣儲存。
6. 檢查點格式未知、內容校驗失敗或應有物件丟失時明確停止，保留證據供處理；不得悄悄跳過檢查點重算來掩蓋資料丟失。顯式內容修復建立獨立範圍並保留舊記錄，不借用舊結果；相同範圍的模型或演算法變更要求新建執行，不自動轉換舊檢查點。
7. 寫入由執行租約保護，校驗租約、登記物件與安裝引用保持一致；取消後不繼續安裝結果，多例項不能同時覆蓋檢查點。最終節點聚合仍執行全覆蓋校驗並安裝現有完整輸出，釋出仍走現有許可權和必需質量檢查。
8. 初版只在原執行內繼續，暫不把批次跨執行復制到新重試。既有新重試的完整節點複用規則保持原範圍，不擴大舊執行的授權範圍。

## 資料保全、驗證與恢復

- 上線前備份資料庫及物件儲存，暫停執行器，完成所有例項更新及結構檢查後再啟用檢查點；不支援混合新舊執行器同時使用該功能。
- 驗證保留真實舊行的隔離 SQLite、PostgreSQL 17 / 18：空表增補、重複/併發啟動、結構差異拒絕且無部分寫入；還需使用實際已釋出舊版本建立的資料做升級驗證。
- 執行驗證覆蓋中途斷流/程序退出/超時/取消/租約丟失後的續跑、恰好一次安裝、許可權撤銷、來源和模型變化、未知版本/損壞/丟物件拒絕、負面驗收保留、不可複用範圍與最終釋出門檻。
- 已儲存物件隨檢查點引用固定；不能因節點尚未完成被回收。刪除知識冊沿用現有明確刪除流程；不因失敗、升級或雜湊不匹配清除使用者資料。
- 出問題時先暫停執行器並在當前版本停用批次續跑，保留檢查點及物件引用固定，修復後再繼續。需要整節點重新執行時由使用者顯式發起；舊檢查點保留供核對。降級到舊二進位制或恢復備份需另行核對新增資料和物件保全，不自動刪表、還原或覆蓋上線後的寫入。

此方案已按倉庫 AGENTS.md 的相容規則取得使用者明確同意。實現與驗證範圍見下文，不能外推為線上耗時保證。

<a id="实现与验证"></a>

## 實現與驗證

- 新表增加節點範圍雜湊 `scope_hash`、請求和計劃雜湊、獨立引用及授權後設資料。原有 node/run/release 引用約束沒有變化。內部 `evidenceInventory` 只儲存來源版本、定位、內容雜湊、實際權重和許可權引用，不復制來源全文。模型指紋不含 API 金鑰、別名和費率。
- 完整的宿主拆分計劃也會儲存，避免恢復後再次支付已知超限的父請求；不儲存截斷響應。原文修復透過既有顯式繼續流程建立新內容範圍，保留但不復用舊範圍。相同內容範圍的模型或演算法變更要求新建執行。
- `DOCA_BOOK_BATCH_CHECKPOINTS=off` 可在當前版本停用恢復而保留記錄及物件保護。已有檢查點時，原儲存格式回滾在修改前拒絕，需另行審定保全方案。
- 隔離完整流水線測試中，兩批寫作的第二批失敗；更換整個執行時繼續後，累計寫作請求由 2 次增至 3 次，第一批沒有重做，42 條判斷全部保留並走完驗收和釋出。另覆蓋長文規劃/分配、否決診斷及超限拆分計劃恢復。
- 真實檔案儲存測試在第一批提交後向程序傳送 SIGKILL；新程序換租約後讀取冷儲存，原批次呼叫為 0、缺失批次呼叫為 1，兩條檢查點均受到回收保護。
- 使用實際已釋出的 `smartdoca/doca:0.2.3` 映象建立 SQLite、PostgreSQL 17/18 資料後升級，13 組既有表記錄指紋、節點/執行/釋出正文 SHA-256、釋出指標和相容代際均保持一致；新表為空。重複/併發啟動及差異拒絕無部分寫入另有迴歸。
- 詳細結果見[隔離驗證記錄](verification/knowledge-book-checkpoints-2026-10-19/README.md)。
