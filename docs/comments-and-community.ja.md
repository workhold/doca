# コメント、ユーザーの可視性、通知

[中文](comments-and-community.zh-CN.md)

<a id="data"></a>

## データ

現在のベースラインではSQLiteとPostgreSQLがサポートされています。

- `users.public_id` 内部のUUIDとは別のユーザーIDです。作成時に小文字に正規化され、3～160文字で、文字と数字で構成されています。 `._@+-`ユニークなインデックスがそれを強制する。登録や管理者の作成で設定可能 `publicId`省略された場合、ログインが使用されます。表示名が変更されても変わりません。
- SSOプロファイルのフィールドは、プロバイダが設定したマッピングから来ます。適切な一意のユーザー名や他の必要なフィールドが欠けている場合は、 `/auth/complete` 返却 `needs_profile` そして、ユーザーがプロフィールを完了すると、ホストはプロバイダー名空間内でユーザー名を生成しません。同じ名前、メールアドレス、または公開IDのため、アカウントは決して統合されません。認証リンクは「プロバイダー plus 対象」のままです。新しいログイン方法を連結しても、元のユーザーIDは変わりません。
- `users.directory_mode` nullである可能性もあり、それはサイトに従う `settings.directory_mode`.
- `comments.body_json` 豊富なコメントのJSONです。 `body` 検索、要約、通知のために単純なテキスト形式で生成されます。削除されないコメントは有効でなければなりません。 `body_json`.
- `notifications` 追加する `actor_id`, `comment_id`、そして `dedupe_key`イベントとビジネスの変更が一緒にコミットされる。ユニークな `dedupe_key` インデックスは重複するイベントを停止する。

豊富なコメントはバージョン1で、テキストの段落ブロックや子供の記載、画像ブロックが含まれます。サーバーはユーザーテーブルからメンション名とIDを取得し、クライアントのラベルを信頼しません。1つのコメントは最大5,000文字、9枚の画像、50ブロックです。画像は現在のリソースに属しており、有効である必要があります。 `comment_image` または画像の添付。アップロードにはプライベートストレージ、画像のクリーニング、承認されたダウンロード機能が利用されます。コメント者はコメント用の画像をアップロードすることができ、それを使ってボディの添付ファイルをアップロードしたり変更したりすることはできません。

<a id="who-can-be-found"></a>

## 誰が見つけられるか

アドミニストレーターは、サイトのデフォルト値とユーザーごとのオーバーライド値を使って、ユーザーの可視性を設定します。

| モード | 新規ユーザー候補者 |
| --- | --- |
| すべて | サイトのアクティブユーザー |
| 関連する | 現在、明示的な文書/ライブラリの権限を共有しているユーザーで、継承、ライブラリの所有権、有効なリンクメンバー、有効なグループの割り当てが含まれます。また、同じアクティブユーザーグループのアクティブメンバーでもあります。 |
| なし | 候補者はありません。権限やメンションを追加するには、ユーザーUUIDを入力することはできません。 |

公開やログインによる可視性は関係を生み出しません。最後の権限/メンバーシップ関係を解除すると、それが消えます。既存の権限は変更または解除することができます。ポリシーが厳格化しても、既存のコメントや本文の言及は消えません。管理者ユーザーリストはこの検索ポリシーによって制限されません。グループ検索には独立した管理者ポリシーがあり、デフォルトでは参加したグループが対象になります。詳細は [ユーザーグループ](user-groups.ja.md).

ルートが確保されている `/api/v1`:

- `GET /users/lookup?q=` 呼び出し側の範囲内のアクティブユーザーを検索し、id、public_id、display_name、avatarフィールドを返します。アカウントとidのプレフィックスが一致します。display nameはファジーな一致です。最大20件です。検索ワイルドカードは通常のテキストです。
- `GET /admin/directory-policy` 返却 `{mode, revision}`.
- `PUT /admin/directory-policy` 取る `{mode, revision}`バージョン衝突は409です。
- `PUT /admin/users/:id/directory` 取る `{mode: "all" | "related" | "none" | null}`nullが再びサイトに続く。
- `GET /me`, `GET /users/:id/profile`、そして管理者ユーザーリストには含まれる `public_id`.

<a id="rich-text-comment-interaction"></a>

## リッチテキストコメントのインタラクション

編集モードでは、エディターのフローティング選択ツールバンの末尾にコメントアイコンが追加されます。読み取りモードでは、フォーマットツールなしでコメントアイコンのみが表示されます。提出にはコメンテーター以上の権限が必要です。

ブラウザの選択はSlateの範囲にマップされ、次にエディターのYjs相対位置アンカーにマップされます。現在のアンカーは1つの段落またはブロック内にあります。ブロックをまたいだ選択は、ユーザーに再選択を求めます。静かに切り捨てられることはありません。

元のテキストがまだ存在する未解決のルートスレッドは、それぞれ独立したカードです。デフォルトのマークは黄色の下線です。テキストやカードをクリックすると、両方がハイライトされます。位置はスクロール、ズーム、共同編集の更新に応じて再計算されます。

元のテキストが削除されたり、アンカーが無効になったり、ルートコメントが削除または解決された場合、カードやハイライトは隠れます。データベースはそのコメントを履歴や監査のために保持します。削除を元に戻すことで、アンカーが有効な時には解決されていないコメントが再び表示されます。

全文コメントと選択コメントには、豊富な機能が含まれています：@検索、画像のアップロード、編集、返信、削除、解決機能です。編集版のチェックは残ります。送信に失敗しても入力内容は削除されません。

削除アイコンはまず確認バブルを表示します。キャンセルすると削除要求は行われません。返信文では、著者、タイムスタンプ、引用は保持しつつ、コンパクトなスペースが使用されます。

5つのエディターすべてのコメントサイドバーには **解決されたコメント** アイコン。そのダイアログには、解決済みのルートコメントとその返答が表示される。著者や管理者はスレッドを未解決としてマークすることができ、現在の権限やコメントのバージョンが再確認される。失敗はリストに残り、エラーが表示される。さらにページを読み込むことができ、削除されたルートは除外される。有効なアンカーを持つスレッドを再開すると、そのカードとマーカーが復元される。

- `POST /resources/:id/comments` 取る `{richBody, parentId, anchor?}`返信はルートコメントのスレッドに残ります。
- `PATCH /resources/:id/comments/:commentId` 取る `{version, richBody?, deleted?, resolved?}`.
- `POST /assets?purpose=comment_image&resourceId=...&filename=...` アップロード可能なバイト数は、最大5MBです。サーバーが画像とアクセス権を検証します。

文書本文内の@はエディターメンション拡張子を使用します。候補者は同じスコープの検索から来ます。メンションノードには表示名だけでなく、ユーザーUUIDも保存されます。


5つのフォーマットすべてに永続的なコメントアンカーがあります。上記のSlate選択詳細はリッチテキストのみについて説明しています。スプレッドシートは独自のコメントAPIを通じて安定した行/列IDを取得し、構造変更後に現在の範囲を解決し、サーバ上での対象の存在を検証します。詳細は [共同編集](collaboration.ja.md).

コメントをクリックすると、5つのエディターそれぞれでそのコメントに関連する内容のみがハイライトされます。サイドバーを開くか、コメントリンクをたどっても以前の背景は復元されません。別のコメントをクリックするとハイライトが解除され、他の場所をクリックしてスレッドを解決したりサイドバーを閉じたりするとハイライトは消えます。ハイライトは表示状態であり、セルスタイル、形状の塗りつぶし、Yjsの更新、永続的なアンカーは記録されません。コメント画像はズーム、コピー、ダウンロード機能付きの共有画像ビューアで開きます。詳細は [0.2.23の検証](verification/editor-comments-2026-10-28.md).

<a id="notifications"></a>

## 通知

イベントには以下が含まれます `comment.created`, `comment.mentioned`, `document.mentioned`, `resource.permissions_changed` 新しい招待状のため `like.added`, `favorite.added`および所有権の移転。

- 俳優には通知されない。同じコメントの中で、所有者である人や返信される相手が受け取るのは単なる言及のみで、特別なコメントの通知はないと言われている。
- 言及だけではアクセス権は与えられません。受信者はアクティブなユーザーで、コメントを投稿した時に文書を読むことができる必要があります。そうでなければ通知はスキップされます。
- 安定したメンションノードIDによって新しいメンションが検出されます。別の新しいノードで同じユーザーをメンションすると、再び通知されます。古い更新を再再生したり、通常のテキストを編集したりすると、通知されません。
- リスト通知は、文書の権限を再確認します。削除または撤回された後、関連する通知は非表示になり、未読としてカウントされません。
- WebSocketが送信する `notifications.changed` 無効化として。クライアントは自身のリストを再取得する。ボディはブロードキャストされない。オフラインイベントはすでにデータベースにあり、再接続後に取得される。
- `GET /notifications?offset=0` 返却 `{items, unread, nextOffset}`1ページあたり50項目、俳優と文書のタイトルを含む。
- `POST /notifications/read` 取る `{ids:[]}`最大100件までで、呼び出し人の通知のみを更新します。
- `POST /notifications/read-all` 取る `{}` そして、発信者の通知をすべて読んだことを示します。

これらはアプリ内通知です。メール、SMS、第三者のプッシュ通知は送信されません。単一インスタンスのWebSocketデプロイメントだけでは、マルチインスタンスバスを自動的に追加することはできません。複数のレプリカがこの設定を使用しています。 [水平スケーリング](horizontal-scaling.ja.md).

<a id="verification"></a>

## 検証

テスト内容には、公共IDの衝突、SSO識別子、可視性、ユーザーごとのオーバーライド、関連性のない公開文書、権限の回避、構造化コメント、画像の隔離とコメンテーターのアップロード、通知の重複排除、アクセス権のないユーザーのスキップ、取消後に通知の隠蔽、自分自身の読み状態のみの更新、共同編集の再再生、そして繰り返される@が含まれます。

ブラウザチェックでは、メモリ内の文書とシミュレートされたユーザーが使用される。実際の文書にテストコメントを書き込むことはない。ツールバーのボタン、読み取り不可ボタン、リッチメンション、両方向での黄色のハイライト表示、解決時に隠れる機能、元のテキストが削除されたときに隠れる機能などが確認される。
