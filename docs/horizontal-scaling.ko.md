# 단일 인스턴스 및 수평 확장

[中文](horizontal-scaling.zh-CN.md)

도카는 추가 인프라 없이 단일 인스턴스 모드를 사용합니다. 로컬 업로드 디렉터리인 SQLite과 프로세스 내 실시간 버스는 개인, 소규모 팀 또는 테스트 환경에 적합합니다. PostgreSQL, 공유 객체 저장소, Redis는 여러 애플리케이션 복제본이 실행될 경우에만 설정해야 합니다. 두 모드 모두 동일한 비즈니스 프로토콜을 사용합니다. 내장된 SQLite-to-PostgreSQL 데이터 전송이나 이중 쓰기 경로는 없습니다. 지원되는 데이터베이스 업그레이드는 다음과 같습니다. [데이터베이스 업그레이드 계약](database-schema-evolution.ko.md).

<a id="capability-matrix"></a>

## 능력 매트릭스

| 능력 | 단일 인스턴스 | 여러 복제본 |
| --- | --- | --- |
| 데이터베이스 | SQLite 또는 PostgreSQL | PostgreSQL; 모든 복제본은 동일한 데이터베이스를 사용합니다. |
| 문서 협업 및 알림 | 프로세스 내 브로드캐스트 및 존재성 | Redis Pub/Sub 및 Redis presence |
| 로그인, 업로드, 공개 봇 속도 제한 | 프로세스 내 카운터 | Redis 카운터 |
| 파일들 | 로컬 지속적 디렉터리 | S3와 호환되는 스토리지, 또는 모든 복제본이 실제로 공유하는 파일 시스템 |
| CDN | 선택적 | 선택적입니다. 읽기 속도를 높이는 데만 도움이 되며 공유 스토리지를 대체하지는 않습니다. |
| 백그라운드 작업 | 데이터베이스 임대 계약 | 같은 임대 계약이에요; 어떤 복제품도 일자리를 요구할 수 있고, 실패는 다시 시도할 수 있습니다. |
| 모바일 푸시 | 데이터베이스 아웃박스 | 같은 출고 및 임대 절차; 대기열을 단 하나의 프로세스에만 유지하지 마세요. |
| 스키마 | 첫 번째 시작으로 현재 기준선이 생성됩니다. | 한 개의 인스턴스가 첫 번째 배포 전에 빈 기준선을 생성합니다. |
| 건강 | `/live` 그리고 `/ready` | `/ready` 또한 데이터베이스와 Redis를 확인합니다. |

<a id="single-instance"></a>

## 단일 인스턴스

때에 `DOCA_REDIS_URL` 설정되지 않았으며, 실시간 이벤트, 존재 상태, 속도 제한은 프로세스 내에 유지됩니다. Redis는 필요하지 않습니다. `pnpm dev`, `pnpm start`하나의 Compose 컨테이너가 빈 데이터베이스에서 현재 기준을 생성한 다음, 현재 DDL과 일치하는 기존 구조들을 조정합니다.

이 모드에서는 두 개의 복제본을 실행하지 마세요. 로드 밸런서의 스티키 웹소켓은 잠시 동안 문제를 숨겨줍니다. 알림, 권한 철회, 온라인 사용자, 그리고 전역 제한은 여전히 분리되어 있습니다.

<a id="minimum-multi-replica-configuration"></a>

## 최소 다중 복제 구성

모든 복제본은 동일한 설정을 필요로 합니다:

```dotenv
DOCA_DATABASE=postgres
DOCA_DATABASE_URL=postgresql://user:password@postgres:5432/doca
DOCA_DATABASE_POOL_MAX=10
DOCA_REDIS_URL=redis://redis:6379
DOCA_REDIS_PREFIX=doca-production
DOCA_TRUST_PROXY=10.0.0.10/32
```

오케스트레이터는 설정할 수 있습니다. `DOCA_INSTANCE_ID` 패드나 컨테이너 이름으로 지정해야 합니다. 그렇지 않으면 각 프로세스가 무작위 ID를 생성합니다. `DOCA_REDIS_PREFIX` 하나의 Redis를 공유하는 환경들을 분리해야 합니다. `DOCA_TRUST_PROXY` 반대 프록시 주소나 CIDR 주소만 나열됩니다. 더 넓은 범위를 사용하면 클라이언트가 IP를 위조하고 감사 및 제한 수를 초과할 수 있습니다.

출시 순서:

1. 빈 데이터베이스에 인스턴스를 시작하여 기준값을 생성하세요. 여러 복제본이 함께 빈 데이터베이스를 초기화하도록 하지 마세요.
2. 동일한 릴리스 및 설정으로 다른 복제본들을 시작하세요. 승인된 구조적 변경 사항은 스키마 잠금 하에서 조정됩니다; 지원되지 않는 또는 검토가 필요한 차이점들은 부분적 쓰기 없이 시작을 중단시킵니다.
3. 로드 밸런서는 사용합니다 `/ready` 교통을 위해 `/live` 프로세스의 건강을 위해서입니다. WebSocket 업그레이드와 일반적인 드레인이 허용되어야 합니다.
4. 드래인 준비 상태를 확인하고, 중지 유예 기간 내에 HTTP/WebSocket 연결을 종료하도록 합니다. 중지/시작 순서에 대한 릴리스 요구사항을 준수하세요; 롤링 배포는 서로 다른 호스트 버전 간의 호환성을 보장하지 않습니다.

Redis가 설정된 후에는 반드시 사용해야 합니다. 시작 연결 실패, 이후의 서비스 중단, 또는 준비 상태 검사 실패가 발생해도 로컬 버스로 무시로 전환되지 않습니다. 이를 통해 클러스터가 여전히 건강해 보이는 여러 개의 단일 인스턴스로 분할되는 것을 방지할 수 있습니다.

<a id="consistency"></a>

## 일관성

공동 작업으로 번역된 업데이트는 PostgreSQL 트랜잭션에 저장되고 확인된 후, Redis가 다른 복제본들에게 알립니다. Redis는 문서 로그가 아닙니다. 중복된 이벤트는 프로토콜에 의해 제거됩니다. 짧은 손실은 재연결 후 데이터베이스에서 복구됩니다. 존재 시간이 만료되면 장애가 발생한 인스턴스가 사라집니다.

파일 인식, 텍스트 추출, 지식-북 워크플로우, 모바일 푸시 기능은 데이터베이스 작업과 임대를 사용합니다. 발생 키는 여러 복제본이 함께 스캔할 때 단 하나의 비즈니스 발생만 생성되도록 보장합니다. 처리자는 중복 작업이 되지 않아야 하며, 임대가 만료된 후 다른 복제본이 다시 시도할 수 있기 때문입니다.

<a id="capacity"></a>

## 용량

- 전체 데이터베이스 연결 수는 복제본 수에 해당합니다. `DOCA_DATABASE_POOL_MAX`PostgreSQL 또는 pooler 제한을 준수하고, 작업 및 백그라운드 작업을 위한 공간을 남겨두세요.
- 로컬 디스크는 여러 호스트의 업로드를 저장할 수 없습니다. CDN은 읽기만 캐싱합니다. 객체는 S3나 공유 파일 시스템에 남아 있습니다. 기존에 존재하는 이름의 스토리지입니다. `storage_profile` 항상 사용 가능해야 합니다.
- Meilisearch, S3, 및 메시지 게이트웨이는 모든 복제본에 동일한 설정과 데이터를 표시해야 합니다. 자격 증명은 공유 데이터베이스에 저장됩니다. 네트워크 접근, 허용 목록, 키 관리는 여전히 배포의 역할입니다.
- 공유 데이터베이스는 원하는 플러그인 출시 정보와 불변한 ZIP 파일을 공유 스토리지에 저장합니다. 각 복제본은 자신만의 쓰기 가능한 설치/캐시 디렉터리를 필요로 합니다.`DOCA_PLUGINS_DIR`); 스타트업이 아카이브에서 그것을 검증하고 복구합니다. 각 복제본을 수동으로 재시작한 후에 작업이 적용됩니다. 동일한 버전을 계속 유지하세요; 참조하세요 [플러그인 배포](plugin-deployment.ko.md).
- Redis는 인증, TLS 또는 프라이빗 네트워크, 메모리 제한, 알림 기능을 사용해야 합니다. 데이터베이스와 객체 저장소는 여전히 별도의 백업이 필요합니다. Redis를 잃어버리면 문서 텍스트가 손실되지 않아야 하지만, 실시간 전달, 존재성, 그리고 전 세계적인 제한 기능은 작동하지 않습니다.
- `/ready` 이 복제본이 데이터베이스와 실시간 클러스터에 접근할 수 있음을 증명할 뿐이며, 공동 작업, 객체 저장소, 검색 및 메시징의 엔드투엔드 검사를 대체하지는 않습니다.

<a id="still-needs-an-external-rehearsal"></a>

## 여전히 외부 리허설이 필요합니다.

이 코드는 문서 업데이트, 커서, 존재 여부, 공유 제한, 그리고 두 애플리케이션 인스턴스 간의 데이터베이스 임대 또는 아웃박스 기능을 포함합니다. 실제 배포 전에 대상 인프라에서 PostgreSQL, 관리형 Redis, S3, WebSocket 드레인, 롤링 업데이트를 연습해야 합니다. 실패 상황을 시뮬레이션하기 위해 Redis를 일시 중단시키고, 작업을 실행 중인 복제본을 종료시키고, 편집 중에 접근 권한을 취소하며, 일치하지 않는 데이터베이스 기준을 제공하고, 객체 저장소의 타임아웃을 발생시켜야 합니다.
