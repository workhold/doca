デスクトップ機能が空の状態を追加する `desktop_auth_flows` そして `desktop_sessions` 現在のDDLを通じたテーブル `schemaEvolution`互換性の生成を変更したり、ブラウザ/モバイルセッションを変換したりすることなく。リモート専用のデスクトップクライアントは、以前の試用状態を保持します。 `local-v1` 開くことや移行することなくデータを利用する。参照 [デスクトップクライアント](desktop-client.ja.md) そして [機能検証](../specs/006-desktop-client/validation.md)デスクトップ認証情報が発行された後のアプリケーションのダウングレードには、別途合意された保存および承認計画が必要です。

## 現在の目標構造

最新のDDL `packages/db/src/create-schema.ts` そして、その構造ヘルパーが唯一のターゲット構造です。新規作成とアップグレード検査が使用されます。 `createCurrentStructure`通常の追加変更に対しては、リリースごとのSQLマイグレーションの順序はありません。

対応するKyselyタイプを保持する `packages/db/src/schema.ts` このDDLと一致しています。 `schemaEvolution` これは、サポートされている互換性生成範囲内でレビューされたテーブル/列の追加項目の許可リストであり、過去のSQLスクリプトの集合ではありません。宣言の追加によって型の変更やデータの変換が安全になるわけではありません。まだサポートされている古い構造に必要な宣言を、結果として生じるサポートの変更について合意しない限り、削除してはいけません。

`schema_baseline.id` すべてのリリースではなく、互換性のある世代を特定する。現在の世代は `doca-2026-10-12-book-payload-storage-v1`承認された [知識ブックスキーマの一致](knowledge-book-payload-storage-plan.md) 0.1.24スタートアップアラインがリリースされました `doca-2026-10-09-history-storage-v1` 通常の現在のDDL調整機能を通じてデータベースを操作し、その後同じトランザクション内でターゲット構造を記録する。古いSQL文の結果や出版ポインタを含む、既存のビジネス行は一切変更されない。自動的なデータ形式の変換やクリーニング、レガシーランタイムリーダーは存在しない。残った古い結果は手動で処理する必要がある。ターゲット構造は記録されるが、古いJSONの可読性は確保されない。起動前に、それらの結果をネイティブオブジェクト形式で保持する必要がある場合、従来のオフラインでのバイトレベルの保守機能は依然として利用可能である。明示的な履歴や中断された変換機能も残っている。

目標は、中間のリリーススクリプトを再実行することなく、サポートされている古い構造から現在の目標構造へ直接アップグレードすることです。単に一致する生成だけでは不十分であり、構造的・意味論的な違いも合意されたポリシーを満たさなければなりません。これは、すべての歴史的なデータベースや手動で変更されたデータベースからのアップグレードを保証するものではありません。重大な不適合な変更が新しい生成を導入する場合、拒否、明示的な変換、保存、復元についての合意が得られるまではそのような変更は行われません。

## スタートアップの決算

スタートアップはデータベース/スキーマのロックを取得し、インストールされた構造を現在のDDLから作成された参照と比較する。検査内容には列、型、デフォルト値、プライマリ/外部/ユニーク/チェック制約、インデックスが含まれる。PostgreSQLはセッションローカルの一時的な参照テーブルを使用するが、SQLiteは別のメモリ内データベースを使用する。どちらもユーザー文書を使用しない。

列の空値可能性は、この方法でチェックされます `pg_attribute.attnotnull` PostgreSQL上です。PostgreSQL 18では、テーブル列も記録されます。 `NOT NULL` 制約がある `pg_constraint`これらの重複する項目は、テーブル制約の比較から除外されます。これにより、承認された必要列の追加を、新しい項目を考慮せずに行うことが可能になります。 `NOT NULL` 無関係な制約変更としてのエントリ。承認された列の整列ポリシーの下では、既存の行を確認した後、ネイティブのALTER COLUMNを使用して既存のnullabilityを整列することができます。プライマリ/キー/チェック制約の変更は依然として審査が必要です。PostgreSQLを参照してください。 [18](https://www.postgresql.org/docs/18/catalog-pg-constraint.html) そして [17](https://www.postgresql.org/docs/17/catalog-pg-constraint.html) カタログ。

`schemaEvolution` 新しいテーブルやフィールドがレビューされたと宣言される。Nullableの追加項目や、文字列による歴史的デフォルトを持つ必須フィールドは、明示的に宣言されると自動的に追加される。新しい通常のインデックスも作成可能である。デフォルトは歴史的なビジネス決定を示すものであり、調整者によって作り出されるべきではない。そのようなデフォルトのない必須新フィールド、サポートされていない型/デフォルト/制約の変更、ユニークインデックスの検証、削除、不明なオブジェクトは具体的な結果を生む。 `SchemaReviewRequired` 持続的な変更が適用される前に計画を立てる。自動的な削除やリセットはない。

| 違い | スタートアップの行動 |
| --- | --- |
| 空のデータベース | 現在の構造と初期のシステム行を作成します。 |
| 欠落しているテーブルを確認した | テーブルとその宣言されたインデックスを作成します。歴史的バックファイルの処理は行われません。 |
| ナッビル可能な列、または承認された文字列のデフォルトを持つ必須列をレビューした | 列を追加します。既存の行には合意された歴史的値が与えられます。 |
| 既存のテーブルに通常の非一意インデックスが欠落している | インデックスを作成し、構造を再確認する。 |
| PostgreSQLのvarcharの長さが増加する、または既存のデフォルト/null許可が異なる | ネイティブのALTER COLUMNを使用して整列させ、すべての旧値を保持し、強化前にNULLがないことを確認する。 |
| SQLiteのナルビリティは異なる | バンドルされているSQLite 3.53.4のネイティブのALTER COLUMNに合わせる。まず古い行を検証する。テーブルの置換や foreign-keyの無効化は行わない。 |
| SQLiteのデフォルトが異なる；型変換/長さの短縮；プライマリ/外部/ユニーク/チェック制約やインデックスの定義が異なる | レビュー計画を報告し、持続的な変更が起こる前に停止する。 |
| 必要な列には承認された歴史的値がない；既存のテーブルに新しいユニークインデックスを追加；名前変更または削除；不明なテーブル；保持されているビジネスセマンティクスの変更 | 別途承認された保存・変換計画が必要です。破壊的または意味論的なアップグレードを無意識に行ってはいけません。 |

既存の行については、新しいフィールドが何を意味するか、その値が以前のビジネス行動をどのように保持するかを説明する必要がある。新規レコードのデフォルト値と歴史的な行のデフォルト値は異なることがある。権限、共有、認証情報、リソースの制限は、古い行に便利な値を入力することで無意識に解除されるべきではない。名前変更は、フィールドの削除や再作成としてではなく、データの保存の観点から審査される必要がある。

SQL構造が同一である場合、構造的比較ではJSON形式やビジネス意味の変化を検出できない。開発者は依然としてその互換性に関する決定を確認し、合意された検証/変換または生成ゲートを実装する必要がある。清潔な構造的比較はセマンティック互換性の証拠ではない。

最新のインストール済みテーブル/カラムのフットプリントに置き換えられます `schema_baseline.structure_json` 成功した調整の後。以前にインストールされたテーブルやフィールドがなくなった場合、元の導入が自動的であったとしても、データ損失の可能性があると報告されます。プラグインのビジネステーブルは、 [コアとは別の共有ビジネスデータベース](plugin-database-isolation.ja.md)ホストストレージフォーマット3は、0.1.25フォーマット2に代わるものです。既存の古いインストールは、永続的な変更前に拒否され、通常は以前のホストからアンインストールされ、プライベートデータの移行なしで再インストールされます。コアDDLや互換性生成は変わりません。残りの古いもの `plugin_<56 hex characters>` テーブルはレビューが必要な未知のテーブルです。起動時にはそれらを保持し、構造的変化が起こる前に停止します。アップグレード前に以前のホストで完全な通常のアンインストールを行ってください。自動的な削除やデータ移行はありません。プラグインのビジネスデータバージョンは依然として独自の公開ストレージ契約を使用しています。

受け入れられた変更やフットプリントの記録はトランザクション的なものであり、コミット前に再確認されます。失敗した操作はその全てを元に戻します。再起動を繰り返すことでデータと設定値が保持されます。審査が必要な差異については、別途承認されたデータ保存/変換計画が必要です。起動操作では破壊的なバイパスはできません。

持続的なDDLが適用される前に、全体の計画が分類されます。何か異なる点が審査が必要な場合、その際には他の自動的な変更は一切適用されません。PostgreSQLはスキーマロックを取得した後に新たなカタログ読み取りを行うため、同時実行中のホストは以前にコミットされたアップグレードを確認できます。無効な記録されたフットプリントも起動を停止します。

## 承認されたネイティブ列の整列（0.2.10）

オーナーは、同じvarchar型の拡張や、現在のDDLのデフォルト設定やnullabilityの同期をPostgreSQLで承認しました。SQLiteでは、nullabilityはネイティブのALTER COLUMNを通じてのみ同期されます。サポートされていないデフォルトの変更は起動を停止させるため、テーブルの再構築、 writable_schemaの編集、値のバックフィル、または自動的なダウングレードは行われません。歴史的なビジネスセマンティクスへの将来の変更についても、現在のDDLを変更する前に合意が必要です。コアポリシーは明確にアライメントを可能にしています。厳格な検査と既存のオフライン書籍ストレージ変換ゲートは、それぞれ独自のポリシーを保持しています。

すべての差分は、持続的なDDL前に分類される。PostgreSQLは古い行をチェックする前に影響を受けるテーブルをロックする。SQLiteは既存の書き込み/スキーマトランジションを使用する。NOT NULLを防ぐNULL、サポートされていない差分、不明なSQLiteトリガー/ビュー、または失敗した再検査は、他の場合で承認された追加項目やインデックスを含む、全体的な試みを拒否する。すべての承認された属性とフィットレコードの記録は一緒にコミットされる。既存のデフォルトは古い行を再書き込むことはなく、NOT NULLを削除してもプライマリ/外部/ユニーク/チェック制約は変わらない。コラッリング、アイデンティティ、生成列の属性は自動変更には許可されていない。

PostgreSQLの現在のassets.purposeのターゲット値はvarchar(32)であり、既存の18文字のai_image_candidate値に十分です。SQLiteはvarchar(16)の宣言を維持しており、その長さには制限を設けていません。新たに作成されるものや一時的なPostgreSQL参照カタログは、同じエンジン固有の現在のDDLを使用します。起動時には、行を削除したり切り捨てたりすることなく、リリースされたPostgreSQLのvarchar(16)を拡大することができます。縮小が必要になるようなより大きなインストール幅は拒否されます。互換性の生成は変わりません。

検証では、0.2.9のソースコミット655e7ecf71274417d2cf5f352f9151612c702859を使用して孤立したデータベースを作成し、SQLiteおよびPostgreSQL 17/18上の全131の元のテーブルハッシュを保持しています。PostgreSQLのカタログの違いは、目的長さが16→32に限られており、SQLiteは変更されていません。別途報告される不具合には、ネイティブのnullability/default動作、親/子行、変わらないSQLiteのルートページ/rowid、繰り返し/同時実行、NULL/type/shrink/unknown-objectの拒否、およびトランザクションロールバックが含まれます。詳細は…を参照してください。 [証拠を明らかにする](verification/ui-image-ark-plan-2026-10-23.md)デプロイ前にバックアップを行い、すべてのホストを同じリリースで維持すること。自動的なダウングレードや混合バージョンの保証はありません。

## 必要な開発およびリリースワークフロー

1. 影響を受けた古いバージョン、スキーマの生成、コードパス、保存された行、保持されているフォーマットを特定する。歴史的値、検証、復元を含め、どのような違いが保持されるか、追加されるか、拒否されるか、または明示的に変換されるかを説明する。リポジトリの互換性規則に基づき合意を得る。
2. 最新のDDLと対応する型を更新する。承認されたサポートされる追加項目のみを宣言する。 `schemaEvolution`別途承認されたメカニズムを通じてルートのセマンティック変換を行う。通常のアップグレードでは、共有されるターゲットと調整器を引き続き使用する必要がある。
3. 影響を受ける古い構造物に含まれる代表的な既存行のための孤立した回帰フィクスチャを追加または調整する。保持される値、新しいデフォルト値、該当する場合の空の新しいテーブル、繰り返し/同時起動、およびレビューや検証によってアップグレードが不可能な場合の変わらないデータ/構造を確認する。以前にインストールされたフィールドが失われた後に無意識に再作成されないかを確認する。
4. SQLiteの調整回帰とPostgreSQL 17/18のマトリックスを実行する。 `.github/workflows/database-upgrade.yml` PostgreSQLのスキーマやフォルダのケースを管理する。新しいビジネス変更には、それに適したケースを自ら追加する必要がある。SQLiteのパスだけではPostgreSQLとの互換性は確立されず、最新のスキーマを逆転させても、実際にリリースされたバージョンのアップグレードとはならない。
5. リリース前に、影響を受けたリリース版を使用して孤立した旧データベースを作成し、リリース候補版でアップグレードします。アップグレード後の保持されているビジネスデータと影響を受けた機能を確認し、再起動します。テストされたバージョン、データベースエンジン、および材料の制限事項を、リリース検証およびアップグレードのメモに記録します。

合成アカウントと孤立したテストデータベース/文書を使用する。 `tests/database.ts` 各フィクションに対して孤立したPostgreSQLスキーマを作成し、クリーニングします。ユーザーデータに対して破壊的なフィクションや共同編集編集チェックを実行することは絶対に避けてください。変更がそれらの領域に入った場合は、該当する共同編集/プラグイン契約を読んでください。

契約およびその中国語版は、実施内容と一致していなければならない。新しい自動的な動作、サポートの変更、セマンティックの例外については、共に合意し、実装し、記録し、検証する必要がある。将来の機能を記述した文書は、その機能をサポートするという証明ではない。

使用されていない古いMCPランタイムは、所有者の承認を得て廃止されました。4つの新しい空のテーブルがあります。`mcp_user_settings`, `mcp_services`, `mcp_contexts`, `mcp_tool_calls`)は現在のDDLによって宣言されている。 `schemaEvolution`、変更せずに `doca-2026-10-12-book-payload-storage-v1`既存の行には推測された助成金や認証情報は与えられません。個人設定の行が欠けているということは、MCPが無効になっていることを意味します。無効な状態です。 `ai_mcp_keys` テーブルと行は保持され、実行時の読み取りやトークン変換は行われない。古い認証情報は拒否される。既存のコンテンツ、権限、設定はすべてそのまま保持される。

それ [MCP受入記録](verification/mcp-2026-10-20/README.md) デプロイでは、SQLiteおよびPostgreSQL 17/18の0.2.4のデータを実際にリリースし、120の元のテーブル用のハッシュを保持し、部分書き込みなしの空の追加、繰り返し/同時起動、拒否を検証します。デプロイ前にバックアップし、サーバー/Webを一緒に更新します。古いバイナリは新しいトークン/グレント契約を強制しません。アプリケーションのダウングレード前に新しい記録を保持し、復元計画を合意します。テーブルの削除、自動変換、ダウングレードアダプターは導入されません。

## デプロイと復旧

承認された [知識ブックバッチチェックポイントの追加](knowledge-book-generation-performance.ja.md) 追加する `knowledge_book_batch_checkpoints` 現在のDDLを通して空の状態 `schemaEvolution`内で `doca-2026-10-12-book-payload-storage-v1`既存のノード/実行/リリース行、参照制約、v1形式、権限、出版ポインタは変更なし。古い結果は推測されたりバックフィルドされたりすることはない。個別のプライベートチェックポイントv1形式は厳格に検証される。 [確認記録](verification/knowledge-book-checkpoints-2026-10-19/README.md) SQLiteおよびPostgreSQL 17/18に関する実際にリリースされた0.2.3データ、保持される行/ボディバイト、部分的な書き込みなしの繰り返し/同時起動および拒否をカバーする。すべての実行器とガベージコレクターを一緒にアップグレードする。古いバイナリでは新しいチェックポイント参照を保護できない。既存のチェックポイントは、別の保存計画が承認されるまでオフラインボディストレージのロールバックをブロックする。

展開前にデータベースをバックアップしてください。新しいフォルダ共有制限を有効にする前に、すべてのホストインスタンスを更新してください。古いコードでは新しい制限や同意プロセスが適用されないため、複数バージョンの操作はサポートされません。このレビューされた追加変更には、互換性の向上やオフライン移行コマンドは必要ありません。

データベース/ファイルボリューム、デプロイアイデンティティ、および元の状態を保持する `DOCA_CREDENTIAL_MASTER_KEY`構造的に互換性のある追加機能のアップグレードだけでは、安全な複数バージョンの動作やアプリケーションのダウングレードは成立しません。これらを、影響を受けるビジネス行動と照らし合わせて評価する必要があります。

失敗したスタートアップアップグレードの場合、トランザクションは元の構造とデータを保持します。成功したデプロイ後は、旧アプリケーションの動作に戻るためには別途検討する復旧計画が必要です。アップグレード前のバックアップを復元すると、後続の書き込みが失われ、旧ホストでは新しい制限を適用できません。このようなロールバック前に、新しい記録を保持してください。審査が必要な差異を解決するためにデータベースを削除しないでください。

検証には、孤立したSQLiteファイルとPostgreSQL 17/18スキーマが使用される。既存の行がある以前の構造、空の新しいテーブル、null可能なフィールドと必須/デフォルトのフィールド、繰り返し/同時起動、変更されたデフォルト/null可能性、保持されたプラグインデータ、そして失われたインストール済みフィールドの拒否が含まれる。リリース0.1.22では、新しいイメージへのアップグレード前に、PostgreSQL 18に対して実際の0.1.20イメージを起動する。フォルダテストでは、通知/チケット、同意、ライブ権限、有効期限、同時リンクの受け入れが対象となる。

## 承認されたブラウザアシスタントの追加

最初のリリースでは、現在のDDLを通じて7つの空のテーブルが追加されます。 `schemaEvolution`、変更せずに `doca-2026-10-12-book-payload-storage-v1`: `browser_clipper_profiles`, `browser_clipper_connections`, `browser_clipper_activations`, `browser_clipper_receipts`, `browser_clipper_assistant_sessions`, `browser_clipper_web_sessions`、そして `browser_clipper_login_codes`すべての元の文書、許可、設定の行は残ります。

リリース前に、オーナーがv1アクティベーションパッケージ/180日間のトークンをウェブサイトセッション限定の認証に置き換えることを明確に承認しました。古いv1設定、アクティベーション、トークンは変換なしで拒否されます。最初の5つのテーブル、古い認証情報の列/記録、プロファイル、受領書、会話は保持されますが、古いアクティベーション記録は無効です。新しい2つのテーブルは空の状態から始まり、推測されたグレードは受け取れません。既存のモバイル、MCP、ビジネスプラグインの認証は別々のままです。

公開サイトの設定は厳格なバージョン2です。SHA-256検証者の挑戦を含む60秒間のコードが、正確なウェブサイトのセッションとインストール接続に基づく10分間のアクセスと交換されます。ログアウトやセッションの無効化によりアクセスが無効になり、接続の無効化では、明示的に復帰するまで自動再認証がブロックされます。ブラウザ起源のジョブIDにより、同じ会話内でのキャンセルと通常のウェブサイトのジョブが区別されます。承認された文書や画像は、ログアウト、認証情報のローテーション、無効化によって決して削除されません。

それ [ログイン受け入れ記録](verification/browser-clipper-login-2026-10-21/README.md) SQLite / PostgreSQL 17/18向けの実際にリリースされた0.2.6のファイチャントは、124の元のテーブルのハッシュが保持され、7つの空のテーブルが追加され、再起動や同時起動が繰り返される。別のファイチャントでは、事前起動時のv1行が保持され、空のセッション/コードテーブルが追加されるが、v1へのアクセスは拒否され、部分的な書き込みがない場合はレビューが必要な差異も拒否される。データベース、ファイルボリューム、認証マスターキーをバックアップした後、サーバー、Web、拡張機能を一緒に更新する。ダウングレードには、別途承認された保存と承認計画が必要であり、旧バイナリを使用すれば旧の認証処理を復元できる。旧の認証アダプター、自動変換、テーブルの削除、データのリセットは導入されない。
