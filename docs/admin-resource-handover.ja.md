# 管理者リソースの引き継ぎ

[中文](admin-resource-handover.zh-CN.md)

中 **管理 → ユーザー**活発なシステム管理者が開く **資源を提供する** 障害者向けアカウントの場合は、有効な受信者とリソースエントリを選択し、実際の変更内容を確認・承認します。元のアカウントは引き続き無効のままです。通常のユーザーは、3つのエンドポイントのいずれも使用できません。

<a id="scope"></a>

## 範囲

インベントリは、既存のリソース、フォルダ、ファイル、権限記録から管理メタデータを読み取ります。文書の内容やプライベート認証情報は読み取りません。

- 文書、図書館、ナレッジブック：選択されたリソースとソース所有の子孫を移行する。他の人が所有権を保持し、関連コンテンツは別途記載される。既存の図書館所有者の権限は受け取り人に適用される。
- 文書画像と添付ファイル：文書と共に転送されたアセットやディレクトリ項目です。それらは独立して選択することはできません。元のアップローダーや履歴の著者は変わりません。
- 通常のフォルダ/ファイル：ソース側が所有する子フォルダやファイルを転送します。親が転送されず、また受信者が所有していない場合、選択されたネストされたフォルダや独立したファイルは受信者の個人用ルートに移動されます。プレビューではこの移動が表示されます。
- 保持文書/ライブラリ助成金：明確に選択された活発な地域の助成金源が直接助成金受給者となり、その源から削除される。子孫範囲は保持され、リンクトークンはコピーされない。
- 共有フォルダの権限付与：既存の高い役割を下げることなく、受信者のフォルダにマージされる権限付与を行い、その後選択したソースの権限付与を削除します。
- 破壊されたリソース：所有権は移転する可能性があり、削除された状態はそのまま保持される。

個人用AIファイル、プライベート会話、認証情報、プラグインのビジネス記録は除外されます。既存のAI/知識セッションファイルの結合、通常のロックされたファイル、認識されないメタデータは保護され続けます。文書添付ファイルのファイルマネージャーロックは、その文書の転送を妨げません。保護されたエントリは、なぜ選択できないのかを説明し、選択されたディレクトリ内の保護されたファイルは全体のバッチをブロックします。

<a id="preview-and-permission-checks"></a>

## プレビューと許可チェック

プレビューには、所有権、権限、添付ファイルの変更、移動、そして所有権が変わらない関連項目が表示されます。親項目を選択すると、その子項目も表示されます。各バッチでは最大500件の在庫項目を選択でき、さらに多くの子項目が表示される場合もあります。在庫情報と変更内容は50行のページで表示されます。

既存の高レベルの受信者権限は保持されます。比類のないノード/子孫の役割、アクセスを拡大するソース子の制限、そして明確な受信者制限が衝突を引き起こし、確認を無効にします。これらの権限を既存の権限ワークフローを通じて確認するか、選択を変更してください。引き渡しはそのような制限を無効にしたり、無関係な相続権利をコピーしたりしません。

選択された文書/フォルダにおける送信元または受信者の招待がキャンセルされるため、後で受け入れることで引き継ぎが上書きされることはありません。文書の招待はチケットとしてアーカイブされ、フォルダの招待はキャンセルされた行とチケットが保持されます。他の人の招待はそのまま残ります。プレビューにはキャンセル数が表示されます。公開状態、リンクの定義、その他の共同作業者は既存の設定が保持され、公開アクセスがユーザーブロックリストになることはありません。

<a id="consistency-and-audit"></a>

## 一貫性と監査

在庫管理とプレビューには共通のデータベーススナップショットが使用されます。実行時には、関連するアカウント、リソース、助成金、添付ファイル、ディレクトリの内容を含む指紋を再計算します。状態が変更されると、確認情報が無効になり、409を返します。再びリフレッシュとプレビューを実行します。同じバッチに対する同時確認は一度だけ成功します。

1回のトランザクションで所有権が確定し、権限付与、招待決定、インデックス処理、セキュリティ監査が行われる。既存の受信者認可/割当ポリシーは引き続き機能する。何らかの失敗が発生した場合、全体のバッチがリセットされる。保存されたオブジェクトは移動も削除もされない。文書の内容、履歴、アップローダー、元の著者はそのまま保持される。コミット後、アクティブな権限が更新され、関与するアカウントに通知が行われる。

それ `user.resources_handed_over` セキュリティ監査では、実際の管理者、情報源、受信者、指紋、変更内容、および関連する以前のメタデータが記録されます。関連性のない個人受信者のデータは除外されます。実行は同期で行われ、再開始可能なバックグラウンドジョブではありません。ブラウザが切断されたり、応答が失われたりした後は、別のバッチを試す前に在庫を再スキャンする必要があります。

この機能は、スキーマの変更や過去の変換なしで、既存のテーブルと保持されたフォーマットを使用します。自動的な逆移行や権限のロールバックはありません。確定したビジネス決定に対する修正には、監査や現在の所有権/権限を再検討する必要があります。

<a id="api-and-verification"></a>

## APIと検証

- `GET /api/v1/admin/users/:id/resource-handover`：在庫
- `POST /api/v1/admin/users/:id/resource-handover/preview`: `targetUserId`, `keys`.
- `POST /api/v1/admin/users/:id/resource-handover/execute`同じ選択肢に加えてプレビューも `fingerprint`.

実行する `pnpm exec vitest run tests/resource-handover.test.ts` サービス/APIのレグレッションのため。実行する。 `pnpm exec tsx scripts/qa-resource-handover.mts` 孤立したSQLite/アカウント/文書/ストレージに対する実際の管理UIのため。結果はここにあります。 `artifacts/verification/resource-handover/`これらのチェックはPostgreSQLの実行時検証を確立するものではありません。
