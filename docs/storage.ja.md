# ファイルの保存とアップロード

Tauriデスクトップクライアントは、選択したリモートホストのストレージを使用する。以前の試用版でも同様 `local-v1` プロファイルは開かれたり移動させられたりせずに保持されます。ご覧ください。 [デスクトップクライアント](desktop-client.ja.md).

[中文](storage.zh-CN.md)

このモジュールにはアバター、ライブラリカバー、文書画像、添付ファイルが保存されます。エディターと管理ページはアップロードAPIを共有します。文書本体には安定したアセットIDが保存されます。リソースアダプターが承認されたURLを解決します。短期間有効なCDN署名は文書には保存されません。

<a id="environment-configuration"></a>

## 環境設定

必要なファイルストレージが選択されました `DOCA_FILE_STORE_ID` そして `DOCA_FILE_STORES_JSON`両方の環境例は使用されている。 `/data/storage`公開されているコンテナの永続ボリュームと一致するように。ソース開発のため、コピーする。 `.env.example` そして、ローカルルートを自分のマシンの絶対的な書き込み可能なディレクトリに設定します。Composeは使用します。 `docker.env.example`データベースは安定したストレージIDとオブジェクト参照を記録するが、サーバー認証情報は記録しない。管理ページは読み取り専用である。

```dotenv
DOCA_FILE_STORE_ID=local
DOCA_FILE_STORES_JSON='{"version":1,"stores":{"local":{"provider":"local","root":"/data/storage"}}}'
```

専用の永続ディレクトリを使用し、サービスユーザーのみが書き込み可能で、静的ウェブツリー外で使用する。複数のインスタンスは同じ物理サーバーを共有しなければならない。バックアップにはデータベース、すべての参照されるファイルストレージ、保護されたデプロイメント設定が含まれる。参照されるストレージIDは設定を維持する必要があり、その物理パスやバケットを変更してもバイト数は移動しない。

現在のスタートアップでは、サポートされているデータベース世代を最新のDDLと照合します。サポートされていない世代や廃止されたデータベース管理型サーバー形式は、自動変換なしで閉じた状態のままです。既存のデプロイメントは、これに従わなければなりません。 [データベースアップグレード契約](database-schema-evolution.ja.md) そして [リリース要件](releases/0.2.23.md)彼らのストア、行、そして元の認証マスターキーを保持する。

## DockerのアップロードがEACCESで失敗する

もし `/api/v1/assets` HTTP 500を返し、コンテナのログが報告される `EACCES: permission denied, mkdir '/app/data'`現在地の店舗が有効かを確認してください `root` 中に `DOCA_FILE_STORES_JSON`画像は正常に動作します。 `node` と共に `/app` 作業ディレクトリとして、Composeは永続ボリュームをそこにマウントします。 `/data`. 開発ルートのようなもの `./data/v1/storage` 解決する `/app/data/v1/storage`その書き込み可能な領域の外側。

成功したファイルのアップロードが一度も行われていない店舗の場合は、ルートを設定してください。 `/data/storage`同じストアIDと他のすべてのストアエントリを維持する。環境変更は、アプリケーションコンテナのみを再作成することで行う。

```sh
docker compose up -d --no-deps --force-recreate --pull never --no-build doca
```

ストアにすでにファイルがある場合は、ルートを変更する前に実際のディレクトリやデータベースを確認し、バックアップを行ってください。設定された場所にオブジェクトのバイトデータと既存のキーを保持する計画を決め、既存のダウンロードと新しいアップロードを確認してください。設定を変更してもファイルは移動されません。パスや権限エラーを修正するためにデータボリュームを削除したり、データベースをリセットしたりしないでください。

## S3とCDN

店舗で `provider:"s3"` 必要とされる `bucket`, `region`, `forcePathStyle` そして `credentials:{accessKeyId,secretAccessKey,sessionToken?}` JSON形式の環境内で。オプションです `endpoint` 認証情報、サブパス、クエリ、またはフラグメントがないHTTP(S)ルートオリジンです。HTTPは信頼できる内部ネットワーク上の明示的に設定されたエンドポイント向けに設計されており、アプリケーションはDNSを解決して宛先をプライベートと分類することはありません。運用者がこれらの宛先とネットワークエグレスを制御し、管理UIを通じて認証情報やエンドポイントは設定されていません。バケットはプライベートのままであり、ホストとプラグインプレフィックスに対して必要な読み取り/書き込み/削除操作のみが許可されます。設定検証は実際の接続性を証明するものではありません。

共有コンテナネットワーク上でのRustFSの場合、プライベートバケットを作成し、そのS3 APIリスナーを設定します（デフォルトポート） `9000`、コンソールポート `9001`) パススタイルアドレッシングで。マッチ `region` 〜に `RUSTFS_REGION`、デフォルトでは `us-east-1`:

```dotenv
DOCA_FILE_STORE_ID=cloud
DOCA_FILE_STORES_JSON='{"version":1,"stores":{"cloud":{"provider":"s3","bucket":"doca-files","region":"us-east-1","endpoint":"http://rustfs:9000","forcePathStyle":true,"credentials":{"accessKeyId":"replace-me","secretAccessKey":"replace-me"}}}}'
```

Docaコンテナからアクセス可能なホスト名や内部アドレスを使用してください。サイト、アセット、CDNのオリジンもHTTP(S)を利用できます。詳細は [RustFS S3のドキュメント](https://docs.rustfs.com/zh/administration/protocols/s3)この例は新しいインストールのためのものです。既存のストアのエンドポイントを変更しても、そのオブジェクトは移動されません。

オプション `cdn:{domain,keyPairId,privateKey}` CloudFrontの署名されたURLプロトコルを使用します。OACと署名されたURLを必要とする信頼できるキーグループを備えたプライベートS3オリジンを設定します。CDNはオブジェクトのキー、コンテンツタイプ、および処理状況を完全に保持する必要があります。環境にはHTTP(S)配布オリジンとPEM署名キーが含まれています。最新のACLを確認した後、ホストは60秒間有効なURLを発行します。無効化は新しいリンクの使用を防ぎますが、既存のリンクは有効期限が切れるまで使用可能です。ダウンロードされたバイトデータは復元できません。

CDNがない場合、ホストがプライベートクラウドファイルをプロキシします。ストレージの秘密情報はブラウザに決して返されません。別のCDN署名プロトコルではアダプターが必要であり、永続的なパブリックURLフォールバックは提供されません。参照されるすべてのストアIDを設定し続け、認証情報のローテーション中もそのバイトへのアクセスを保つ必要があります。ローテーションはデータ移行ではありません。

## ブラウザの画像キャッシュとファイルCDN

ドキュメント/コメント画像、アシスタント画像、ホストプロキシされたアバター/カバーは安定版を使用する `/api/v1/assets/:id/content` URL。サムネイルを含む、成功したインライン画像のレスポンスは、次のように送信されます：

```http
Cache-Control: private, max-age=3600, must-revalidate
Vary: Cookie, Authorization
ETag: W/"object-and-variant-identity-digest"
```

ブラウザは1時間間、ローカルコピーを再利用できます。一度古くなれば、 `If-None-Match` 再確認する：ホストは返信する前に現在のアクセス状況を確認する `304` 画像のバイト数なし。オリジナル画像とサムネイルには異なるETagがあります。オブジェクトのキーは不変であり、画像を置き換えるには新しいアセットが必要です。Cookie/Authorizationの変更では、アカウントを切り替える際に別のキャッシュされた応答が選択されます。新鮮度の間に撤回は行われず、ダウンロードされたバイトは取り消すことはできません。ブラウザはエントリを削除でき、再読み込み/DevToolsを強制できます。 **キャッシュを無効にする** それらを回避できます。これは、追加のIndexedDBやService Workerのコピーを使わずにHTTPキャッシュを利用しています。詳細は [MDN HTTPキャッシュ](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching) 再検証のための対照 `no-store`.

## 歴史データの保存とオフラインでのアップグレード

データベースには最新の20個の完全なビジネススナップショットが保持されている。各10個の古いスナップショットの完全なグループは、設定されたファイルストレージ（S3が設定されている場合はクラウドストレージ）内の最新のポイントを保持する。ポイントとは、チェックポイントと独立した復元メタデータを保持するgzip JSONファイルであり、小さなデータベースインデックスも含まれる。不変なアップロードとSHA-256の読み戻しが成功した場合のみ、原子的なインデックスコミットと10個のデータベース行の削除が可能となる。残りの9個のポイントは意図的にサンプリングされており、復元することはできない。不完全なグループやストレージ障害の場合は、データベースのオリジナルが保持される。通常のページングリストは、ストレージの種類やオブジェクトキー、署名されたURLを公開せずに、両方のソースを統合する。

ライブチェックポイント、明らかになった共同編集の増分や添付ファイルはサンプリングされません。トラッシュは歴史を保存します。明示的な永久リソース削除キューは、1時間後の回復処理と再チェックを記録します。古いrecovery_jsonは新しいスキーマにデコードされることも、現在のベースラインから埋め込まれることもありません。欠落した回復メタデータや不明な回復バージョンは、依然としてプレビューを拒否します。ファイルにはenvelope v1、一致するハッシュ、制限された解圧、インデックス合意が必要です。バックグラウンドの持続可能なジョブは、コンテンツのコミットをブロックすることなく失敗を再試行します。

現代の世代は `doca-2026-10-12-book-payload-storage-v1`以下の歴史的メンテナンス手順は、正確な場合にのみ適用されます。 `doca-2026-10-08-knowledge-books-v2` データベース（0.1.13版）：最初に記録される `doca-2026-10-09-history-storage-v1`その後、現在の起動プロセスが承認された構造的整列を行うことができる。すべてのホストを停止し、データベース、ファイルストレージ、設定をバックアップし、マスターキーを保持した後、次のコマンドを実行する：

```sh
pnpm history:upgrade                 # Show requirements; no mutation
pnpm history:upgrade --apply         # Add structure, update baseline and queue work; no immediate sampling
```

アップグレードの代わりにデータベースを再構築しないでください。失敗したアップグレードトランザクションでは元のデータベースが保持されます。直接の履歴ロールバックはのみ受け付けられます。 `doca-2026-10-09-history-storage-v1` または、専用の中断ロールバックマーカーであり、現在のブックペイロード生成ではない。現代のデータベースについては、まず確認する。 [ブックストレージの復元](knowledge-book-storage-verification.ja.md)保存されたチェックポイント参照が、以前のロールバックを阻害する可能性があります。検証を回避するためにベースラインを再ラベル付けしないでください。適格な歴史生成データベースの場合、保持されたポイントをインポートする前に、すべてのインスタンスを停止してください。

```sh
pnpm history:rollback --apply --manifest /backup/history-cloud-references.json
```

マニフェストは新しいファイルでなければならず、0600モードで書き込まれます。ロールバックはクラウド参照を保存し、保持されたポイントを検証・インポートした後、以前のベースラインに戻ります。クラウドファイルは保持されます。中断されたロールバックでは、ホストの起動を拒否する専用マーカーが使用され、インポートされたポイントが再びサンプリングされるのを防ぎます。ストレージの問題を解決し、新しいマニフェストパスでロールバックを再実行してください。サンプリングされたポイントには、完全な事前サンプリングデータベースのバックアップが必要です。ユーザー向けの復元では、現在のエポック、権限、expectedSeqチェックが適用されます。リッチテキストとMarkdownの復元では、他のフォーマットはプレビュー専用のままです。

## チェックと権限設定

- アバターとカバーは最大5MBです。PNG、JPEG、WebP、GIFはファイルヘッダーから認識され、デコードされます。制限は2500万ピクセルです。メタデータは削除され、画像はWebP形式で保存されます。アバターは正方形に切り取り、最大512pxです。カバーは最大1600pxの幅です。GIFは最初のフレームを保持します。
- 文書/AIアップロードファイルのサイズは最大20MiBで、元のバイト数が保持されます。認識されたラスター画像は2500万ピクセルの制限で検証されます。アバター/カバー/コメント画像のパスは、目的に応じた制限で画像をWebP形式に正規化します。一般ユーザーのファイルは、2GiBの制限を持つ別のストリーミングアップロードAPIを使用します。SVGやHTMLは実行可能な画像として埋め込まれません。一般のファイルはアップロードとして提供されます。 `nosniff` そしてサンドボックスもある。ウイルススキャンはない。
- 最大4件の同時アップロードが可能で、10分間に1ユーザーあたり60回の試行が許可されます。APIはまた、最近のアップロード記録もチェックします。リバースプロキシは、自身のボディサイズ、接続数、ストレージの制限を加えるべきです。まだユーザーごとのディスククォータはありません。
- アバターのドラフトはアップロード者のみが閲覧可能です。それがバインドされた後は、サイトのログインユーザーが閲覧できます。匿名ユーザーは閲覧できません。カバーはライブラリのACLに従います。バインドされていないカバーのドラフトはアップロード者のみが閲覧可能です。添付ファイルは文書のACLに従います。システム管理者には追加の閲覧権限はありません。カバーには管理者の権限が必要です。添付ファイルにはエディターの権限が必要です。
- オブジェクトを先に記述します。その後、トランザクションがユーザーとリソースの権限を再確認し、アセットを記録します。記録が失敗した場合、未コミットのオブジェクトは可能な限り削除されます。カバー編集ではリソースバージョンを使用し、アバター編集ではプロファイルバージョンを使用します。
- 完成したが、バウンドされていないアバターやカバーのドラフトは今のところ保持されている。アセットドラフトのクリーンアップ、ユーザーごとのクォータ、ウイルススキャンはまだ実施されていない。通常のユーザーファイルのアップロードでは、32MiBから8MiBのパートによるS3マルチパートサポートが利用可能であり、これはバウンドされたアセットエンドポイントとは別物である。クラッシュにより登録されていないオブジェクトが残る可能性がある。クリーンアップではすべてのアセット参照をチェックする必要がある。あるドキュメントが削除されたからといって、共有オブジェクトを削除しないこと。

## 検証

自動テストでは、ローカルアップロード、プライベート権限、画像チェック、バインディング、衝突、安定したストレージID、プラグイン名空間、不変アーカイブの整合性が対象となります。隔離されたPostgreSQL統合と2台のローカルブラウザチェックも通過しました。S3 SDK呼び出しとCDN署名はシミュレートされており、実際のクラウド認証情報は使用されていません。実際のバケットのアップロード/ダウンロード、プライベートオリジン制御、署名の有効期限、撤回、ネットワーク障害、バックアップ復元については、サービス固有の承認がまだ必要です。詳細は [ブラウザ受け入れレポート](storage-browser-acceptance.md).
