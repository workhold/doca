# Мониторинг и телеметрия

[简体中文](plugin-monitoring.zh-CN.md)

Реализовано в исходном коде SDK **0.1.11**. Импорт `monitoringServiceToken` (`monitoring.v1`), `telemetryServiceToken` (`telemetry.v1`и их типы из `@smartdoca/plugin-sdk/monitoring`Проверка SDK 0.1.11 через npm указана в разделе публикации ниже; производственное развертывание остается отдельным.

<a id="installation-and-access"></a>

## Установка и доступ

Объявите каждую услугу, которую вы используете. `injections.required` и диапазон SDK, начиная с версии 0.1.11, например `sdkRange: "^0.1.11"`Отсутствующая услуга или устаревший диапазон SDK явно не работают. Новые услуги не имеют адаптера для старых хостов. Существующие методы… `events.v1`Структура базы данных и хранимые форматы сохраняют свою прежнюю работу.

Установленные серверные плагины — это надежный код, установленный администратором. Необходимое вмешательство в мониторинг предоставляет серверному плагину доступ к фактам работы сайта для последующего сбора данных. Это вмешательство не дает обычному пользователю доступа к этим данным. Плагины должны авторизовывать свои собственные маршруты, задачи и инструменты ИИ; никогда не отправлять глобальные логи или данные аудита обычным пользователям или автоматически в промпты моделей.

Внедрите мониторинг во время установки, чтобы активировать веб-доступ плагина. `host.platform.monitoring` вызывает тот же фиксированный метод, который был использован `/api/v1/plugin-platform/<pluginId>/monitoring.<method>`Хозяин проверяет область живого мониторинга и снова проверяет статус активного администратора в аккаунте при каждом вызове браузера. Неактивная или отсутствующая установка отклоняется существующим механизмом платформы. Не предусмотрено никаких механизмов отправки сервисов или точек ввода телеметрии через браузер. Очистка от данных отменяет область мониторинга и сохраненные сервисы. Телеметрические записи связаны с идентификатором установки.

```ts
import { definePlugin } from "@smartdoca/plugin-sdk";
import { monitoringServiceToken, telemetryServiceToken } from "@smartdoca/plugin-sdk/monitoring";
import { httpServiceToken } from "@smartdoca/plugin-sdk/platform";
import manifest from "../manifest.json" with { type: "json" };

export default () => definePlugin({
  manifest, // sdkRange: "^0.1.11"; package.json also declares doca.storage: "host"
  injections: { required: [monitoringServiceToken, telemetryServiceToken, httpServiceToken] },
  async uninstall() {},
  async mount(context) {
    const monitoring = context.inject(monitoringServiceToken);
    const telemetry = context.inject(telemetryServiceToken);
    telemetry.log(manifest.id, { level: "info", module: manifest.id, message: "Collector started" });
    await context.inject(httpServiceToken).register(manifest.id, [{
      method: "GET", path: "/metrics", admin: true,
      handle: request => monitoring.metrics({ scope: "cluster", windowSeconds: 60 }, { signal: request.signal }),
    }]);
  },
});
```

Web-пакет может читать `await host.platform.monitoring.stats({})` или `await host.platform.monitoring.logs({cursor})`Он получает типизированные DTO, включая информацию о покрытии и пробелах. Опции вызова SDK принимают сигнал AbortSignal; запросы проверяют отмену перед и после I/O, не обещая отмены уже отправленного запроса к базе данных.

## Методы чтения

| Метод | Факты и ограничения |
| --- | --- |
| `stats({})` | Количество общих баз данных: не удаленные документы, библиотеки и файлы; все активные учетные записи; логические байты файлов; зарегистрированные объекты хранения файлов и их байты. Логические байты файлов могут учитывать ссылки на один и тот же объект. Байты зарегистрированных объектов — это инвентаризация, а не объем файловой системы/бакета; приватные объекты плагинов, архивы релиза и незарегистрированные объекты не входят в этот общий показатель. |
| `online({offset?,limit?})` | Свежие реальное время соединения; люди отбираются по ID пользователя, количеству соединений, количеству активных документов и списку ID пользователей/документов. По умолчанию 100, максимум 200. Область действия — инстанс для локального присутствия и кластер для Redis. Никогда не используется старый метод отслеживания состояния; отсутствие реального времени приводит к сбоям. |
| `metrics({scope?,windowSeconds?})` | HTTP завершил запросы, 4xx, 5xx, отмененные запросы, запросы в процессе передачи данных, QPS, гистограммы частоты и длительности ошибок 5xx; группы шаблонов маршрутов и серии метрик плагинов. По умолчанию 60 секунд, поддерживается диапазон 1–300. По умолчанию кластер областей; если не настроен Redis, фактическая область, возвращаемая, — это экземпляр. |
| `logs({scope?,cursor?,limit?,level?,pluginId?,module?,requestId?,since?})` | Буферизованные структурированные операционные журналы. Сохраняется последовательность каждого эпохи, а головы экземпляров объединяются по времени; обратный отсчет никогда не выходит за пределы необработанных записей. По умолчанию 100, максимум 200. Фильтры точные, уровень не является минимальным порогом. Максимальный размер курсора – 64 КиБ. Всегда сохраняется возвращаемый курсор, даже на пустых страницах. |
| `audit({source,...})` | Существующий долгосрочный аудит безопасности или ресурсов. Необходимо `source: "security" \| "resource"`Опциональные точные данные о действии/идентификаторе актера и идентификаторе пользователя/ресурса, связанных с источником, ISO времени начала/окончания, курсор и лимит. Фильтры, не связанные с источником, не работают. Детали безопасности скрыты; нечитаемые/не связанные с объектом данные… `null` с `detailsValid:false`Никакие записи не переписываются. |
| `jobs({})` | Группы статусов общей базы данных, AI/проекции, извлечения файлов, истекшие арендные соглашения AI/проекций и приватные объекты, ожидающие удаления. Категории проекций включают задачи, уже использующие эту очередь. Это не означает, что каждый бизнес-плагин использует хост-очередь. |
| `jobErrors({source,limit?})` | Новейшие ошибки, связанные с AI/проекцией/экстракцией файлов; нет промптов, полезной информации или результатов. Это новый диагностический пример, а не полный архив ошибок с пагинацией. `nextCursor` всегда равно null. Регистры проекции не имеют надежного временного стека обновления ошибок, поэтому `updatedAt` Это null, и порядок сортировки использует атрибут available_at. |
| `aiUsage({...})` | Страницы снимков общих реестров, точные ID пользователя/модели/статус, даты начала/окончания в формате ISO. ID вызова/задания/модели, статус, оцененные токены и числовые метрики оригинального поставщика. Неизвестное использование равно нулю; старые числовые колонки SQL никогда не использовались для оценки. Указанные записи, не соответствующие текущему состоянию,… `usageStatus:"invalid"`, оставлены без изменений. Секреты, данные от поставщиков и файлы снимков моделей не включены. |
| `health({scope?})` | Версия, экземпляры, процесс RSS/heap/cumulative CPU/event-loop P95, проверка чтения базы данных и готовность к реальному времени/cache. Проверки хранения/поиска/сети AI проводятся явно. `not-probed`Обзор здоровья не вызывает оплаты модели или не записывает объект теста хранения. |

Аудит и пагинация данных по использованию по умолчанию равны 100, а количество записей – 200. Курсор фиксирует верхний временной предел, включает отпечаток запроса, и сортирует по полю created_at, а затем по ID; некорректные/несоответствующие курсоры не работают. Эти чтения представляют собой инвентаризацию, а не обновления данных. Для долговременного использования данных в системе AI-счетов используйте существующие ресурсы. `events.v1` / `ai.usage.recorded`Ранее отложенный звонок может быть завершен после прочтения страницы, созданной во время его создания. Все оригинальные интерфейсы аудита и использования остаются доступными с их первоначальным поведением.

## Запросы метрик и пользовательские метрики

Метрики HTTP учитывают все нормальные HTTP маршруты, включая запросы администратора/платформы/о здоровье. Соединения WebSocket исключаются; для их соединений используется реальное время присутствия. Отклонения учитываются отдельно от завершенных ответов. Уровень ошибок составляет 5xx/завершенных ответов; для пустого окна значение равно нулю. QPS учитывает скорость запросов в экземпляре в течение фактически охваченного окна, с ограничением до момента запуска. Отчеты о снимках указывают время выборки и момент запуска, чтобы потребители могли оценить задержку выборки.

Время откликов используют эксклюзивные бакеты в миллисекундах: 1, 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000 и неограниченное количество. P50/P95/P99 – это оценки верхних пределов бакетов, ограниченные максимальными значениями, зафиксированными в данных; процентилы кластеров суммируют количество бакетов, а не средние процентилы экземпляров. Для пустой распределения минимум/максимум/процентилы равны нулю. Лabels маршрутов используют зарегистрированные шаблоны маршрутов, а не строки запросов или динамические URL ресурсов. Первые 64 группы маршрутов/методов сохраняются для каждого процесса; дополнительные группы… `[other-routes]`.

```ts
telemetry.record(manifest.id, {
  name: manifest.id + ".sync.completed", kind: "counter", value: 1,
  labels: { source: "mail" },
});
telemetry.record(manifest.id, {
  name: manifest.id + ".sync.duration_ms", kind: "histogram", value: 120,
});
```

Названия метрик начинаются с ID плugина-владельца и точки. Виды — счетчик (неотрицательные увеличения), гейдж (последнее конечное значение) и гистограмма (неотрицательные наблюдения, использующие те же числовые бакеты). Изменения видов и ключей метки под одним именем не работают с кодом 409. Можно использовать до шести меток, 100 символов/значения, 200 серий/плугинов и 1,000 пользовательских серий/инстановок; новые избыточные серии не работают с кодом 429 и увеличение отклоняется через MetricSeries. Метки, похожие на секреты, и числовой переполнение не работают. Используйте ограниченные категории вместо идентификаторов пользователя/запроса/документа. Пользовательские серии возвращаются для каждой инстанции/эпохи; сброс счетчика и агрегация гейджа остаются явными решениями потребителя. Их значения — с момента начала совокупные/последние, независимые от HTTP-rolling-окна. Авторы плугинов могут выводить свои собственные зависимости/факты работы через пользовательские метрики.

## Логи, хранение и покрытие кластера

Логи хоста включают структурированные логи приложения Fastify, когда включен логирование хоста, а также HTTP-ошибки, откавы и запросы, длительностью не менее двух секунд, независимо от логирования stdout. Линии обычных успешных запросов представлены в виде метрик. Логи плагинов содержат id плагина, epoch, instanceId, последовательность, время создания и опциональный requestId. Секретные ключи, тело запроса, запросы, полезная нагрузка, снимки моделей и стек ошибок удаляются или редактируются; URL userinfo/query/hash и общие строки учетных данных очистываются. Логирование произвольного секретного текста не может быть безопасным с помощью поиска по шаблонам: авторам никогда не следует размещать секреты или тела документов в message/module/requestId/fields.

Каждый экземпляр хранит не более 2,000 записей и 2 МиБ сериализованных данных лога. Количество удаляемых байт увеличивает порог последовательности, а количество потерянных записей также увеличивается. Сохраненный курсор за этот порог сообщает о разнице в количестве удаляемых записей, включая потерянное количество. При перезапуске экземпляр получает новый эпоха, даже если ID экземпляра повторно используется. Отсутствие предыдущей эпохи сообщает о невозможности использования экземпляра; некорректно обработанные новые представления кэша отмечаются как недоступные, сохраняются до истечения срока действия и никогда не обновляются или возвращаются в качестве содержимого.

С настроенным Redis хосты выпускают снимки версии 1 каждые пять секунд в отдельном режиме. `monitoring:v1` Ключевой пространство имён. Закрытые экземпляры или снимки, старые более 15 секунд, считаются устаревшими и исключаются из текущих общих метрик, в то время как сохранённые логи могут быть удалены. Снимки и записи о известных экземплярах истекают через час; устаревшие/отсутствующие/некорректные экземпляры… `complete:false`Кластерный доступ обновляет ответную инстанцию и читает другие снимки. Можно сохранять до 128 эпох и 16 МБ/снимок в секунду; более крупные инвентарные объемы невозможны. Ошибки в Redis не приводят к переходу конфигурированного кластера на локальные данные. Локальный режим остается явным диагностическим вариантом. Этот кэш временный и не гарантирует долговечной доставки или обнаружения флота смешанных версий: хосты, не имеющие нового издателя, не входят в его инвентарь.

Мониторинговые плагины хранят исторические агрегаты, записи логов, курсоры, метки разрывов и состояние уведомлений через хранилище, управляемое хостом. Логи дедуплицируются по идентификатору, записи коммитов с их курсором обрабатываются в одной транзакции плагина, а разрывы отмечаются и отчитываются как таковые. Сэмплирование не восстанавливает потерянный окно запроса. Хост сохраняет данные аудита безопасности и факты использования ИИ; плагины не могут удалить их через этот SDK.

<a id="upgrade-rollback-and-verification"></a>

## Установка обновлений, откат и проверка

Это добавление не изменяет таблицы хост-базы данных, базовые параметры, формат аудита, формат AI-листов или существующую структуру данных плагинов. Существующие альтернативы online-heartbeat и AI historical-reading остаются на своих первоначальных путях. Новые факты работы программы начинаются при запуске обновленного процесса; исторический вывод стандартного входа не импортируется. Новые плагины требуют SDK 0.1.11 и не работают на старых хостах. Откат кодов сохраняет существующие постоянные данные и исторические записи плагинов; плагины, требующие новых сервисов, отключаются перед запуском старого хоста. Кэш мониторинга может истечь без влияния на авторитетные данные.

Тестирование проводится с использованием изолированных баз данных/документов и уникального пространства имен Redis. Приемка включает объединение запросов/гистограмм, уменьшение дубликатов пользователей, фильтры/пагинация/удаление курсора, скрытие секретов, отказ в доступе обычных пользователей и отозванных администраторов, обеспечение соблюдения пространства имен/версий/цикла жизни, устаревшие/отсутствующие/некорректные кэшированные данные и эпохи перезапуска, а также сборка SDK и независимый потребитель JavaScript/деклараций. Публикация в npm, плагин для мониторинга производства и производственное развёртывание — это отдельные процессы.
