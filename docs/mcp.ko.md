## 발견하고 실행하기

1. 전화하기 `doca_tools` 전체 작업이 완료되었습니다. `purpose`. 선택적 `resources`, `files`, `currentResourceId` 그리고 `currentFolder` 기존 문서/파일 UUID를 사용하여 명시적인 맥락을 제공합니다. 파일 참조는 어시스턴트가 사용하는 동일한 승인된 입력 스냅샷을 받습니다. 결과에는 `contextId`, 독립적인 `taskId`그리고 간결한 카탈로그입니다. 대화는 생기지 않습니다.
2. 전화하기 `doca_describe_tools` 그렇다면 `contextId` 전체 입력 스키마를 얻기 위해 최대 4개의 도구 ID를 사용할 수 있습니다. 다음 작업에 필요한 스키마만을 가져옵니다.
3. 매뉴얼을 완독하세요. `doca_skills`/`doca_load_skill`또는 표준 `doca_skill` MCP 프롬프트. 이들은 현재 카탈로그를 읽습니다; 비활성화된 개인 SKILL은 더 이상 사용할 수 없습니다.
4. 전화하기 `doca_call` 순차적으로 `contextId`새로운 UUID `requestId`, `tool` 그리고 `input`원본 수정은 현재 상태를 사용합니다. `seq`, `epochId`일반 문서 도구에서 반환되는 ID와 명령어입니다. 이는 동일한 어시스턴트 구현 방식이며, 동일한 네이티브 코덱, 트랜잭션, 알림, 그리고 Doca 제공자가 실제로 호출될 때의 원본 AI 사용 내역도 포함됩니다. 외부 클라이언트 모델의 사용은 Doca의 내역에 포함되어 있지 않습니다.
5. 전화하기 `doca_context_close` 완료되면, 저장된 문서/파일은 그대로 유지됩니다. 대기 중인 업로드 버퍼와 로컬 시각 검사 상태도 해제됩니다.

개인적인 작업은 생략됨 `userId`그것을 제공하는 것은 거부됩니다. 회사는 매번 활성 타겟 사용자의 UUID를 제공해야 합니다. 컨텍스트는 서비스나 실제 사용자를 변경할 수 없습니다. 검색, 읽기, 쓰기, 다운로드 작업은 해당 사용자의 권한을 확인합니다. 감사 기록에는 서비스 창조자, 실제 사용자, 컨텍스트, 요청 ID, 도구 및 결과가 기록되지만 입력된 비밀 정보는 기록되지 않습니다.

`requestId` 자신의 컨텍스트 내에서 최대 한 번만 실행을 제공합니다. 반복된 ID는 기록된 상태와의 HTTP/tool 충돌을 일으키며, 다른 매개변수로는 그 ID를 재사용할 수 없습니다. 캐시된 개인 콘텐츠를 다시 재생하거나, 완료된可能性이 있는 쓰기 작업을 맹목적으로 재시도하지 않습니다. 불확실한 결과가 나온 후 새로운 쓰기를 수행하기 전에 저장된 리소스를 검사해야 합니다. 일반적인 네이티브 및 파일 워크플로우는 기존의 견고한 기록을 유지합니다.

## 파일들

원주민 `file_browse`, `file_manage`, `file_folder_manage`, `file_read` 그리고 `file_create` 도구들은 여전히 사용 가능합니다. `file_download` assistant의 의미를 유지: 공개 웹 파일을 가져오기 **안으로** 도카.

실제 고객 전송에 관한 내용:

- `file_upload_begin`: 파일명, MIME 타입, 선언된 크기 및 선택적 SHA-256; 최대 20 MiB이며, 더 엄격한 사용자 제한도 가능.
- `file_upload_chunk`: 표준적인 base64, 연속적인 바이트 오프셋; 최대 디코딩된 데이터 크기 128 KiB.
- `file_upload_complete`완료된 업로드를 사용자 폴더 UUID에 저장하거나 `folderId:null` 사용자의 루트에 대해서입니다. 업로드된 파일은 서비스 컨텍스트와 효과적인 사용자와 연결됩니다.
- `file_upload_abort`대기 중인 업로드를 발행합니다.
- `file_content`base64를 사용한 허가된 바이트 범위 다운로드, 전체 파일/청크 SHA-256, 파일 버전 및 `nextOffset`같은 버전을 다음 부분들에도 전달하세요; 변경된 파일은 거부하고 버전을 결합하지 마세요.

이러한 방법들은 호스트 파일 서비스를 재사용합니다. 브라우저 쿠키나 서버 파일 시스템 경로가 필요하지 않으며, 콘텐츠를 읽은 URL을 다운로드 권한 우회로 전환하지도 않습니다.

## 운송 및 수명

엔드포인트는 SDK 1.30.0의 stateless Streamable HTTP를 사용하며, 명시적으로 허용되는 프로토콜 버전을 사용합니다. `2025-11-25`, `2025-06-18` 그리고 `2025-03-26`초기화 시 지원되는 버전을 명시해야 하며, 이후 요청에서는 그 버전을 반드시 포함해야 합니다. `MCP-Protocol-Version`GET/DELETE 요청은 인증된 405 응답을 반환합니다. 기존 호스트 규칙이 적용되며, 유효하지 않은 Origin 값은 거부됩니다. 폐기된 HTTP+SSE 및 오래된 토큰 어댑터는 지원되지 않습니다.

실행 컨텍스트는 15분의 대기 시간을 가지며, 각 서비스당 최대 16개의 활성/대기 컨텍스트와 각 인스턴스당 128개의 컨텍스트가 있습니다. 한 컨텍스트 내의 호출은 순차적으로 이루어집니다. 도구/기술 보너스, 토큰 및 활성 사용자는 다시 확인됩니다. 토큰을 재설정하거나 취소하거나 서비스를 비활성화하거나 개인 MCP를 끄면 해당 MCP의 실시간 컨텍스트가 무효화됩니다. 호스트 속도 제한기를 사용하는 각 서비스의 HTTP 요청 제한은 분당 600개입니다. 요청 바디는 1 MiB로 제한됩니다.

컨텍스트 실행 및 시각적 증명은 인스턴스 로컬입니다. 활성 컨텍스트를 동일한 인스턴스로 라우팅합니다. 재시작 후 만료되거나 다른 인스턴스로 라우팅될 때, 새로운 컨텍스트를 열고 기존 아티팩트를 검사합니다. 자동적인 연속성 또는 시각적 증명 복구는 제공되지 않습니다. 네이티브 문서 데이터는 일반적인 내구성 있는 저장소에 남아 있습니다. 제공자 자격 정보, 비밀 값, 브라우저 세션 및 임의의 이전 채팅 기록은 MCP 설정으로 내보내지지 않습니다.

## 실행 기록 및 업그레이드

MCP와 채팅은 작업 임대, 취소, 리소스 승인, 도구 구현, 운영 영수증, 제공자 사용 사실 및 보안 감사를 공유합니다. MCP는 `ai_jobs` NULL로의 실행 `session_id` 그리고 `model_id`; 그것은 생성하지 않습니다 `ai_sessions` 행, 채팅 메시지 또는 메모리 스레드. 실제 제공자 호출은 여전히 실제 모델과 사용량을 기록합니다. `ai_calls`.

개인 설정 → MCP → 실행 기록은 해당 사용자가 수행한 회사 서비스 작업을 포함한 유효한 사용자의 작업을 표시합니다. 승인된 리소스 링크, 통화 상태, 닫힌 실행 기록의 중단 및 삭제 기능을 지원합니다. 기록을 삭제하면 저장된 문서, 생성된 파일, 작업 영수증, 원본 제공자 사용 정보 및 보안 감사 사실이 보존됩니다. 생성된 이미지는 AI 출력 디렉터리의 제한 사항을 유지하며 명시적인 정보를 포함합니다. `aiTaskId` 대화 폴더 없이 바인딩됩니다. 작업은 자신만의 수신 내용만 읽습니다; NULL 대화 연관성은 관련 없는 실행을 결코 그룹화하지 않습니다.

소유자는 2026-11-01에 직접 분리를 승인했습니다. 현재의 DDL은 `ai_jobs.session_id`, `ai_jobs.model_id` 그리고 남아있는 것 `mcp_contexts.session_id` 기존의 네이티브 컬럼 조정기로 통해 유효하지 않음. 새로운 `ai_task_resources` 레거시는 비어 있게 시작되며 선언됩니다. `schemaEvolution`백업이나 호환성 생성 관련 변경 사항은 없습니다. 과거의 MCP 대화, 컨텍스트, 파일, 보조금 및 감사 행은 그대로 유지되며, 채팅 기록에서 제외되고, 변환되거나 재시작되지 않습니다. 이전에 설치된 필드/테이블은 설치된 파일로 보호됩니다.

플러그인 SDK 소스 0.2.0이 공개됨 `ai.v2` / `ai.continuations.v2`: `jobId` 필요하며 `sessionId` 대화 기반 실행을 위해서만 존재합니다. 플러그인 패키지를 재구축해야 합니다. `sdkRange: "^0.2.0"`호스트, 웹 및 플러그인은 함께 업데이트되어야 합니다. 오래된 서비스 계약과 SDK 범위는 거부되며, 기존 인터페이스 어댑터나 자동 다운그레이드 기능도 없습니다. 업그레이드 전에 데이터베이스/파일 백업을 보관하고, 애플리케이션 바이너리를 복구하기 전에 별도로 검토된 복구 절차에 따라 후속 작업/파일 작성 내용을 보존해야 합니다. 참조하십시오. ## 저장 및 퇴역된 MCP

소유자는 2026-10-20에 사용되지 않는 오래된 구현을 폐기하는 것을 승인했습니다. `/ai/mcp-keys` 그리고 오래된 4가지 도구 어댑터가 제거됩니다. `doca_mcp_…` 자격 증명이 거부되었습니다; 새로운 토큰을 사용합니다. `doca_mcp_v1_…`. 무활동 `ai_mcp_keys` table/rows는 저장된 데이터를 보존하기 위해서만 남아 있습니다. 실행 시간에 이를 읽지 않으며, 자격 증명이나 권한도 변환되지 않습니다.

`mcp_user_settings`, `mcp_services`, `mcp_contexts` 그리고 `mcp_tool_calls` 현재의 DDL에서 선언된 비어 있는 추가적 테이블들 `schemaEvolution`기존 사용자는 새로운 설정 행이 없기 때문에 개인용 MCP가 비활성화된 상태로 시작됩니다. 회사 서비스 사용은 그 설정과는 독립적입니다. 기존 문서, 파일, ACL, AI 세션, 설정된 값 및 호환성 정보는 그대로 유지됩니다. 구조적 검토 거부나 불완전한 조정은 부분적인 영구적 변경을 일으키지 않습니다. 이전에 설치된 MCP 테이블이 제거될 경우 데이터 손실이 발생하며, 이는 무시되지 않습니다.

사전 업그레이드 백업을 유지하고 서버/웹을 함께 업그레이드하세요. 오래된 바이너리들은 새로운 토큰/보조금/컨텍스트 계약을 적용하지 않습니다. 자동적인 애플리케이션 다운그레이드나 데이터 삭제는 없습니다; 새로운 기록을 보존하고 더 오래된 배포로 돌아가기 전에 복구를 검토하세요. 자세한 내용은...을 참조하세요. [데이터베이스 업그레이드 계약](database-schema-evolution.ko.md) 그리고 [수락 증거](verification/mcp-2026-10-20/README.md).
