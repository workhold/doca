# 모니터링 및 텔레메트리

[简体中文](plugin-monitoring.zh-CN.md)

SDK 소스에 구현됨 **0.1.11**. 수입 `monitoringServiceToken` (`monitoring.v1`), `telemetryServiceToken` (`telemetry.v1`)과 그 유형들 `@smartdoca/plugin-sdk/monitoring`SDK 0.1.11 npm 검증은 아래의 발표 섹션에 기록되어 있으며, 프로덕션 배포는 별도로 진행됩니다.

<a id="installation-and-access"></a>

## 설치 및 접근

사용하는 각 서비스를 명시하세요. `injections.required` 예를 들어 0.1.11부터 시작하는 SDK 범위입니다. `sdkRange: "^0.1.11"`누락된 서비스나 오래된 SDK 범위는 명확하게 실패합니다. 새로운 서비스에는 기존 호스트 어댑터가 없습니다. 기존 방법들도 마찬가지입니다. `events.v1`데이터베이스 구조와 저장 형식은 이전과 동일한 동작을 유지합니다.

설치된 서버 플러그인은 관리자가 설치한 신뢰할 수 있는 코드입니다. 필수적인 모니터링 인젝션 기능은 서버 플러그인이 백그라운드 데이터 수집을 위해 사이트 운영 정보에 접근할 수 있도록 해줍니다. 인젝션은 일반 사용자에게 해당 데이터에 접근할 수 있는 권한을 부여하지 않습니다. 플러그인은 자신만의 라우트, 작업 및 AI 도구를 인증해야 하며, 일반 사용자나 모델 프롬프트에게 전 세계 로그나 감사 데이터를 자동으로 전송해서는 안 됩니다.

마운트 과정 중 모니터링을 실행하여 플러그인의 웹 접근을 활성화합니다. `host.platform.monitoring` 동일한 고정 메서드를 호출합니다. `/api/v1/plugin-platform/<pluginId>/monitoring.<method>`호스트는 실시간 모니터링 범위를 확인하고 각 브라우저 호출 시 계정의 활성 관리자 상태를 다시 확인합니다. 존재하지 않는/비활성화된 설치는 기존 플랫폼 게이트에 의해 거부됩니다. 일반적인 서비스 전송이나 브라우저 텔레메트리 쓰기 엔드포인트는 제공되지 않습니다. 폐기 과정에서는 범위와 유지된 서비스 처리 기능이 취소됩니다. 텔레메트리 쓰기는 설치 ID에 연결됩니다.

```ts
import { definePlugin } from "@smartdoca/plugin-sdk";
import { monitoringServiceToken, telemetryServiceToken } from "@smartdoca/plugin-sdk/monitoring";
import { httpServiceToken } from "@smartdoca/plugin-sdk/platform";
import manifest from "../manifest.json" with { type: "json" };

export default () => definePlugin({
  manifest, // sdkRange: "^0.1.11"; package.json also declares doca.storage: "host"
  injections: { required: [monitoringServiceToken, telemetryServiceToken, httpServiceToken] },
  async uninstall() {},
  async mount(context) {
    const monitoring = context.inject(monitoringServiceToken);
    const telemetry = context.inject(telemetryServiceToken);
    telemetry.log(manifest.id, { level: "info", module: manifest.id, message: "Collector started" });
    await context.inject(httpServiceToken).register(manifest.id, [{
      method: "GET", path: "/metrics", admin: true,
      handle: request => monitoring.metrics({ scope: "cluster", windowSeconds: 60 }, { signal: request.signal }),
    }]);
  },
});
```

웹 번들은 읽을 수 있습니다. `await host.platform.monitoring.stats({})` 아니면 `await host.platform.monitoring.logs({cursor})`그것은 커버리지와 격차를 포함한 타입화된 DTO를 받습니다. SDK 호출 옵션은 AbortSignal을 허용합니다; 쿼리는 I/O 전후에 취소 여부를 확인하지만, 이미 제출된 데이터베이스 명령의 취소는 보장하지 않습니다.

## 읽기 방법

| 방법 | 사실과 한계 |
| --- | --- |
| `stats({})` | 공유 데이터베이스 수: 삭제되지 않은 문서, 라이브러리 및 파일; 모든/활성 계정; 논리 파일 바이트; 등록된 파일 저장 객체 및 바이트. 논리 파일 바이트는 동일한 객체에 대한 참조를 포함할 수 있습니다. 등록된 객체 바이트는 파일 시스템/버킷 용량이 아닌 재고 수치입니다; 개인용 플러그인 객체, 릴리스 아카이브 및 등록되지 않은 객체는 이 총계에 포함되지 않습니다. |
| `online({offset?,limit?})` | 신선한 실시간 연결; 사용자 ID, 연결 수, 활성 문서 수, 사용자 ID/문서 ID 페이지를 기준으로 중복된 사람을 제거합니다. 기본값은 100, 최대는 200입니다. 범위는 로컬 존재를 위한 인스턴스와 Redis를 위한 클러스터입니다. 오래된 하트비트 대안을 절대 사용하지 않으며, 실시간 연결 불가능 시 작동하지 않습니다. |
| `metrics({scope?,windowSeconds?})` | HTTP 요청 완료, 4xx, 5xx, 중단된 요청, 진행 중인 요청, QPS, 5xx 오류율 및 지속 시간 히스토그램; 라우트-템플릿 그룹 및 플러그인 메트릭 시리즈. 기본값은 60초이며, 1–300까지 지원됩니다. 기본 범위 클러스터; 설정된 Redis가 없으면 실제 반환되는 범위는 인스턴스입니다. |
| `logs({scope?,cursor?,limit?,level?,pluginId?,module?,requestId?,since?})` | 버퍼링된 구조화된 운영 로그. 각 에포크의 순서를 보존하고 시간에 따라 인스턴스 헤드를 병합합니다. 시계 역전은 처리되지 않은 항목을 넘어서는 결코 진행되지 않습니다. 기본값은 100, 최대는 200입니다. 필터는 정확하며, 레벨은 최소 임계값이 아닙니다. 커서 크기는 최대 64 KiB입니다. 빈 페이지에서도 반드시 반환된 커서를 저장합니다. |
| `audit({source,...})` | 기존의 지속 가능한 보안 또는 자원 감사. 필요. `source: "security" \| "resource"`; 선택적 정확한 액션/actorId 및 소스별 userId/resourceId, ISO 시작/종료일, 커서 및 제한값. 소스와 관련 없는 필터는 실패합니다. 보안 정보는 가명 처리되었으며, 읽을 수 없거나 비목적적인 정보는 `null` 와서 `detailsValid:false`기록은 다시 작성되지 않습니다. |
| `jobs({})` | 공유 데이터베이스 AI/프로젝션/파일 추출 상태 그룹, 만료된 AI/프로젝션 임대 계약, 그리고 삭제 대기 중인 개인 객체가 있습니다. 프로젝션 유형에는 이미 해당 큐를 사용하는 작업도 포함됩니다. 이는 모든 비즈니스 플러그인이 호스트 큐를 사용한다는 것을 의미하지 않습니다. |
| `jobErrors({source,limit?})` | 최신 제한된 AI/프로젝션/파일 추출 오류; 프롬프트, 페이로드 또는 결과가 없습니다. 이는 최근의 진단 샘플이며, 전체 페이지화된 오류 아카이브는 아닙니다. `nextCursor` 항상 null입니다. 프로젝션 레코드에는 신뢰할 수 있는 오류 업데이트 타임스탬프가 없으므로 `updatedAt` null이며, 정렬은 available_at을 사용합니다. |
| `aiUsage({...})` | 공유된 레지스트의 스냅샷 페이지, 정확한 userId/modelId/state, ISO 기준 시작/종료일. 호출/job/model ID, 상태, 평가된 토큰 및 원본 제공자의 숫자 지표. 알 수 없는 사용량은 null이며, 오래된 SQL 숫자 컬럼으로는 절대 추정할 수 없다. 현재 표현과 일치하지 않는 확인된 항목은 `usageStatus:"invalid"`, 그대로 유지됩니다. 비밀 정보, 공급업체의 원시 응답 및 모델 스냅샷은 생략됩니다. |
| `health({scope?})` | 버전, 인스턴스, 프로세스 RSS/heap/누적 CPU/이벤트 루프 P95, 데이터베이스 읽기 프로브 및 실시간/캐시 준비 상태. 저장소/검색/AI 네트워크 프로브는 명시적으로 `not-probed`건강 리드는 유료 모델을 호출하거나 저장 테스트 객체를 작성하지 않습니다. |

감사 및 사용 페이징은 기본적으로 100으로 설정되며 200개의 레코드까지 허용됩니다. 커서는 최대 시간 한도를 설정하고 쿼리 피해석 정보를 포함하며, created_at 순서로 ID를 기준으로 정렬됩니다. 잘못된/일치하지 않는 커서는 작동하지 않습니다. 이러한 읽기 작업은 변화 피드가 아닌 재고 조회입니다. 지속적인 AI 결제 처리를 위해서는 기존 설정을 사용하세요. `events.v1` / `ai.usage.recorded`이전에 대기 중이었던 통화는 생성 시점의 페이지가 읽힌 후에 종료될 수 있습니다. 모든 원본 감사 및 사용 인터페이스는 원래의 동작을 그대로 유지합니다.

## 요청 지표 및 커스텀 지표

HTTP 메트릭은 관리자/플랫폼/건강 관련 요청을 포함한 모든 일반적인 HTTP 경로를 포함합니다. WebSocket 핸드셰이크/메시지는 제외되며, 이들의 연결은 실시간 존재성으로 처리됩니다. 중단은 완료된 응답과는 별도로 계산됩니다. 오류율은 5xx 코드의 완료된 응답 수이며, 빈 창의 경우는 null입니다. QPS는 실제 커버되는 시간대 동안의 인스턴스 요청 속도를 합산한 값으로, 시작 시점까지 제한됩니다. 스냅샷 보고서는 샘플링 시간과 시작 시점을 포함하므로, 사용자는 샘플링 지연을 평가할 수 있습니다.

지속 시간은 1, 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000, 그리고 무제한인 독점 밀리초 버킷을 사용합니다. P50/P95/P99는 관측된 최대값으로 제한된 버킷 상한 추정치입니다; 클러스터 백분위수는 평균 인스턴스 백분위수가 아닌 버킷 수를 합산합니다. 비어 있는 분포는 null min/max/quantiles를 가집니다. 라우트 라벨은 등록된 라우트 템플릿을 사용하며, 쿼리 문자열이나 동적 리소스 URL은 사용되지 않습니다. 처리 에포크마다 처음 64개의 라우트/방법 그룹이 유지되며, 추가 그룹은 공유됩니다. `[other-routes]`.

```ts
telemetry.record(manifest.id, {
  name: manifest.id + ".sync.completed", kind: "counter", value: 1,
  labels: { source: "mail" },
});
telemetry.record(manifest.id, {
  name: manifest.id + ".sync.duration_ms", kind: "histogram", value: 120,
});
```

메트릭 이름은 소유하는 플러그인 ID와 점으로 시작합니다. 종류는 카운터(부정적이지 않은 증가), 게이지(최신 유한 값), 히스토그램(동일한 숫자 버킷을 사용하는 부정적이지 않은 관측치)입니다. 한 이름 하에서 종류와 레이블-키를 변경하면 409 에러가 발생합니다. 최대 6개의 레이블, 100자리/값, 200개의 시리즈/플러그인, 1,000개의 커스텀 시리즈/인스턴스가 가능합니다; 새로운 과잉 시리즈는 429 에러와 함께 증가가 거부됩니다. 비밀 같은 레이블과 숫자 오버플로우는 실패합니다. 사용자/요청/문서 ID 대신 제한된 범주를 사용하세요. 커스텀 시리즈는 인스턴스/에포크별로 반환됩니다; 카운터 재설정과 게이지 집계는 명시적인 소비자 결정입니다. 그 값은 시작부터의 누적/최신 값으로, HTTP 롤링 윈도우와는 독립적입니다. 플러그인 개발자는 커스텀 메트릭을 통해 자신의 의존성/작업 사실을 노출할 수 있습니다.

## 로그, 보관 및 클러스터 커버리지

호스트 로그는 호스트 로깅이 활성화된 경우 구조화된 Fastify 애플리케이션 로그를 포함하며, stdout 로깅 여부와 관계없이 최소 2초가 걸리는 HTTP 오류/거부/요청도 포함됩니다. 일반적인 성공적인 요청 라인은 지표로 표시됩니다. 플러그인 로그에는 호스트와 관련된 플러그인Id, 에포크, 인스턴스Id, 시퀀스, 생성 시간 및 선택적 요청Id가 포함됩니다. 민감한 키, 요청 본문, 프롬프트, 페이로드, 모델 스냅샷 및 오류 스택은 삭제되거나 수정됩니다. URL의 userinfo/query/hash 및 일반적인 자격 증명 문자열도 삭제됩니다. 임의의 비밀 텍스트를 로깅하는 것은 패턴 매칭으로 안전하게 만들 수 없습니다. 작성자들은 메시지/모듈/요청Id/필드에 비밀 또는 문서 본문을 절대로 포함해서는 안 됩니다.

각 인스턴스는 최대 2,000개의 레코드와 2 MiB의 시리얼라이즈된 로그 데이터를 저장합니다. Count/byte eviction은 시퀀스 워터마크와 삭제된 개수를 증가시킵니다. 그 워터마크 뒤에 저장된 커서는 손실된 개수를 포함한 명시적인 삭제 간격을 보고합니다. 인스턴스는 재시작 시 새로운 에포크를 가지며, instanceId가 재사용되더라도 마찬가지입니다. 이전 에포크가 없는 경우는 인스턴스 사용 불가 간격을 보고합니다. 잘못된 새로운 캐시 표현은 사용 불가로 표시되어 만료될 때까지 유지되며, 결코 적용되거나 콘텐츠로 반환되지 않습니다.

설정된 Redis를 사용하면 호스트는 5초마다 별도의 버전 1 스냅샷을 게시합니다. `monitoring:v1` 키 네임스페이스. 15초보다 오래된 폐쇄된 인스턴스나 스냅샷은 유효하지 않으며 현재 메트릭 총계에서 제외되지만, 보존된 로그는 여전히 삭제될 수 있습니다. 스냅샷과 알려진 인스턴스 기록은 1시간 후에 만료됩니다. 유효하지 않거나 누락된/잘못된 인스턴스는... `complete:false`클러스터 읽기 방식은 응답하는 인스턴스를 새로 불러오고 다른 스냅샷도 읽습니다. 최대 128개의 보존 에코시와 16 MiB/스냅샷이 가능하며, 더 큰 저장 공간은 사용할 수 없습니다. Redis 오류가 발생해도 설정된 클러스터 요청이 로컬 데이터로 감소되지는 않습니다. 로컬 범위는 명시적인 진단 옵션으로 남습니다. 이 캐시는 일시적이며, 안정적인 전달이나 혼합 버전 플릿 발견을 보장하지 않습니다. 새로운 출판자가 없는 호스트는 이 저장 공간에 포함되지 않습니다.

모니터링 플러그인은 호스트가 관리하는 저장소를 통해 역사적 집계 데이터, 로그 기록, 커서, 간격 표시기 및 알림 상태를 저장합니다. ID별로 로그를 중복 제거하고, 커서와 함께 하나의 플러그인 트랜잭션으로 기록을 커밋하며, 간격은 간격으로 인정/보고합니다. 샘플링은 손실된 요청 창을 재구성하지 않습니다. 호스트는 보안 감사 및 원본 AI 사용 사실을 유지하며, 플러그인은 이 SDK를 통해 이를 삭제할 수 없습니다.

## 업그레이드, 롤백 및 검증

이 추가는 호스트 데이터베이스 테이블, 기준값, 감사 형식, AI 원장 형식 또는 기존 플러그인 데이터 구조에는 변화를 주지 않습니다. 기존의 온라인-heartbeat 및 AI 역사적 읽기 대안들은 원래의 경로에 그대로 남습니다. 새로운 런타임 사실은 업그레이드된 프로세스 시작 시부터 적용되며, 역사적 stdout은 가져오지 않습니다. 새로운 플러그인은 SDK 0.1.11이 필요하며, 더 오래된 호스트에서는 작동하지 않습니다. 코드를 롤백하면 기존의 영구 데이터와 플러그인 역사적 기록이 보존되며, 더 오래된 호스트를 시작하기 전에 새로운 서비스가 필요한 플러그인은 비활성화됩니다. 모니터링 캐시는 권위 있는 데이터에 영향을 주지 않으면서 만료될 수 있습니다.

테스트에는 격리된 데이터베이스/문서와 고유한 Redis 네임스페이스가 사용됩니다. 인수 검증에는 요청/히스토그램 병합, 사용자 중복 제거, 필터/페이징/커서 제거, 비밀 정보 숨김, 일반 사용자 및 폐지된 관리자의 거부, 네임스페이스/버전/라이프사이클 강제 적용, 유효하지 않은 캐시 및 재시작 에포크, 그리고 SDK 빌드와 독립적인 JavaScript/선언 소비자도 포함됩니다. npm 출시, 생산 모니터링 플러그인, 생산 배포는 별도의 제공 사항입니다.
